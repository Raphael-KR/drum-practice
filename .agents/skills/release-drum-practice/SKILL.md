## 실행 순서

### 0. 범위 확정과 작업 브랜치 준비

- 목표·변경 범위·완료 조건·제외 범위·검증 방법을 정리한다. 현재 Git 루트, HEAD, 브랜치, staged/unstaged/untracked 변경, 원격, 기존 PR과 worktree를 확인한다.
- 이번 릴리스 변경과 관련 없는 작업을 구분한다. 기존 적절한 작업 브랜치·PR을 재사용하고, 없으면 개선 전에 `codex/` 작업 브랜치를 만든다. main에 직접 릴리스 변경을 커밋하지 않는다.
- dirty 파일을 일괄 stash/reset/삭제하지 않는다. 대상이 겹치지 않으면 분리해 진행하고, 사용자 변경과 충돌하여 안전하게 분리할 수 없을 때만 해당 범위를 확인한다. 기존 미커밋 변경도 이번 릴리스 대상으로 확인되면 보존하여 포함한다.
- 로컬 자료·실행 중인 개발 서버·Sites 사본을 보존한다. 새 worktree가 필요하면 프로젝트 하위에 두고 로컬 검사 자산 준비는 검사 문서를 따른다.

### 1. 변경 검토와 필요한 개선

- 이번 변경과 영향받는 경로의 기능·저장 호환성·구조·문서·코드 품질을 확인한다. 저장 관련 변경은 기존 DB/키/직렬화/패키지의 재읽기와 왕복 호환성 검사를 확인한다.
- 신규·이동 파일/폴더는 위치·명명·책임 분리·공통 모듈 재사용·의존 방향·진입점·참조 문서·검사 대상 포함 여부를 점검한다. 두 앱 공통 변경은 두 앱의 사용 경로를 확인한다.
- 객관적으로 판정 가능하고 반복 가치가 있는 기준은 기존 공통 검사에 추가하고 CI에서 재사용한다. UI 판단이나 설계 선호를 기계적인 실패 조건으로 바꾸지 않는다.
- 이번 변경에 필요한 개선을 반영한다. 무관한 정리·전체 구조 개편·새 사용자 기능은 별도 작업으로 남긴다. 구현과 달라진 정본 문서는 함께 갱신한다.

### 2. 버전과 변경 기록

- 버전 정책에 따라 두 앱의 공통 버전과 변경 기록을 갱신하고 증가 단계의 이유를 적는다. `package.json`을 앱 표시 버전으로 사용하지 않는다.
- 재개 작업에서는 이미 반영한 버전을 확인하여 중복 인상하지 않는다. 문서만 바뀐 경우 앱 버전·발행 필요성은 정책에 따라 판단한다.
- 소스 빌드번호를 갱신하고 이후 검증과 빌드가 같은 소스를 대상으로 하는지 확인한다.

### 3. 로컬 검증

- 검사 문서의 공통 명령을 사용한다. 현재 전체 로컬 명령은 `pnpm run verify`이며 lint·서식·타입·문서/구조·전체 테스트·두 앱 빌드를 포함한다.
- CI의 `verify:portable`은 원본 미디어가 필요한 회귀 검사와 두 앱 빌드를 대체하지 않는다. 자산 누락을 skip으로 바꾸거나 테스트 개수를 고정 성공 기준으로 사용하지 않는다.
- UI 변경은 승인된 로컬 앱·자료 범위에서 프로젝트 지정 브라우저로 화면과 관련 조작을 확인한다. 실제 검증 환경을 기록하고 화면 크기 모사를 iPad 실기기 검증으로 보고하지 않는다.
- iOS·iPadOS 실기기·시뮬레이터 검증은 릴리스 범위에서 제외한다. 사용자가 해당 검증을 별도로 명시한 경우에만 [기기 검증 절차](../../../docs/how-to/verify-ipad.md#ipad-simulator--ipad-mini-검증-실행-절차)를 수행한다. 일반 릴리스 요청만으로 실행하지 않으며, 미수행을 릴리스 차단 사유나 필수 잔여 작업으로 취급하지 않는다.
- 현재 시험 승인 범위를 적용한다. 합성 자료·신규 DB·운영 쓰기 시험을 릴리스 검증에 임의로 추가하지 않는다.

### 4. 작업 브랜치 커밋·푸시

- 최종 diff와 stage 목록을 검토하고 이번 변경만 커밋·푸시한다. 원본 미디어·생성물·비밀정보·관련 없는 작업은 포함하지 않는다.
- 커밋 SHA와 push 결과를 확인한다. 일반 push가 실패하면 원인을 조사하며 force-push로 해결하지 않는다.

### 5. PR 검토와 CI

- main 대상의 기존 PR을 갱신하거나 새 PR을 만들고 현재 작업에 연결한다. 설명에는 최종 문제·변경 결과·검증·남은 한계를 적는다.
- 최종 PR diff를 검토한다. 기능 회귀·저장 호환성·공통 모듈/의존 경계의 중요한 지적을 해결하고 영향받는 검사를 다시 실행한다. 검토자·대상 SHA·결과를 구분하며 자체 검토를 독립 검토로 표현하지 않는다.
- 최신 PR head SHA의 CI와 저장소가 요구하는 검토 승인을 확인한다. 이전 SHA의 성공이나 CI 통과 자체를 코드 검토 완료로 대신하지 않는다. 검토·검사가 남으면 Draft 상태로 두고, 준비가 끝나면 요청 범위에서 ready로 전환한다.

### 6. main 병합과 결과 검증

- 검토한 head SHA가 바뀌지 않았는지 확인하고 저장소에서 허용하는 방식으로 merge한다. 보호 규칙·필수 승인을 우회하지 않는다.
- 실제 병합된 main SHA를 조회하고 그 커밋의 CI 결과를 확인한다. PR head와 merge commit은 다를 수 있다.
- 병합·충돌 해결·다른 변경 유입으로 검증 대상 코드가 달라졌으면 영향받는 로컬 검사와 필요한 전체 검사를 다시 실행한다. 이전 결과를 재사용할 때는 코드·의존성·설정·검사 자산의 동일성 근거를 남긴다.

### 7. 검증된 main 빌드·발행

- 검증한 main SHA를 릴리스 후보로 고정한다. 그 코드와 준비된 자산으로 두 앱을 빌드하고 player만 발행 문서의 경로로 패키징한다. 생성 준비 후 실제 빌드번호와 산출물 일치를 확인한다.
- editor는 로컬 전용이다. 기존 Site의 ID·공개 범위를 유지하고 배포 사본의 별도 변경 유무를 확인한다. 사본에서 제품 코드를 독립 수정하지 않는다.
- 현재 Sites 스킬의 소스 동기화·인증·저장·배포 계약을 따른다. 정본 main SHA와 Sites 소스 SHA는 별개이므로 대응과 파일 해시를 기록한다. 미커밋 코드나 오래된 dist를 섞지 않는다.

### 8. 공개 확인과 결과 기록

- 배포 상태와 공개 읽기 smoke를 각각 확인한다. 발행 문서의 HTML·보안 헤더·JS/CSS/Worker·악보 다운로드·폐기 API 응답 기준을 사용하고, 공개된 파일이 이번 산출물과 일치하는지 확인한다.
- 이번 변경이 동작 확인을 필요로 하면 해당 흐름을 승인된 환경에서 확인한다. 정적 파일 일치를 실제 재생·청취·실기기 동작 성공으로 확대하지 않는다.
- 버전, PR, 구현/병합 SHA, CI, 소스 빌드번호, Sites 소스/버전/배포 ID, 산출물 해시, 공개 URL, 검사 결과와 미확인 범위를 변경 기록·발행 문서에 남긴다.
- 발행 후 결과 기록만 추가하는 문서 변경도 작업 브랜치·PR을 통해 반영한다. 제품 소스가 같으면 이 문서 변경만으로 버전을 다시 올리거나 재발행하지 않는다.

### 9. 병합된 작업 브랜치 정리

- 발행·공개 확인 후 이번 작업에서 병합된 로컬·원격 브랜치만 정리한다. squash/rebase merge는 PR의 실제 병합 상태와 포함된 변경을 확인하고 단순 ancestry 검사만으로 판단하지 않는다.
- 미병합 커밋·사용자 수정·사용 중인 worktree가 남아 있으면 해당 브랜치/작업 폴더를 보존하고 이유를 보고한다. 무관한 브랜치를 지우거나 main만 남기기 위한 일괄 삭제를 하지 않는다.
- 최종 main의 로컬/원격 일치와 작업 트리를 확인한다. 관련 없는 변경을 보존했다면 전체가 clean이라고 보고하지 않는다.

## 실패·중단·재개

실제 검사 실패는 원인을 해결하고 재검증한 뒤 해당 단계 이후로 진행한다. 기준을 끄거나 결과를 숨기지 않는다. 비차단 경고는 영향과 함께 기록한다. 검사 미실행·권한 부족·외부 장애는 통과와 구분하고, 차단되는 단계와 재개 지점을 남긴다.

결과가 불명확한 push·merge·버전 저장·발행은 원격 상태를 먼저 조회하여 중복 실행을 피한다. 재개 시 완료된 버전 인상·커밋·발행을 반복하지 않는다. 배포 후 문제가 확인되면 현재 상태와 수정 방안을 보고한다. 별도 승인 없는 rollback은 실행하지 않는다.

최종 보고에는 버전, 커밋/푸시/PR/merge/발행/공개 검사/브랜치 정리의 실제 결과와 남은 작업을 구분하고 공개 URL 및 근거 문서를 연결한다.
