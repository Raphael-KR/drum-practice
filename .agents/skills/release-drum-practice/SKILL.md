## 실행 순서

<a id="release-git-scope"></a>

### 0. 범위 확정과 작업 브랜치 준비

- 목표·변경 범위·완료 조건·제외 범위·검증 방법을 정리한다. 현재 Git 루트, HEAD, 전체 로컬·원격 브랜치, 기존 PR과 worktree를 확인하고 각 작업 트리의 staged/unstaged/untracked 변경을 목록으로 남긴다.
- 전체 릴리스는 작성 세션·작업 주제와 관계없이 이 프로젝트의 모든 미커밋 소스·설정·문서·테스트 변경을 포함한다. 기존 Git 추적 제외 원본·사용자 데이터·생성물·비밀정보를 새로 커밋하라는 뜻은 아니다. 명시적으로 제외된 변경과 아직 통합하지 못한 변경은 구분해 기록한다.
- 잔여 브랜치의 main 미반영 변경도 수집해 기존 적절한 작업 브랜치·PR로 통합한다. 필요하면 개선 전에 `codex/` 작업 브랜치를 만든다. main에 직접 릴리스 변경을 커밋하지 않는다. 단순 ancestry뿐 아니라 PR 병합 기록·실제 diff로 이미 반영된 변경을 구분한다.
- dirty 파일을 일괄 stash/reset/삭제하거나 일부 작업을 조용히 누락하지 않는다. 병행 작업은 변경 시점을 조율하고 충돌은 기존 의도를 보존해 해결한다. 진행 중인 수정과 충돌하여 통합할 수 없으면 해당 파일·브랜치를 보존하고 필요한 판단만 요청한다. 통합하지 못한 변경이 남으면 전체 통합·정리 완료로 보고하지 않는다.
- 로컬 자료·실행 중인 개발 서버·Sites 사본을 보존한다. 새 worktree가 필요하면 프로젝트 하위에 두고 로컬 검사 자산 준비는 검사 문서를 따른다.

### 1. 변경 검토와 코드·문서 정리

- 이번 변경과 영향받는 경로의 기능·저장 호환성·구조·문서·코드 품질을 확인한다. 저장 관련 변경은 기존 DB/키/직렬화/패키지의 재읽기와 왕복 호환성 검사를 확인한다.
- 신규·이동 파일/폴더는 위치·명명·책임 분리·공통 모듈 재사용·의존 방향·진입점·참조 문서·검사 대상 포함 여부를 점검한다. 두 앱 공통 변경은 두 앱의 사용 경로를 확인한다.
- 객관적으로 판정 가능하고 반복 가치가 있는 기준은 기존 공통 검사에 추가하고 CI에서 재사용한다. UI 판단이나 설계 선호를 기계적인 실패 조건으로 바꾸지 않는다.
- 릴리스 기준 커밋과 현재 변경을 비교하여 교체·삭제된 기능이 남긴 함수·상수·import·이벤트 연결·UI·CSS·테스트·문서 참조를 추적한다. 두 앱의 실제 진입점·호출 경로·동적 사용처와 CSS 적용 순서를 확인한다. lint 통과나 검색 결과만으로 기능 단위의 미사용 여부를 단정하지 않는다.
- 실제 사용처와 구체적인 호환성 보존 이유가 없는 코드를 제거하고, 중복 구현/CSS·임시 디버깅 코드·낡은 주석을 정리한다. 보존할 호환 코드는 지원하는 파일 형식·저장 키·읽기 경로 등 근거를 확인한다. 기존 기능·화면 배치·저장 호환성을 유지하고 필요한 공통 모듈을 재사용한다. 무관한 정리·전체 구조 개편·새 사용자 기능은 별도 작업으로 남긴다.
- 구현과 달라진 정본 문서·명령·링크를 갱신하고 중복 설명은 정본으로 연결한다. 기존 앵커와 과거 기록 원문은 보존하며 변경 이유와 현재 상태를 구분한다.
- 코드·문서 정리는 로컬 검증 전에 끝내고 정리한 diff까지 검증·커밋·PR 검토에 포함한다. 검증 후 추가 수정이 생기면 영향받는 검사를 다시 확인한다. 발행 후 작업 파일 정리 단계에서는 제품 코드를 변경하지 않는다.
- 제거·통합한 항목과 이유, 호환성 때문에 보존한 항목과 구체적인 근거, 미확인·보류 항목을 `history.md`와 릴리스 기록에 남긴다. 추가 정리가 필요 없으면 검토 범위와 그 결과를 기록한다.

#### 불필요·중복·과잉 검사 정리

- 코드 변경과 영향받는 경로의 테스트·정적 검사·CI를 함께 검토한다. [검사 정리 기준](../../../docs/reference/engineering/verification.md#verification-rules--검사-정리와-기준-변경)에 따라 목적·막는 위험·현재 적용 대상·중복 여부·실행 비용을 확인한다.
- 폐기된 기능만 검사하는 항목은 제거하고 중복 검사는 통합한다. 필요한 회귀검사는 현재 진입점·동작 기준으로 옮기고, 과도한 범위·실행 빈도·차단 조건은 실제 영향에 맞게 축소하거나 경고로 전환한다. 기존 기능·저장 호환성·보안·실제 회귀를 확인하는 검사는 근거를 확인해 유지한다. 실패 은폐나 실패 이력의 부재만을 이유로 제거하지 않는다.
- 기준 변경은 관련 문서·공통 검사·CI에 함께 반영하고 같은 diff로 검토·검증한다. 무관한 검사 체계 개편은 별도 작업으로 남긴다. 개정된 기준의 필수 검사를 최종 코드에 실행하며 미실행·실패를 통과로 보고하지 않는다.
- 삭제·통합·수정·축소한 검사와 이유, 유지한 검사의 근거, 남은 검증 공백과 실행 결과를 릴리스 기록·`history.md`·최종 보고에 남긴다. 필요한 검증이 남은 검사에서 어떻게 확인되는지도 기록한다.

### 2. 버전과 변경 기록

- 버전 정책에 따라 두 앱의 공통 버전과 변경 기록을 갱신하고 증가 단계의 이유를 적는다. `package.json`을 앱 표시 버전으로 사용하지 않는다.
- 재개 작업에서는 이미 반영한 버전을 확인하여 중복 인상하지 않는다. 문서만 바뀐 경우 앱 버전·발행 필요성은 정책에 따라 판단한다.
- 앱 변경이 있으면 소스 빌드번호를 갱신하고 이후 검증과 빌드가 같은 소스를 대상으로 하는지 확인한다. 문서·지침만 바뀌면 빌드번호를 갱신하지 않는다.

### 3. 로컬 검증

- 코드와 검사 정리 후 [카탈로그](../../../docs/reference/engineering/check-catalog.md)에서 공통 필수·변경 영향별 선택·해당 릴리스 단계 검사를 정한다. 목적·실행 조건·명령·환경·부수 효과와 현재 허가를 확인하고, 기존 릴리스 기록에 항목별 `실행/결과 재사용/비대상/보류`와 이유를 남긴다. 카탈로그 전체를 매번 실행하거나 고정 테스트 개수를 성공 기준으로 삼지 않는다.
- 코드 릴리스의 공통 자동검증은 `pnpm run verify`다. lint·서식·타입·문서/경계·전체 Vitest 회귀·두 앱 빌드를 유지한다. 문서·지침만 바뀐 후속 작업은 문서·링크·앵커·diff와 해당 스킬의 정적 검증만 수행하며 앱 생성·테스트·빌드·재발행을 하지 않는다. lint는 앞 단계의 실제 사용처 검토를 대체하지 않는다.
- 화면·재생·저장·SVG/악보·성능·보조 도구는 카탈로그의 조건에 해당하는 범위를 추가한다. 조건이 맞으면 해당 릴리스 범위의 필수 검사다. 공통 코드·저장/보안·의존성의 영향이 불명확하면 확대한다. 비대상과 허가/자료/환경 부족으로 인한 보류를 구분하며 필요한 검사가 보류되면 해당 단계는 미완료로 남긴다.
- [재사용 기준](../../../docs/reference/engineering/verification.md#verification-rules--결과-재사용)에 따라 같은 입력·환경의 성공과 근거를 재사용한다. `verify`가 이미 수행한 공통 검사·테스트·빌드를 별도 명령으로 반복하지 않는다. 바뀐 입력에 의존하는 검사만 다시 실행하되, 최종 후보의 필수 범위가 모두 확인되어야 한다. CI의 `verify:portable`로 로컬 미디어 회귀·두 앱 빌드를 대체하거나 자산 누락을 skip으로 처리하지 않는다.
- UI 변경은 승인된 로컬 앱·자료 범위에서 프로젝트 지정 브라우저로 관련 화면과 조작을 확인한다. editor는 PC, player는 영향받는 보기/화면만 선택한다. 실제 환경을 기록하고 화면 크기 모사를 iPad 실기기 검증으로 보고하지 않는다.
- iOS·iPadOS 실기기·시뮬레이터 검증은 일반 릴리스에 포함하지 않는다. 사용자가 별도로 명시한 경우에만 [기기 검증 절차](../../../docs/how-to/verify-ipad.md#ipad-simulator--ipad-mini-검증-실행-절차)를 수행한다. 별도 요청 없는 미수행을 릴리스 차단 사유로 취급하지 않는다.
- 현재 시험 승인 범위를 적용한다. 합성 자료·신규 DB·운영 쓰기 시험과 실계정 QA를 임의로 추가하지 않는다. 사용자가 정적 검사만 지시했으면 동적 검증과 릴리스는 보류하고 수행 결과를 구분한다.

### 4. 작업 브랜치 커밋·푸시

- 최종 diff와 stage 목록을 시작 시 수집한 전체 변경 목록과 대조하고, 위 범위의 미커밋 변경을 모두 커밋·푸시한다. 주제별로 커밋·PR을 나눌 수 있지만 다른 세션의 작업이라는 이유만으로 누락하지 않는다. 검증 중 추가된 수정도 포함하고 Git 추적 제외·비밀정보 경계는 유지한다.
- 커밋 SHA와 push 결과를 확인한다. 일반 push가 실패하면 원인을 조사하며 force-push로 해결하지 않는다.

### 5. PR 검토와 CI

- main 대상의 기존 PR을 갱신하거나 새 PR을 만들고 현재 작업에 연결한다. 설명에는 최종 문제·변경 결과·검증·남은 한계를 적는다.
- 최종 PR diff를 검토한다. 기능 회귀·저장 호환성·공통 모듈/의존 경계의 중요한 지적을 해결하고 영향받는 검사를 다시 실행한다. 검토자·대상 SHA·결과를 구분하며 자체 검토를 독립 검토로 표현하지 않는다.
- 최신 PR head SHA의 CI와 저장소가 요구하는 검토 승인을 확인한다. 이전 SHA의 성공이나 CI 통과 자체를 코드 검토 완료로 대신하지 않는다. 검토·검사가 남으면 Draft 상태로 두고, 준비가 끝나면 요청 범위에서 ready로 전환한다.

### 6. main 병합과 결과 검증

- 검토한 head SHA가 바뀌지 않았는지 확인하고 전체 변경을 담은 각 PR을 저장소에서 허용하는 방식으로 merge한다. 보호 규칙·필수 승인을 우회하지 않는다.
- 실제 병합된 main SHA를 조회하고 그 커밋의 CI 결과를 확인한다. PR head와 merge commit은 다를 수 있다.
- 병합·충돌 해결·다른 변경 유입으로 검사 입력이 달라졌으면 영향받는 로컬 검사와 필요한 전체 검사를 다시 실행한다. [재사용 기준](../../../docs/reference/engineering/verification.md#verification-rules--결과-재사용)의 코드·의존성·설정·검사 자산·실행 환경이 같으면 통과한 정적 검사·테스트 결과를 재사용하고 동일성 근거와 기존 결과를 연결한다. 커밋 SHA가 달라졌다는 이유만으로 같은 검사를 반복하지 않으며 재사용을 신규 실행으로 보고하지 않는다.

### 7. 검증된 main 빌드·발행

- 로컬 main을 GitHub 원격 main과 같은 커밋으로 맞추고 검증한 main SHA를 릴리스 후보로 고정한다. 그 코드와 준비된 자산으로 두 앱을 새로 빌드하되, 앞 단계에서 재사용이 확인된 정적 검사·테스트를 빌드 명령에 묶어 반복하지 않는다. [발행 절차](../../../docs/how-to/release.md#sites-publication--발행-순서)의 생성 준비와 번들 명령을 사용하고 실제 빌드번호와 산출물 일치를 확인한다.
- 배포 사본을 준비·교체하기 전에 현재 Sites 스킬·도구 계약을 읽고 기존 Site의 소스 저장소를 열어 상태를 확인한다. 기존 ID·공개 범위를 유지하고 반환된 checkout 경로와 별도 변경 유무를 확인한 뒤 그 경로에 player 배포 파일을 준비한다. editor는 로컬 전용이며 사본에서 제품 코드를 독립 수정하지 않는다.
- main 병합·검증 후 배포 사본 준비·Sites 빌드·자산 일치 확인을 마치고, 소스 push·버전 저장·발행을 진행한다. 기존 소스 저장소를 먼저 여는 단계와 준비한 소스를 나중에 push하는 단계를 구분한다. Sites helper에는 입력이 같고 이미 통과한 검사·빌드를 제외한 남은 명령만 전달한다. 필수 main 빌드·Sites 빌드/패키징·공개 확인은 유지한다.
- 정본 main SHA와 Sites 소스 SHA는 별개이므로 대응과 파일 해시를 기록한다. 사이트 일치는 Git SHA를 억지로 같게 만드는 것이 아니라 검증된 main의 제품 소스·빌드 입력과 공개 산출물의 일치로 확인한다. 미커밋 코드나 오래된 dist를 섞지 않는다.

### 8. 공개 확인과 결과 기록

- 배포 상태와 공개 읽기 smoke를 각각 확인한다. 발행 문서의 HTML·보안 헤더·JS/CSS/Worker·악보 다운로드·폐기 API 응답 기준을 사용하고, 공개된 파일이 이번 산출물과 일치하는지 확인한다. 이 확인에 로그인·계정 상태 변경·실계정 QA를 포함하지 않는다.
- 이번 변경이 동작 확인을 필요로 하면 해당 흐름을 승인된 환경에서 확인한다. 정적 파일 일치를 실제 재생·청취·실기기 동작 성공으로 확대하지 않는다.
- 버전, PR, 구현/병합 SHA, CI, 소스 빌드번호, Sites 소스/버전/배포 ID, 산출물 해시, 공개 URL, 검사 결과와 미확인 범위를 변경 기록·발행 문서에 남긴다.
- 발행 후 결과 문서는 다음 단계의 작업 파일 정리 결과까지 모아 작업 브랜치·PR을 통해 반영한다. 제품 소스가 같으면 이 문서 변경만으로 버전을 다시 올리거나 재발행하지 않는다.

### 9. 발행 후 작업 파일 정리

- 배포 성공과 공개 확인 후 프로젝트 안의 사용이 끝난 임시 파일·캐시·중복/구형 빌드·오래된 배포 아카이브를 찾는다. 삭제 전에 정확한 경로·용도·사용 여부·보존 대상을 구분하고 정리 범위를 알린다. 날짜나 Git 제외 여부만으로 삭제하지 않는다.
- 원본 악보·미디어·제작 자료·사용자 데이터/백업·최신 릴리스의 빌드와 배포 아카이브·검증 기록과 재현에 필요한 입력/스크립트·과거 기록은 보존한다. 실행 중인 서버가 참조하는 파일·현재 런타임/의존성·Sites 사본도 보존한다. 미통합 변경과 명시적 제외 작업은 파일 정리로 삭제하지 않고 위 통합 절차에서 처리한다. 프로젝트 밖의 공용 pnpm 저장소는 정리 대상이 아니다.
- 사용이 끝났음을 확인한 산출물 중 재생성 가능하거나 보존본과 중복인 것만 정리한다. 오래된 배포 아카이브는 최신 발행본 보존을 확인하고 실제 파일의 버전·해시를 기존 기록과 대조한 뒤 삭제하며, 기록에는 파일의 삭제 상태를 남긴다. 검증 자료와 임시 산출물이 섞인 폴더는 통째로 지우지 않는다. 용도·소유·참조가 불명확한 대상은 보존하고 이유를 보고한다.
- 삭제한 경로·이유·확보 공간과 주요 보존 대상, 보류 항목을 릴리스 기록과 `history.md`에 남긴다. 해당 결과는 앞 단계의 발행 결과 문서 PR에 함께 포함한다. 정리 대상이 없으면 그 결과를 기록한다.
- 정리 후 보존 파일의 존재·필요한 해시와 Git diff를 확인해 제품 소스·최신 발행 산출물에 변화가 없는지 확인한다. 파일 정리만으로 이미 통과한 전체 테스트나 발행을 반복하지 않는다.

### 10. main 일치와 전체 브랜치 정리

- 발행·공개 확인과 결과 문서 PR 병합 후 정본 저장소의 main 외 모든 로컬·GitHub 원격 브랜치를 정리한다. 이번에 만든 브랜치뿐 아니라 이전 잔여 브랜치도 포함한다. 각 브랜치의 고유 변경이 main에 반영됐는지 확인한 뒤 삭제한다. squash/rebase merge는 PR의 실제 병합 상태와 포함된 diff를 확인한다.
- 임시 worktree는 미커밋 변경이 없고 고유 변경이 main에 반영됐으며 사용이 끝난 것을 확인한 뒤 제거한다. 메인 작업 폴더와 별도 Sites 배포 사본은 유지한다. 새로 발견한 미반영 변경은 통합·검증 절차로 되돌려 처리하며, 삭제로 없애지 않는다. 충돌·진행 중인 작업·권한 제한 등으로 남은 브랜치는 이유와 함께 정리 미완료로 보고한다.
- 정리 후 원격 상태를 갱신해 로컬 main과 GitHub main의 SHA 일치, Git에 포함할 미커밋 변경 없음, 로컬·원격의 실제 브랜치가 main뿐임을 확인한다. `origin/HEAD` 같은 심볼릭 참조는 별도 브랜치로 세지 않는다. 사용자가 명시한 제외가 있으면 예외를 함께 기록하고 전체가 clean/main만 남았다고 표현하지 않는다.
- 공개 파일이 검증된 main 산출물과 일치하는지 최종 대조한다. 발행 후 결과 문서만 추가되어 최종 main SHA가 달라졌으면 빌드 기준 SHA와 최종 SHA를 모두 기록하고 제품 소스·설정·의존성·자산 입력이 같음을 확인한다. 문서만으로 재발행하지 않으며, 제품 입력이 달라졌다면 새 main 검증·빌드·발행·공개 확인까지 마친다.

## 실패·중단·재개

검사 실패는 원인을 조사하고 제품 결함과 낡거나 과도한 검사 기준을 구분한다. 기준 변경이 필요하면 위 검사 정리 절차에 따라 근거와 관련 문서·공통 검사·CI를 함께 반영한다. 실패를 숨기기 위한 규칙 해제·임의 생략·결과 조작은 하지 않는다. 개정된 기준의 필수 차단 검사는 원인을 해결하고 재검증한 뒤 다음 단계로 진행한다. 비차단 경고는 영향과 함께 기록한다. 검사 미실행·권한 부족·외부 장애는 통과와 구분하고, 차단되는 단계와 재개 지점을 남긴다.

결과가 불명확한 push·merge·버전 저장·발행은 원격 상태를 먼저 조회하여 중복 실행을 피한다. 재개 시 완료된 버전 인상·커밋·발행을 반복하지 않는다. 배포 후 문제가 확인되면 현재 상태와 수정 방안을 보고한다. 별도 승인 없는 rollback은 실행하지 않는다.

최종 보고에는 버전, 코드·문서 정리와 보존 이유, 검사 정리·유지 근거와 남은 검증 공백, 공통 필수·영향별 선택 검사의 실제 실행 결과와 재사용 근거·비대상 이유·보류, 전체 미커밋 변경의 반영 여부, 커밋/푸시/PR/merge/발행/공개 검사, 로컬·GitHub main SHA와 배포 내용의 일치, 작업 파일·전체 브랜치 정리의 실제 결과와 예외·보류 항목을 구분하고 공개 URL 및 근거 문서를 연결한다.
