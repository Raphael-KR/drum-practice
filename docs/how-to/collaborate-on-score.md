# 악보 제작·수정 공동 워크플로우

[공동작업 Rule](../reference/score/production.md#score-session-collaboration)을 실행하는 절차다. 사용자와 악보제작자는 곡별 프로젝트 하나를 함께 다루고, 악보제작기는 원본 비교·재생·가사 교정에 사용한다. 결정 이유는 [ADR-0035](../decisions/0035-score-session-collaboration.md), 파일 저장 전환의 구현 상태는 [구현 계획](../plans/score-editor-workflow-20261114.md)에 둔다.

이 문서는 작업 순서와 역할을 정의한다. PDF · MusicXML 동시 비교와 악보 아래의 상시 가사 작업대를 사용한다.

**구현 구분(2026-11-14):** 상시 작업대·가사 직접 조작·곡별 파일 저장·프로젝트 요청 경로를 구현했다. 이번 작업은 정적 검사까지만 수행하며 실제 사용자 자료 이관, 저장·재열기 왕복, 화면 조작과 Session Bridge 송신은 미검증이다. 아래는 구현된 계약에 따른 절차이며 실제 연결 성공 보고가 아니다.

<a id="shared-score-workflow"></a>

## 한 곡을 함께 완성하는 순서

| 단계 | 사용자 | 악보제작자 | 프로젝트에 남길 자료 |
| --- | --- | --- | --- |
| 1. 제작 시작 | 이 채팅에서 곡·원본·원하는 작업을 알린다. | 같은 곡의 기존 폴더를 찾거나 새 폴더를 준비한다. 원본과 적용할 결정을 확인한다. | 곡 식별 정보, 원본/참조 자료, 제작 목표 |
| 2. 첫 검수본 | 준비된 악보를 기다린다. | 변환·음표·주법·가사·음원 연결·조판을 처리한다. 원본 대조와 기본 검증을 먼저 한다. | 첫 MusicXML, 판독 근거, 검증 결과·미확정 사항 |
| 3. 사용자 검수 | **PDF · MusicXML 검수** 화면에서 두 악보를 동시에 보고 전체를 확인한다. 가사는 직접 편집하거나 이 채팅에서 수정을 지시한다. 다른 오류도 이 채팅에서 알려준다. | 지적을 해당 곡의 작업 사항으로 정리하고 판단 근거를 확인한다. | 미확정 편집, 검수 지적·처리 상태 |
| 4. 저장·작업 재개 | 직접 편집했다면 저장 후 요청 버튼이나 이 채팅으로 작업 재개를 알린다. 채팅 수정 지시는 별도 편집·저장 없이 전달한다. | 같은 프로젝트의 최신 파일·변경 이력과 채팅 지시를 읽는다. 저장된 변경 내용을 다시 작성하게 하지 않는다. | 확정 교정, 변경 전후·수정 시각, 작업 기준 저장본 |
| 5. 수정·재검증 | 같은 앱에서 수정 결과를 확인한다. | 채팅으로 지시한 가사 교정을 포함해 요청된 수정을 반영하고 확정 교정을 유지한다. 바뀐 부분과 영향 범위를 검증해 같은 프로젝트에 저장한다. | 새 MusicXML, 처리 내역, 검증 결과·남은 지적 |
| 6. 완성·인계 | 검수 결과를 확인하고 연습에 사용한다. | 완료 범위·남은 사항을 명시하고 요청된 완성 파일과 검증 근거를 앱 담당에게 인계한다. | 완성본, 검증 근거, 인계 상태 |

핵심 반복은 **첫 검수본 → 사용자 검수·직접 교정 또는 채팅 지시 → 제작자 반영·저장·재검증**이다. 사용자 확인이 더 필요하면 해당 부분을 다시 검수한다. 변경 없는 전곡 검수·질문·파일 전달을 반복하지 않는다.

## 처음 만드는 악보

1. [접수·보존과 원본별 제작](produce-score.md#score-production-process--악보-제작-프로세스)을 수행한다. 곡별 원본·판독 자료·정본·검수 근거를 같은 프로젝트에서 연결한다.
2. 제작자가 [완료 판정과 검증 근거](review-score.md#score-production-process--완료-판정과-필수-근거)를 확인한다. 검사하지 못한 부분을 구분한 뒤 첫 검수본을 준비한다.
3. 사용자가 PDF · MusicXML 비교 화면에서 전체 악보를 검수한다. 악기·리듬·주법·마디·가사 등의 지적을 프로젝트의 남은 작업으로 기록한다. 사용자의 검수는 제작자 자체 검증을 대신하지 않는다.
4. [검수 화면](../reference/product/editor.md#score-review--화면과-캡처)의 정지·캡처 기능을 필요할 때 사용한다.

## 가사 위치를 고쳐 이어서 작업하기

1. 사용자가 가사 편집 기능으로 필요한 위치를 옮기거나 이 채팅에서 수정을 지시한다.
2. 직접 편집은 초안과 확정 저장을 구분한다. 채팅 지시는 제작자가 최신 프로젝트에 반영하고 저장한다. 어느 경로든 확정 저장에는 변경 전후·수정 시각을 남긴다.
3. 직접 편집 후 요청 버튼을 사용하면 프로젝트를 확인하라는 알림과 식별 경로만 전달한다. 저장된 교정 내용을 다시 입력하거나 파일을 첨부하지 않는다. 채팅으로 지시할 때는 별도 앱 편집·저장을 요구하지 않는다.
4. 제작자는 마지막으로 확인한 저장본과 최신 저장본을 비교한다. 사용자 확정 교정·채팅 지시·남은 지적을 확인하고 [교정 재적용 절차](correct-lyrics.md#confirmed-lyric-corrections)를 사용한다. 화면 픽셀·실제 가창 시각으로 확정된 음악적 위치를 대체하지 않는다.
5. 사용자 교정이 이미 정본에 들어 있으면 다시 옮기지 않는다. 다른 제작 작업을 위해 재생성하더라도 확정 위치를 유지한다. 원본 재분석만으로 사용자의 교정을 되돌리지 않는다.
6. 변경한 범위와 관련 부분을 재검증한다. 같은 프로젝트의 최신 파일을 앱에서 읽어 확인하며 제작 결과의 수동 다운로드·재가져오기를 기본 흐름으로 두지 않는다.

## 같은 프로젝트 파일로 작업하기

1. 제작자는 [공통 프로젝트 CLI](../reference/score/tools.md#local-score-project-cli)로 기존 곡 ID를 조회한다. `read` 결과의 확정 `record`, 별도 `draft`, 최신 `head`, `work`를 구분한다. 처음 만드는 프로젝트만 `init`을 사용한다.
2. 기존 브라우저 자료는 앱의 첫 편집에서 전체 자료를 파일로 저장·재조회한다. 이미 파일 프로젝트가 있으면 그것을 연다. 브라우저 사본과 원본 파일은 삭제하지 않는다.
3. 가사 이동은 컨트롤바의 8·16·32·64분 격자와 악보 클릭·드래그·방향키를 사용한다. 작업대의 연속 선택은 M으로 병합하고, 보존된 구성 자료가 있는 묶음만 S로 분리한다. 입력칸의 글자 입력에는 단축키가 개입하지 않는다.
4. 제작자는 확인한 `head`를 `base`로, 확인한 초안 ID 또는 `null`을 `expectedDraft`로 지정해 `save`한다. 가사를 바꾸면 Song과 정본을 기존 공통 writer로 함께 준비하고 누적 교정 이력을 유지한다. CLI가 공통 차이 계산으로 제작자 변경 이력을 덧붙인다. 새 기준으로 재생성할 때는 확정 교정을 재적용한 뒤 저장한다.
5. 진행·질문·결과·실행하지 못한 검증은 `work`로 기록한다. 질문 답변은 같은 질문 ID로 한 번만 확정한다. 앱의 요청은 프로젝트 ID·경로만 전달하며, 일반 저장이나 새로고침이 제작 채팅을 호출하지 않는다.
6. 앱은 파일 알림과 수동 새로고침을 제공한다. 새 저장본이 생기면 가사·메타정보·마디 차이를 요약한다. 사용자 초안이 있으면 먼저 보존하며, 새 확정본을 열지 사용자가 선택한다. 저장 충돌은 최신 파일을 다시 읽고 해결한다.

파일별 책임과 보존 조건은 [로컬 제작 프로젝트 계약](../reference/score/file-formats.md#local-score-projects)에 둔다. 요청 `accepted`는 전달 접수다. 제작 완료와 사용자 검수 완료는 해당 결과·검증 기록으로 확인한다.

## 다른 오류와 작업 중단·재개

- 음표·주법·구조·조판 오류는 이 채팅의 지적을 읽어 제작자가 고친다. 사용자에게 범용 편집 기능으로 대신 수정하게 하지 않는다.
- 진행에는 현재 단계, 처리한 저장본, 해결한 지적, 남은 판단·검사를 기록한다. 사용자에게 필요한 선택만 짧게 묻는다. 파일 복사·명령 실행 등 제작자의 내부 작업을 질문으로 넘기지 않는다.
- 다시 시작할 때 같은 프로젝트의 최신 확정본·초안·진행 기록을 읽는다. 채팅 기억만으로 현재 파일을 추정하지 않는다.
- 제작자가 작업하는 동안 사용자가 새 교정을 저장했다면 두 변경을 확인한다. 확인한 이전 사본으로 최신 저장을 덮지 않고, 충돌하는 부분만 따로 판단한다. 같은 곡을 새 요청서로 다시 접수하지 않는다.
- 임시저장 또는 확정 저장이 실패하면 실제 상태를 알리고 작업 내용을 보존한다. 기록되지 않은 편집을 파일에 저장됐다고 보고하지 않는다.

## 완성 판단

사용자 검수 지적의 해결 여부와 제작자 검증 결과를 대조한다. 파일 생성·실제 표시·저장 후 재열기·청취는 각각 확인한 범위만 보고한다. 미확정 부분이 있으면 대상과 다음 조치를 남긴다.

완성 MusicXML과 요청 범위의 음원·`.drumscore`는 프로젝트에서 만든다. [개발 인계](produce-score.md#score-production-process--8-결과-인계와-제작-종료)는 재생 앱 수록을 위한 단계이며 사용자와 제작자가 공동 편집한 결과를 다시 가져오기 위한 단계가 아니다. 수록·공개 발행·Git 작업을 같은 완료 상태로 취급하지 않는다.

## 기존 요청 자료를 확인해야 할 때

아래는 이미 생성된 `data/production/requests/<UUID>/`의 기록을 처리하는 현행 CLI다. 새 워크플로우의 필수 접수 단계로 사용하지 않는다. [기존 파일 계약](../reference/score/file-formats.md#score-production-requests)과 [실행 기록](../plans/score-session-collaboration-20261113.md)을 함께 확인한다.

```sh
node tools/score-production/production_request.mjs list
node tools/score-production/production_request.mjs show --request "$REQUEST_ID" --request-sha256 "$REQUEST_SHA256"
```

- 실제 요청 값으로 입력·해시·진행 상태를 확인한다. 답장은 전달된 `--question-id`·`--answer-sha256`을 함께 대조한다. 완료된 요청은 다시 실행하지 않는다.
- `start`, `question`, `complete`, `fail`은 이 구형 요청의 진행 기록에 사용한다. `complete --result`의 JSON은 `summary`, `checks`, `artifacts`와 실제 결과 파일 경로를 담는다. 검증 상태는 `passed/not-run/failed`로 구분한다. 이 명령은 공유 프로젝트 저장 명령이 아니다.
- 기존 미반영 결과가 있으면 기준 정본·현재 편집을 대조한 후 현행 반영 경로로 처리한다. 기록과 원본을 삭제하지 않는다.
- Bridge의 `accepted`는 전달 접수이며 작업 완료가 아니다. 불확실한 전송을 중복 재전송하지 않는다. 연결 문제는 기존 5173 서버·프로젝트 설정·설치된 CLI의 실제 오류로 확인한다.
- 승인된 질문/답장 시험은 검증용임을 표시한다. Codex가 입력한 시험 답장을 사용자 결정으로 취급하거나 정상 제작에 시험 질문을 삽입하지 않는다.
