- 목표: 사용자 지정 폴더의 실제 음원으로 공개 서버 저장·재사용과 메타정보 품질을 검증한다.
- 범위: 해당 폴더의 MP3 16개, 공개 player 0.7.2/build b55c783faf01, 해시·태그·분석값 저장 API.
- 완료 조건: 모든 파일의 가져오기, 저장 후 재사용, 별도 클라이언트 조회, 전송 필드와 원본 보존을 확인한다.
- 제외: 앱 수정·커밋·발행, 원본 음원 서버 전송, 실제 iPhone/iPad Safari 동작·청취 검증.
- 검증: ego-browser의 파일 입력과 앱 화면 전환, fetch 관측, IndexedDB 결과 대조, 독립 HTTP 조회 및 기존 패키지의 동일 음원 해시 비교.

파일 입력 자동화가 Safari MCP에 없으므로 ego-browser를 사용했다. Apple STT/AFM은 해시·네트워크 계약 검증에 필요하지 않아 호출하지 않았다.

## 결과

**가져오기·서버 저장 경로는 동작하지만 안정화 통과로 판정하지 않는다.** 조회 시간 초과로 재분석이 발생하며 자동 곡 정보와 박자 추정의 정확도 문제가 있다.

- MP3 16개, 총 41회 가져오기 모두 파형·마디가 있는 연습 화면까지 진입했다.
- 1회차: 서버 miss/로컬 분석, 7개 PUT200, 나머지 9개 PUT 시간 초과. 다음 별도 조회에서 표본 2개가404여서 실제 미저장도 확인했다.
- 2회차: 7개 GET200으로 동일 값 재사용, 나머지 9개는 GET404 후 재분석/PUT200.
- 추가 회차(위9개): 3개 GET200, 나머지6개는 이미 저장됐는데도 GET 시간 초과 후 다시 분석했다. PUT도 시간 초과했다.
- 별도 Node HTTP 클라이언트는16개 모두 GET200, 브라우저가 저장한 태그/BPM/첫 박/길이와 정확히 일치했다. 기기 로컬 DB 없이 서버 조회가 가능함을 확인했다.
- 브라우저에서 실제 cache hit 관측은16개 중10개다. 나머지6개의 브라우저 재사용을 통과로 간주하지 않는다.
- API 송신은 허용된11개 메타정보 필드뿐이며 원본/파형/파일명/경로는 없다. 브라우저 보관 음원 크기가 원본과 일치하고, 원본16개의 시험 전후 SHA-256도 일치한다.
- Loveholic 재생 시작 후 진행률이1→2마디로 이동했다. 마지막 pointer 일시정지·목록 이동 자동화는 입력 반영을 확인하지 못했고, DOM click으로 일시정지→재생 버튼 전환을 확인한 뒤 페이지 이동으로 재생을 종료했다. 원인이 앱인지 자동화 환경인지는 미확정이며 pointer 정지 검증은 통과로 간주하지 않는다. 실제 소리·장시간 싱크 청취는 검증하지 않았다.

## 확인된 문제

1. **서버 조회·저장 안정성:** 현재 앱의1.5초 제한으로 첫 회차9개 저장 실패, 추가 회차6개 조회 실패가 관측됐다. 같은 시기의 독립 HTTP 조회는 성공했다. 브라우저/네트워크/서버 중 정확한 지연 원인은 아직 미확정이며 단순히 서버 장애라고 단정하지 않는다.
2. **곡명·가수:** 14개는 파일 태그가 없어 전체 파일명을 제목으로 쓰고 가수를 비워둔다. 2개의 태그 가수는‘웅키’다. 현 구현은 태그를 그대로 읽으므로 파일명에 나온 BIGBANG/I.O.I와 구별·보정하지 못한다. 서버 재사용이 곡 정보 정확성을 높이지 않는다.
3. **BPM·첫 박:** 패키지와 SHA-256이 같은‘바람과 언덕의 발라드’는 기존94BPM/첫 박0.388971초에 대해188BPM/0.02초로 분석했다. Loveholic은136BPM은 일치하지만 첫 박0.28초로 기존0.193초와0.087초 차이다. 다른14곡의 BPM 정답은 이번 시험에서 검증하지 않았다.
4. **박자표:** 현재 자동 분석은 BPM/위상을 추정하고 박자표는4/4를 고정한다. 곡별 박자표를 자동 인식하는 기능은 아니다. `firstBeat`도 첫 실제 타격을 찾아내는 검출이 아니라 주기 위상에 가깝다.

## 한계와 다음 작업

- 실제 iPhone/iPad Safari에서 파일 선택·다른 기기 간 시험은 수행하지 않았다. 공개 앱의 macOS Chromium과 별도 HTTP 클라이언트의 검사다.
- cache hit도 해시·디코딩·파형·로컬 저장·화면 준비가 남는다. 전체 가져오기 시간은 네트워크/브라우저 상태에 따라 변했고, 이번 결과로 속도 개선 배율을 보장하지 않는다.
- 공개 DB에는 이16개의 자동 분석값이 저장되어 있다. 오추정값도 재사용되므로 품질 개선 시 분석기 버전 변경/교정 정책을 함께 다뤄야 한다. 테스트라는 이유로 기존 공용값을 임의 덮어쓰거나 삭제하지 않았다.
- 다음 우선순위: 조회·저장 시간 초과 원인 확인 → 반·두배 BPM 및 첫 박 검증 강화 → 태그 없음/태그 가수 불일치 처리. 앱 수정·커밋·발행은 이번 시험에서 하지 않았다.
- 상세 로컬 증거: `.tmp/audio-folder-qa/{files,results,reference,independent-client,cleanup,playback}.json`. 원본 음원은 이 문서나Git에 포함하지 않는다.

## 수정 후 재검증 — 로컬 5173, 분석기 v2

위 공개 사이트 시험에서 확인한 문제를 수정한 뒤 같은 MP3 16개를 다시 가져왔다. 아래 결과는 수정된 로컬 앱의 결과다. 공개 사이트는 아직 분석기 v1이며 발행하지 않았다.

### 적용한 수정

- 조회 제한을 1.5초에서 4초, 저장 제한을 8초로 변경했다. 네트워크 실패와 HTTP 408/429/5xx 일부에만 250ms 뒤 한 번 재시도한다. 404·계약 오류는 재시도하지 않는다. 저장은 재생을 막지 않고 작은 JSON에 keepalive를 사용한다.
- 태그와 명확한 `가수 - 곡명` 파일명 구조를 해석한다. 가사/영상 접미사와 가수 뒤 앨범 표기를 정리한다. 업로더 가수 태그는 구조화된 태그 제목과 파일명의 곡명이 일치할 때 보정한다. 원본 파일명·경로는 보내지 않는다.
- player 전용 BPM 분석에 15초 구간별 주기 합산, 반·두배 후보 비교와 소수점 정밀화를 추가했다. 편집기 분석은 변경하지 않았다. 분석기/API를 v2로 바꿔 기존 오추정 캐시를 배제한다. v1 행은 보존한다.

### 관측 결과

- 실제 브라우저 가져오기 32회: 첫 회차 16개 GET404 → PUT200, 두 번째 회차 16개 모두 GET200. 두 번째에는 PUT·재분석이 없었다. 조회·저장 시간 초과 0건.
- 곡명·가수 16개 모두 자동 입력. 두 번째 가져오기에서 곡명·가수·BPM·첫 박·길이가 첫 저장값과 일치했다.
- 별도 Node 클라이언트도 16개 v2 결과를 조회해 첫 PUT JSON과 일치를 확인했다. 실제 iPad/iPhone 간 검증은 아니다.
- 첫 가져오기 중앙값 1,542ms, 두 번째 1,521ms. 디코딩·파형·로컬 저장이 남으므로 의미 있는 전체 속도 향상을 주장하지 않는다.
- 추가 오류 주입 3회: 2초 지연 조회는 GET200 한 번으로 완료, 첫 GET503은 재시도 GET200으로 복구, 첫 PUT 연결 오류는 재시도 PUT200으로 복구했다. 공개 서버의 실제 지연을 재현·해결했다고 단정하지 않는다.

### 정확도와 검증 범위

- 동일 해시 기준 악보가 94BPM인 ‘바람과 언덕의 발라드’는 188 → 94.1BPM, 첫 박 0.02 → 0.43초(기준 0.388971초). Loveholic은 136.4BPM(악보 136, 별도 음원 측정 약 136.232), 첫 박 0.22초(기준 0.193초)다.
