## 범위와 필수 경계

- 악보제작기는 PC(데스크톱·노트북) 화면만 개발·릴리스 검증 대상으로 삼는다. 휴대폰·태블릿 화면 검증은 드럼연습실에만 적용한다. 릴리스의 공통 코드 검사와 두 앱 빌드는 유지한다.
- 웹앱 개발 단계는 사용자의 결정에 따라 정적 검사만 수행하며, 구체적인 명령과 범위는 아래 [변경 영향과 검사 선택](#verification-rules--변경-영향과-검사-선택)에 따라 정한다. 화면 테스트는 릴리스 때 진행하며, 사용자가 별도로 검사 범위를 지시한 경우는 해당 요청을 따른다. 개발 중 보류한 테스트·빌드·화면 검수는 미확인으로 기록하고 릴리스의 필수 검증에서 확인한다.
- iOS·iPadOS 실기기·시뮬레이터 검증은 릴리스 범위에서 제외한다. 사용자가 해당 검증을 명시적으로 지시했을 때만 수행하며, 일반 릴리스 요청은 이 검증의 실행 지시가 아니다. 미수행을 릴리스 차단 사유나 필수 잔여 작업으로 취급하지 않는다. macOS Safari 응답형 디자인 모드의 화면 검수는 유지한다.
- 검사는 이 저장소의 `tests/{unit,integration,local-media}`를 사용한다. 다른 프로젝트·checkout·배포 사본은 포함하지 않는다. portable 성공을 local-media·두 앱 빌드 성공으로 대신하지 않는다.
- 실제 자산이 필요한 검사는 없으면 명시적으로 실패한다. 자료를 자동 다운로드·임의 생성·Git 업로드하거나 실패 검사를 삭제/skip하여 통과시키지 않는다.
- 재생 소유권·공통 UI·app/model/shared 경계·player 번들의 제작 코드 유입 차단을 유지한다. ESLint의 억제 baseline·일괄 규칙 해제로 기존 지적을 숨기지 않는다.
- DB 이름·스키마·키·bytes-v1·구형 Blob·snapshot·큐·원자적 저장, 전체 Song/정본/자산과 연습 정보의 보존을 변경 범위에 맞게 확인한다.
- 빌드·테스트가 같은 생성 파일을 쓰거나 읽으면 순차 실행한다. `pretest`·`generate`·build-info 생성의 쓰기를 단순 읽기 검사로 간주하지 않는다.

## 변경 영향과 검사 선택

[프로젝트 기본 규칙](../../../AGENTS.md#수정과-실행의-기본-규칙)에 따라, 변경 대상의 집중 검사를 먼저 선택하고 공통 기능·저장 호환성 등의 영향과 릴리스 필수 범위에 맞춰 확대한다. 명령 목록 전체를 모든 작업의 실행 순서로 사용하지 않는다.

| 변경 범위 | 우선 확인할 항목과 확대 조건 |
| --- | --- |
| 문서·지침만 변경 | 규칙 간 일관성·파일/문단 링크·앵커와 금지 범위의 보존을 확인한다. `pnpm run check:docs`와 `git diff --check`를 사용하며 앱·악보 재생성, 테스트·빌드는 실행하지 않는다. |
| 악보 정본·수록 패키지만 변경 | 변경 구간의 MusicXML 규격·프로젝트 표기 규칙·패키지 참조와 변경하지 않은 음악·자산·연습 정보의 보존을 확인한다. 변경된 입력에 의존하는 결과만 승인된 범위에서 재생성·재검증한다. |
| 앱·도구·설정 변경 | 영향받는 lint·서식·타입·정적 경계 검사를 먼저 선택한다. 공통 모듈·의존성·저장 계약 등에 영향이 있으면 관련 호출부와 호환성 검사까지 확대한다. 개발의 정적 검사 제한과 별도 시험 허가를 따른다. |
| 릴리스 | 릴리스 절차의 `pnpm run verify`·CI·두 앱 빌드와 해당 화면 검수·공개 확인 등 필수 범위를 수행한다. 집중 검사만으로 필수 단계를 대체하지 않는다. |

새 변경·실패·미해결 문제가 없으면 통과한 검사를 반복하지 않는다. 기존 결과를 재사용할 때는 검사에 영향을 주는 입력·코드·의존성·실행 환경이 그대로인지 확인하고 근거를 연결한다. 과거 PASS를 이번 실행으로 보고하지 않으며, 필수 검사의 실패·미실행을 통과나 불필요로 바꾸지 않는다.

<a id="verification-rules--환경과-판정"></a>

## 환경과 판정

검사 전에 [작업 전 조회와 실행 환경](../../how-to/develop.md#development--작업-전-조회와-실행-환경)에 따라 기록된 런타임·필수 의존성의 실제 경로와 사용 가능 여부를 확인하고 재사용한다. 시스템 기본 환경이나 과거 성공 기록만으로 현재 실행 가능하다고 추정하지 않는다.

코드 검사·원본 의미·규격·패키지 왕복·실제 앱 저장/재열기·화면·오디오 예약/출력·사람의 청취는 각각 구분한다. 해시·개수·XSD·렌더 경고 없음은 원본 의미나 모든 주법 지원을 보증하지 않는다. 독립 원본 기대값을 생성기 출력으로 대체하지 않는다.

웹앱 화면 검수는 기본적으로 Safari MCP가 연 창에서 Safari 응답형 디자인 모드를 사용한다. 같은 창의 기기·방향 설정은 Computer Use, 페이지 읽기·조작·캡처는 Safari MCP를 사용한다. 확인할 화면 크기와 기기·방향은 변경 영향과 요청에 맞게 선택한다. 상세 순서는 [응답형 화면 검수](../../how-to/verify-ipad.md#safari-responsive-mode)를 따른다. GUI와 시험은 현재 승인 범위 안에서 수행한다.

Safari MCP의 미지원 기능은 프로젝트 지침에 따라 적합한 도구를 사용하고, 지원 기능의 실패는 원인과 대체 근거를 남긴다. 비교만을 위한 동일 검사 중복은 하지 않는다. iPad는 [지정 환경](../../how-to/verify-ipad.md#ipad-simulator--ipad-mini-검증-실행-절차)의 Safari 응답형·시뮬레이터·실기기를 구분한다. Chromium viewport를 iPad Safari 검증으로 기록하지 않는다.

실제 재생은 사용자 버튼 조작 후 실제 플레이어 `AudioContext.state=running`과 위치 진행을 확인한다. 다른 인스턴스·합성 click·재생 아이콘만으로 앱 동작을 확정하지 않는다. 오디오 출력 신호·예약 시각은 사람이 들은 음질/싱크와 구분한다.

## 유지하는 번들·SQLite 경고

2026-11-09 사용자 결정: 아래 두 경고는 현재 상태로 유지하고 즉시 수정하지 않는다. 경고 출력과 기존 검사 기준을 유지하며, 필수 검사가 통과한 릴리스를 이 경고만으로 차단하지 않는다. 실제 검사 실패나 새 오류는 별도로 판정한다. 이 결정은 코드 수정·패키지 교체·추가 시험·발행 권한을 부여하지 않는다.

### 번들 크기

- 의미: `Some chunks are larger than 500 kB after minification`은 축소된 JavaScript 파일의 gzip 압축 전 크기가 Vite 기본 기준 500kB를 넘었다는 안내다. 다운로드·코드 해석/실행 비용을 점검할 신호이며, 500kB 자체를 성능 실패 기준으로 사용하지 않는다. [Vite 기준](https://vite.dev/config/build-options.html#build-chunksizewarninglimit).
- 유지 이유: MusicXML 렌더러는 이미 필요한 기능에서 동적으로 불러온다. [기존 로딩 실측](../../records/archive/runtime-loading-cost-20261109.md)에서 초기 목록에 렌더러를 요청하지 않음을 확인했고, 별도로 큰 비용이 확인된 [SVG 화면 준비 경로를 개선](../../records/archive/screen-preparation-20261109.md)했다. 추가 분할의 효과가 확인되지 않은 상태에서 파일 크기만 맞추려고 구조를 바꾸지 않는다. 경고 기준 상향·로그 억제로 개선을 대신하지 않는다.
- 다시 조사할 조건: 초기 목록·악보 열기의 지연이 같은 환경에서 반복되거나, 의존성/로딩 경로 변경으로 초기 JS가 늘거나 필요 없는 대형 모듈·중복 패키지가 포함될 때다. 이전과 같은 곡·보기·브라우저·CPU/네트워크·캐시 조건에서 다운로드, 모듈 해석/실행, 악보 화면 준비를 나누어 측정한다.
- 개선에 착수할 기준: 측정에서 해당 청크의 전송·해석/실행이 지연의 유의한 원인으로 확인되거나, 사용 전부터 불필요하게 읽는 코드·중복 포함이 확인될 때다. 원인에 맞는 지연 로딩·중복 제거·분할을 우선하며, 총 전송량과 실제 준비 시간의 전후 반복 측정으로 효과를 판단한다. 각 파일이 500kB 아래라는 사실만으로 개선 완료로 보지 않는다.
- 수치와 범위: 0.10.8 빌드의 player 본체는 711.46kB(gzip 194.70kB), player MusicXML 렌더러는 1,380.09kB(gzip 360.66kB), 로컬 전용 editor 본체는 834.27kB(gzip 225.59kB)였다. 이는 당시 산출물 크기이며 메모리 사용량·현재 공개망 전송량·iPhone 성능을 뜻하지 않는다. [릴리스 근거](../../records/archive/release-0.10.8.md).

### Node SQLite 실험 API

- 의미: `SQLite is an experimental feature and might change at any time`은 검사에 사용한 Node 22.22.2의 `node:sqlite` API 안정성 안내다. SQLite DB 손상이나 SQL 실행 실패를 알리는 메시지가 아니다. [Node 22 계열 API 설명](https://nodejs.org/download/release/latest-jod/docs/api/sqlite.html).
- 유지 이유: 현재 사용처는 [서버 분석 기능 폐기 회귀검사](../../../tests/integration/analysis-retirement.test.ts)의 메모리 DB다. 폐기 migration이 분석 테이블만 제거하고 무관한 자료를 보존하는지 확인한 뒤 DB를 닫는다. 브라우저 앱 실행 경로에는 포함되지 않으며, 0.10.8 전체 검사도 통과했다. 경고만 없애기 위한 라이브러리 교체·시험 삭제·경고 억제는 하지 않는다.
- 재검토·수정 기준: 정기 Node 업데이트에서 API 변경·제거로 이 검사가 실행되지 않거나 결과가 달라지는 경우, 해당 Node/SQLite 버전에 영향을 주는 보안·정확성 문제가 확인된 경우, 또는 `node:sqlite` 사용 범위를 테스트 밖으로 확대하려는 경우다. 지원 Node 버전과 실제 사용 API를 확인하고 필요한 수정만 수행한다. API가 안정화된 버전으로의 갱신도 기존 Node 지원 정책과 의존성 갱신 절차를 따른다.
- 수정 후 확인: 같은 migration의 분석 테이블 제거·무관한 데이터 보존·DB 종료를 다시 검증하고, 영향받는 타입 검사와 회귀검사를 수행한다. 경고 소멸만을 성공 조건으로 삼지 않는다. 시험 DB 생성 허가와 운영 데이터 보존 원칙은 그대로 적용한다.

향후 성능·호환성 검사는 [범위와 필수 경계](#verification-rules--범위와-필수-경계)를 따른다. iOS/iPadOS 실기기·시뮬레이터 검증은 사용자가 별도로 지시했을 때만 수행한다. 이번 결정은 상시 계측·새 CI 차단 기준을 추가하지 않으며, 위 조건이 확인된 작업에서 재검토한다.

<a id="verification-rules--결과-기록"></a>

## 결과 기록

입력/후보 해시·명령·버전·환경·대상·수행 행동·관측·실패·증거 경로·미확인과 다음 확인을 기록한다. 로컬 자료 `.tmp/`·`data/production/`의 존재는 다른 checkout에서 전제하지 않는다. 공개 HTTP·실기기·청취·원격 CI는 실제 확인한 경우만 완료로 쓴다. 과거 결과와 이번 재실행을 구분한다.
