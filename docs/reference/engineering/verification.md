## 범위와 필수 경계

- 악보제작기는 PC(데스크톱·노트북) 화면만 개발·릴리스 검증 대상으로 삼는다. 휴대폰·태블릿 화면 검증은 드럼연습실에만 적용한다. 릴리스의 공통 코드 검사와 두 앱 빌드는 유지한다.
- 웹앱 개발 단계는 사용자의 결정에 따라 정적 검사만 수행하며, 구체적인 명령과 범위는 아래 [변경 영향과 검사 선택](#verification-rules--변경-영향과-검사-선택)에 따라 정한다. 화면 테스트는 릴리스 때 변경 영향에 맞춰 진행하며, 사용자가 별도로 검사 범위를 지시한 경우는 해당 요청을 따른다. 개발 중 보류한 테스트·빌드·화면 검수는 미확인으로 기록하고 릴리스에서 필요한 범위를 확인한다.
- iOS·iPadOS 실기기·시뮬레이터 검증은 릴리스 범위에서 제외한다. 사용자가 해당 검증을 명시적으로 지시했을 때만 수행하며, 일반 릴리스 요청은 이 검증의 실행 지시가 아니다. 미수행을 릴리스 차단 사유나 필수 잔여 작업으로 취급하지 않는다. macOS Safari 응답형 디자인 모드의 화면 검수는 유지한다.
- 검사는 이 저장소의 `tests/{unit,integration,local-media}`를 사용한다. 다른 프로젝트·checkout·배포 사본은 포함하지 않는다. portable 성공을 local-media·두 앱 빌드 성공으로 대신하지 않는다.
- 실제 자산이 필요한 검사는 없으면 명시적으로 실패한다. 자료를 자동 다운로드·임의 생성·Git 업로드하거나 실패 검사를 삭제/skip하여 통과시키지 않는다.
- 재생 소유권·공통 UI·app/model/shared 경계·player 번들의 제작 코드 유입 차단을 유지한다. ESLint의 억제 baseline·일괄 규칙 해제로 기존 지적을 숨기지 않는다.
- DB 이름·스키마·키·bytes-v1·구형 Blob·snapshot·큐·원자적 저장, 전체 Song/정본/자산과 연습 정보의 보존을 변경 범위에 맞게 확인한다.
- 빌드·테스트가 같은 생성 파일을 쓰거나 읽으면 순차 실행한다. `pretest`·`generate`·build-info 생성의 쓰기를 단순 읽기 검사로 간주하지 않는다.

## 변경 영향과 검사 선택

[프로젝트 기본 규칙](../../../AGENTS.md#수정과-실행의-기본-규칙)에 따라 **공통 필수 검사 + 변경 영향별 선택 검사**를 적용한다. 검사별 목적·실행 조건·명령·환경·부수 효과·재사용 입력은 [검사 카탈로그](check-catalog.md)를 따른다. 개발에서는 변경 대상의 집중 정적 검사부터 시작하고, 코드 릴리스에서는 공통 자동검증을 유지하면서 화면·기능·성능·제작 도구 검사를 영향에 맞춰 추가한다. 카탈로그 전체를 매번 실행하지 않는다.

| 변경 범위 | 우선 확인할 항목과 확대 조건 |
| --- | --- |
| 문서·지침만 변경 | 규칙 간 일관성·파일/문단 링크·앵커와 금지 범위의 보존을 확인한다. `pnpm run check:docs`와 `git diff --check`, 스킬을 수정했으면 해당 정적 검증을 사용한다. 앱·악보 재생성, 테스트·빌드는 실행하지 않는다. 검사 명령/CI/실행 설정의 변경은 파일 확장자와 관계없이 아래 코드·설정 변경으로 판단한다. |
| 악보 정본·수록 패키지만 변경 | 변경 구간의 MusicXML 규격·프로젝트 표기 규칙·패키지 참조와 변경하지 않은 음악·자산·연습 정보의 보존을 확인한다. 변경된 입력에 의존하는 결과만 승인된 범위에서 재생성·재검증한다. |
| 앱·도구·설정 변경 | 영향받는 lint·서식·타입·정적 경계 검사를 먼저 선택한다. 공통 모듈·의존성·저장 계약 등에 영향이 있으면 관련 호출부와 호환성 검사까지 확대한다. 개발의 정적 검사 제한과 별도 시험 허가를 따른다. |
| 코드 릴리스 | `pnpm run verify`의 공통 정적 검사·전체 Vitest 회귀·두 앱 빌드를 필수로 유지한다. 변경 영향별 선택 검사의 조건을 대조해 해당 항목만 추가한다. PR/main CI·발행 후보 빌드·Sites 패키징/자산 일치·공개 읽기 확인은 해당 릴리스 단계에서 필요하며 로컬 검사로 대체하지 않는다. 문서만 변경한 후속 커밋은 위 문서 범위를 따른다. |

선택 검사는 임의로 생략 가능한 검사를 뜻하지 않는다. 조건이 맞으면 해당 범위의 필수 항목이며, 무관하면 이유와 함께 비대상으로 기록한다. 공통 모듈·저장/보안·의존성의 영향이 불명확하면 범위를 확대한다. 특정 작업에서 확인한 테스트 파일 수나 과거 화면 목록을 모든 릴리스의 고정 목록으로 삼지 않는다.

실행 전 공통 필수·영향별 선택·단계별 검사에서 `실행/결과 재사용/비대상/보류`와 이유를 정하고, 결과와 근거를 기존 작업·릴리스 기록에 남긴다. 보류는 통과가 아니며, 릴리스에 필요한 검사가 보류됐으면 해당 단계는 미완료다. iOS/iPadOS 실기기·시뮬레이터와 실계정 QA는 일반 릴리스에 포함하지 않는다. 공개 파일의 읽기 확인은 실계정 QA와 구분하고, 로그인·계정 상태 변경·외부 쓰기는 별도 요청 범위를 따른다.

<a id="verification-rules--결과-재사용"></a>

### 결과 재사용

- 새 변경·실패·미해결 문제가 없으면 통과한 검사를 반복하지 않는다. 이전 결과의 명령·검사 대상·환경·성공 로그와 실제 입력을 확인할 수 있어야 한다.
- 해당 검사가 읽는 제품/검사 코드와 전이 의존성, 설정·lockfile·patch·생성 입력, fixture·수록 자산, 실행 도구·버전·모드가 같아야 한다. Git SHA만 비교하지 않으며 미커밋 변경과 Git 제외 자산도 입력에 포함한다. 브라우저 검사는 origin·자료·초기 저장 상태·브라우저/화면 조건도 대조한다.
- 일부 입력이 달라졌으면 영향받는 검사를 다시 실행하고, 그대로인 범위만 기존 성공을 재사용한다. 영향 범위가 불명확하면 관련 묶음 또는 전체 검사를 실행한다. 최종 후보의 공통 필수 범위는 새 실행과 유효한 재사용 결과로 모두 확인돼야 한다.
- 같은 실행에서 `verify`가 수행한 검사나 빌드 전 검사를 별도 명령으로 반복하지 않는다. main 병합 시에도 입력이 같으면 로컬 정적/회귀 결과를 재사용한다. 해당 PR/main의 CI, 새 발행 후보 산출물·Sites 패키징·공개 배포 상태는 각 단계의 입력으로 확인한다. 상세 재개 조건은 [단계 검사](check-catalog.md#ci빌드발행-단계-검사)를 따른다.
- 실패·미실행·오래되어 입력을 확인할 수 없는 결과는 재사용하지 않는다. 검사 변경이나 실패 수정 후에는 영향을 받은 검사를 다시 확인한다. 재사용한 성공을 이번에 실행한 성공으로 보고하지 않는다.

## 검사 정리와 기준 변경

릴리스에서는 코드 변경과 영향받는 경로의 테스트·정적 검사·CI를 함께 검토한다. 검사별 목적·막는 위험·현재 적용 대상·중복 여부·실행 비용을 근거로 판단하며, 무관한 검사 체계 개편은 별도 작업으로 남긴다. 수행 순서는 [릴리스 스킬](../../../.agents/skills/release-drum-practice/SKILL.md#release-check-cleanup)을 따른다.

- 폐기된 기능만 검사하는 항목은 제거하고 같은 동작·위험을 중복 검사하는 항목은 통합한다. 서로 다른 실행 환경·저장 형식·실패 조건을 검증하면 같은 기능을 다룬다는 이유만으로 중복으로 보지 않는다.
- 내부 구현 방식에 과도하게 의존하는 검사는 현재 동작과 계약 기준으로 수정한다. 필요한 회귀검사는 현재 진입점으로 옮기며 실제 결함 재발을 확인하는 조건을 유지한다.
- 이미 제거된 함수명·DOM ID·번들 문자열의 부재만 검사하지 않는다. 현재 호출 소유권·화면 진입점·응답 계약을 검사한다. 현재 요소의 수명·보안 차단·지원 종료 API의 404처럼 의미가 있는 부정 검증은 유지한다.
- 화면 검사 대상은 지원 범위와 맞춘다. 폰·태블릿 레이아웃은 player 경로에서 검사하고, 두 앱의 공통 동작은 지원되는 PC 경로에서 확인한다. 생성 파일을 사용하지 않는 검사에는 준비 단계를 붙이지 않으며, 독립 실행에 필요한 준비와 같은 명령 안의 중복 준비를 구분한다.
- 수록 패키지·정본의 승인 버전 식별은 인계·릴리스의 입력 해시와 발행 자산 대조가 담당한다. 회귀검사에서는 음악적 의미·메타정보·source/정본 일치·저장 왕복을 확인하며, 정상적인 교정도 막는 파일 전체 해시 고정은 사용하지 않는다. 보존 원본·구형 호환 입력을 식별하는 해시는 별도 목적이 있으므로 유지한다.
- 과도한 검사 범위·실행 빈도·차단 조건은 실제 영향과 실행 비용에 맞게 축소하거나 경고로 전환한다. 차단 검사가 막는 구체적인 위험과 차단 범위를 확인하며, 경고 전환 시에도 결과와 영향을 기록한다.
- 기존 기능·저장 호환성·보안·실제 회귀를 확인하는 검사는 필요한 근거를 확인해 유지한다. 실패 은폐를 위한 삭제·skip·규칙 해제나 결과 조작은 금지한다. 실패 이력이 없다는 이유만으로 제거하지 않는다.
- 정상 소스의 정적 계약은 공통 `check`, 위반 탐지와 런타임 동작은 해당 테스트가 담당한다. 같은 정적 검사의 정상 통과를 테스트에서 반복하지 않는다. 계획 표의 고정 행 개수·ID 존재나 수동 검토용 중복 후보 보고서를 제품의 통과 조건으로 삼지 않는다. 현재 참조·앵커와 실제 소유권·의존 경계 검사는 유지한다.
- CI는 PR과 main push를 검사한다. 작업 브랜치의 push와 PR 이벤트에 같은 전체 검사를 중복 예약하지 않으며, 병합 예정 코드와 병합된 main의 검증은 구분하여 유지한다.
- 검사 기준 변경은 카탈로그·관련 문서·릴리스 스킬·공통 검사·CI의 실제 실행 조건을 함께 대조하고 필요한 곳을 갱신한다. 정리한 최종 코드에 개정된 기준의 필수 검사를 수행한다. 미실행·실패를 통과로 보고하지 않으며 시험 실행 허가와 사용자 지정 범위를 유지한다.

삭제·통합·수정·축소한 검사와 이유, 유지한 검사의 근거, 필요한 검증을 남은 검사가 담당하는 방식, 남은 검증 공백과 실행 결과를 릴리스 기록과 `history.md`에 남긴다. 과거 기록 원문은 보존하고 새 기준·결과를 구분한다. 최종 보고에도 정리 결과와 미확인 범위를 명시한다.

<a id="verification-rules--환경과-판정"></a>

## 환경과 판정

검사 전에 [작업 전 조회와 실행 환경](../../how-to/develop.md#development--작업-전-조회와-실행-환경)에 따라 기록된 런타임·필수 의존성의 실제 경로와 사용 가능 여부를 확인하고 재사용한다. 시스템 기본 환경이나 과거 성공 기록만으로 현재 실행 가능하다고 추정하지 않는다.

코드 검사·원본 의미·규격·패키지 왕복·실제 앱 저장/재열기·화면·오디오 예약/출력·사람의 청취는 각각 구분한다. 해시·개수·XSD·렌더 경고 없음은 원본 의미나 모든 주법 지원을 보증하지 않는다. 독립 원본 기대값을 생성기 출력으로 대체하지 않는다.

웹앱 화면 검수는 기본적으로 Safari MCP가 연 창에서 Safari 응답형 디자인 모드를 사용한다. 같은 창의 기기·방향 설정은 Computer Use, 페이지 읽기·조작·캡처는 Safari MCP를 사용한다. 확인할 화면 크기와 기기·방향은 변경 영향과 요청에 맞게 선택한다. 상세 순서는 [응답형 화면 검수](../../how-to/verify-ipad.md#safari-responsive-mode)를 따른다. GUI와 시험은 현재 승인 범위 안에서 수행한다.

Safari MCP의 미지원 기능은 프로젝트 지침에 따라 적합한 도구를 사용하고, 지원 기능의 실패는 원인과 대체 근거를 남긴다. 비교만을 위한 동일 검사 중복은 하지 않는다. iPad는 [지정 환경](../../how-to/verify-ipad.md#ipad-simulator--ipad-mini-검증-실행-절차)의 Safari 응답형·시뮬레이터·실기기를 구분한다. Chromium viewport를 iPad Safari 검증으로 기록하지 않는다.

실제 재생은 사용자 버튼 조작 후 실제 플레이어 `AudioContext.state=running`과 위치 진행을 확인한다. 다른 인스턴스·합성 click·재생 아이콘만으로 앱 동작을 확정하지 않는다. 오디오 출력 신호·예약 시각은 사람이 들은 음질/싱크와 구분한다.

## 번들 경고와 SQLite 검사 종료

2026-11-09에 보류한 경고 중 번들 크기 경고는 유지한다. 필수 검사가 통과한 릴리스를 이 경고만으로 차단하지 않으며 실제 검사 실패나 새 오류는 별도로 판정한다. SQLite 검사는 2026-11-11 사용자 결정에 따라 아래와 같이 종료했다. 과거 검증·릴리스 기록의 경고 내역은 당시 결과로 보존한다.

### 번들 크기

- 의미: `Some chunks are larger than 500 kB after minification`은 축소된 JavaScript 파일의 gzip 압축 전 크기가 Vite 기본 기준 500kB를 넘었다는 안내다. 다운로드·코드 해석/실행 비용을 점검할 신호이며, 500kB 자체를 성능 실패 기준으로 사용하지 않는다. [Vite 기준](https://vite.dev/config/build-options.html#build-chunksizewarninglimit).
- 유지 이유: MusicXML 렌더러는 이미 필요한 기능에서 동적으로 불러온다. [기존 로딩 실측](../../records/archive/runtime-loading-cost-20261109.md)에서 초기 목록에 렌더러를 요청하지 않음을 확인했고, 별도로 큰 비용이 확인된 [SVG 화면 준비 경로를 개선](../../records/archive/screen-preparation-20261109.md)했다. 추가 분할의 효과가 확인되지 않은 상태에서 파일 크기만 맞추려고 구조를 바꾸지 않는다. 경고 기준 상향·로그 억제로 개선을 대신하지 않는다.
- 다시 조사할 조건: 초기 목록·악보 열기의 지연이 같은 환경에서 반복되거나, 의존성/로딩 경로 변경으로 초기 JS가 늘거나 필요 없는 대형 모듈·중복 패키지가 포함될 때다. 이전과 같은 곡·보기·브라우저·CPU/네트워크·캐시 조건에서 다운로드, 모듈 해석/실행, 악보 화면 준비를 나누어 측정한다.
- 개선에 착수할 기준: 측정에서 해당 청크의 전송·해석/실행이 지연의 유의한 원인으로 확인되거나, 사용 전부터 불필요하게 읽는 코드·중복 포함이 확인될 때다. 원인에 맞는 지연 로딩·중복 제거·분할을 우선하며, 총 전송량과 실제 준비 시간의 전후 반복 측정으로 효과를 판단한다. 각 파일이 500kB 아래라는 사실만으로 개선 완료로 보지 않는다.
- 수치와 범위: 0.10.8 빌드의 player 본체는 711.46kB(gzip 194.70kB), player MusicXML 렌더러는 1,380.09kB(gzip 360.66kB), 로컬 전용 editor 본체는 834.27kB(gzip 225.59kB)였다. 이는 당시 산출물 크기이며 메모리 사용량·현재 공개망 전송량·iPhone 성능을 뜻하지 않는다. [릴리스 근거](../../records/archive/release-0.10.8.md).

### 과거 폐기 SQL 검사 종료

- D1·Drizzle과 마이그레이션 배포 지원이 종료됐고, 보관 SQL은 운영에서 재실행하지 않는다. 현재 실행·지원 경로가 없는 SQL을 매번 메모리 DB에 적용하던 `tests/integration/analysis-retirement.test.ts`를 제거했다.
- 이 변경으로 해당 검사의 `node:sqlite` 사용도 종료했다. 현재 브라우저 IndexedDB 저장·백업·복원, Worker 보안 헤더·폐기 API의 404 응답과 배포 자산 일치 검사는 유지한다.
- [과거 SQL·스냅샷·저널](../../records/archive/server-analysis-migrations/README.md)과 당시 검증·배포 기록은 보존한다. 향후 SQL 실행 지원을 다시 도입하면 실제 실행 대상과 데이터 보존 계약에 맞는 검증을 그 작업 범위에서 정한다.

향후 성능·호환성 검사는 [범위와 필수 경계](#verification-rules--범위와-필수-경계)를 따른다. iOS/iPadOS 실기기·시뮬레이터 검증은 사용자가 별도로 지시했을 때만 수행한다. 이번 결정은 상시 계측·새 CI 차단 기준을 추가하지 않으며, 위 조건이 확인된 작업에서 재검토한다.

## 결과 기록

입력/후보 해시·명령·버전·환경·대상·부수 효과/허가·수행 행동·관측·실패·증거 경로를 기록한다. 선택/비대상 이유, 재사용한 결과와 입력 대조 근거, 보류 사유·다음 확인을 구분한다. 로컬 자료 `.tmp/`·`data/production/`의 존재는 다른 checkout에서 전제하지 않는다. 공개 HTTP·실기기·청취·원격 CI는 실제 확인한 경우만 완료로 쓴다. 과거 결과와 이번 재실행을 구분한다.
