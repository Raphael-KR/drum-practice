# Apple 로컬 전처리 → 검토 워크플로우

## 역할과 완료 조건

Mac에서 Apple SpeechTranscriber가 음원과 시간 정보를 읽는다. Python이 사용자 가사와 대조하고, AFM 3가 짧은 문맥 기반 발음 비교 의견을 붙인다. Codex/사람은 원문·음원 범위와 각 의견을 검토한다. 최종 음절 정렬은 별도 작업이다.

성공 조건은 모든 지정 구간의 STT 결과, 검사된 시간 범위, AFM 결과/실패 기록, 원본을 보존한 검토 목록 생성이다. 후보 개수를 인식 오류 수로 해석하지 않는다. 이번 구현은 Mac 자료 준비용 CLI이며 웹앱/iPad HTML에서 AFM을 호출하지 않는다.

## 실행

프로젝트 루트 `/Users/raphael/Playground/drum-practice`에서 실행한다. 현재 Mac/Xcode의 Speech 및 FoundationModels SDK, 설치된 일본어 STT 자산과 사용 가능한 로컬 모델, ffmpeg, Python 3가 필요하다. 도구는 모델을 자동 다운로드하지 않는다.

```sh
npm run review:local -- \
  --audio public/demo/audio.mp3 \
  --manifest data/reference/apple-stt-manifest.json \
  --song public/demo/song.json \
  --out docs/experiments/apple-workflow-03
```

출력 경로는 존재하지 않는 새 디렉터리여야 한다. 기존 실행·소스·song.json을 덮어쓰지 않는다. 원본 가사 및 음원은 Git 제외 경로에 유지한다. 새 곡은 아래 형식의 manifest를 제공한다. `song`은 마디 번호 연결을 위한 선택 입력이다.

```json
{"locale":"ja_JP","segments":[
  {"id":"verse1","start":10,"end":25,"reference":"사용자가 제공한 해당 구간의 일본어 가사"}
]}
```

구간 경계·가사 자체의 정확성도 검토 대상이다. 인접 구간이 겹치면 같은 발음이 중복 인식될 수 있다. 누락된 원문 부분에는 시각을 만들어 넣지 않는다.

## 산출물과 검사

- `*-stt.json`: 원래 STT 텍스트·시각·인식 신뢰도.
- `report.json`: 전체 run 시각, 동일 텍스트 구간, 차이 후보, 주변 문맥, 마디 번호, AFM 의견, 원본/스크립트 해시, 실행 시간.
- `afm-input.json`, `afm-output.jsonl`: 짧은 비교 요청과 모델 이름·응답.
- `review.md`: 검토자가 읽을 목록. 별도 검토 결과는 `review-decisions.json` 등으로 기록한다.

시간의 유한성·순서·길이를 검사한다. AFM의 ID·분류 enum·누락·중복을 검사한다. AFM 실패 시 STT와 후보는 보존하고 실패를 명시한다. `sameReading`도 후보를 제거하지 않는다. AFM이 시각을 생성하는 계약은 없다. 한 STT run이 여러 발음을 포함해도 균등 분배하지 않는다. `confirmed`는 변경하지 않는다.

```sh
npm run test:local
```

## 이 곡의 실제 실행 및 후처리

2026-09-19, 사용자 가사 기준 11개 가창 구간을 실행했다. 첫 실행은 문맥 없는 AFM 비교, 두 번째는 주변 문맥을 추가한 비교다. 보컬 없는 전체 전주/간주 전사는 목적상 제외했다.

| 항목 | 두 번째 실행 |
|---|---:|
| 구간 수 | 11 |
| STT 호출 시간 합계 | 3.77초 |
| 검토 후보 | 69 |
| AFM 비교 | 47건 / 20.91초 |

| 비교 대상 외 후보 | 22 |

마지막 행은 출력 계약 검사이며 답의 정확도를 의미하지 않는다. 컴파일·오디오 변환은 위 시간에 포함하지 않았다. 원문에는 블로그 표기 오류 가능성이 있으며 영어 혼합, 구간 경계, 문장부호, 표기 차이가 후보에 포함된다.

Codex 후처리에서 `が似/かに`, `って/らせ`를 같은 발음으로 판단한 AFM 의견을 기각했다. `いま/今`와 일부 히라가나/한자 표기는 표기 차이 후보로 검토했다. 문맥 추가로 AFM의 정확성이 일반적으로 개선됐다고 주장하지 않는다. 모든 후보와 원문을 보존하므로 잘못된 의견이 가사나 시각을 바꾸지 않는다.

특히 48마디 `思` 시작이 이전 113–129초 시험에서는120.32초, 전체 2절 구간에서는121.52초로 반환됐다. 같은 음원에서 입력 문맥에 따라1.20초 차이가 발생했다. 따라서 해당 STT 값 하나로 기존 오/모 음절을 옮기지 않았다. `って`도 `らせ`로 인식됐으며 AFM이 이를 같다고 잘못 판단했다.

현 단계에서 STT는 빠른 검토 자료 생성에 유용하다. AFM 의견은 재검토가 필요한 보조 정보다. 실제 음절 위치 검증·전체 가사 싱크 보정은 미완료이며 앱의 기존 가사 시각은 유지한다. 검토 자료는 `docs/experiments/apple-workflow-02/`에 있다.

## 경계 오류 재검사 — 15마디 사례 반영

`boundaries.py`를 추가했다. 텍스트가 원문과 같더라도 별도로 시간 경계를 검사한다. 단일 문자 STT run이0.8초 이상이거나 사용자 청취 앵커와 연결되면 검토 대상으로 만든다.0.8초는 의심 후보를 찾는 휴리스틱이며 긴 음절을 오류로 확정하는 기준이 아니다.

각 후보는 기존 시작에서 조금씩 다른 두 지점으로 잘라 다시 전사한다. 이 절차는 실제 발음을 잘라낼 수도 있어 늦은 결과를 자동 채택하지 않는다. 동일 문자가 해당 시간범위에 정확히 하나 있고, 클립 시작에서0.12초 이상 떨어진 결과만 비교한다. 누락·중복·잘린 시작은 근거 부족으로 보존한다.

- 기존/재전사 시작의 차이가0.2초를 넘으면 `context_sensitive`.
- 유효 결과가 두 개이고 차이가 작으면 `stable_in_tested_windows`지만 정확성 확인은 아님.
- 다른 경우 `insufficient_evidence`.
- 모든 경계 후보는 `needsReview=true`, `autoApply=false`. AFM 판단이 이를 해제하지 않는다.

사용자 앵커는 manifest의 별도 `anchors` 배열로 제공한다. STT 출력과 합치거나 덮어쓰지 않는다. 매칭 못 한 앵커도 report의 unmatchedListeningAnchors에 남긴다.

```json
{"anchors":[{"id":"user-bar15-ko","segmentId":"part01","text":"こ","time":37.09022813444695,"reviewer":"user","source":"15마디 네 번째 팔분음표"}]}
```

검증: 전체11구간에서32개 경계 후보를 두 번씩 재검사했다.24개는 문맥에 따라0.2초 넘게 변했고8개는 근거 부족이었다. 추가 클립 생성·STT 호출 시간 합계10.61초. 이것은 오류32개가 확정됐다는 뜻이 아니다.

최종 코드로15마디를 별도 재실행한 결과, 기존こ36.12초에 대해37.090/37.101초를 얻고 context_sensitive로 분류했다. 사용자 앵커37.090228초와의 계산상 차이는 약-0.0002/+0.0108초다. 타임스탬프의 실제 정밀도나 모든 음절의 정확도가 이만큼이라는 뜻은 아니다. 후속 문구의 오인식도 원시 결과에 보존되어 있다.

집중 테스트13개(신규8개) 통과. 동일텍스트 경계누락,15마디 재현,클립 경계·중복·누락 처리,안정된 긴음절의 자동적용 금지,앵커 검증을 확인했다. 실제 결과는 docs/experiments/apple-workflow-boundaries-01 및 apple-workflow-bar15-regression에 보존한다. 기존 앱의 가사 시각은 이번 절차 변경으로 추가 수정하지 않았다.
