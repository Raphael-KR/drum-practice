## 1. 공유 분석정보의 오염 가능성

근거: `server/audio-analysis-api.ts:15–34`, `server/audio-analysis-store.ts:10–14`, `src/audio-practice.ts:124–149`.

PUT은 로그인이나 작성자 증명 없이 허용한다. Origin/Sec-Fetch-Site 검사는 다른 웹사이트의 브라우저 요청을 제한하지만 직접 HTTP 클라이언트의 인증 수단이 아니다. 서버는 해시 형식, JSON 구조, 숫자 범위를 검사하며 실제 음원 소유 여부나 분석 정확성은 확인하지 않는다.

클라이언트는 동일 해시의 서버 기록이 있고 음원 길이가 맞으며 박 배열이 유효하면 로컬 분석과 ID3 읽기를 생략한다. 따라서 아직 등록되지 않은 파일의 해시·길이를 아는 사람이 형식상 유효한 잘못된 제목·가수·BPM·박 배열을 먼저 등록할 수 있는 구조다. 박 배열이 없는 기존 기록도 배열이 있는 값으로 갱신할 수 있다.

**이미 박 배열이 있는 기존 기록은 덮어쓰기를 막는다.** 전체 데이터가 자유롭게 수정·삭제되는 API는 아니다. 다만 잘못된 값이 먼저 등록되면 이 보호 때문에 서버 값을 정상 분석으로 교정하는 것도 현재 공개 쓰기 경로에서는 어렵다.

권장: 공유 분석값을 검증된 정답으로 취급하지 않고, 기기 ID3 우선 적용·캐시 무시 재분석·오염 기록 격리/교정 경로를 제공한다. 작성 제어 또는 봇 방지·요청 제한을 함께 검토한다. 요청 제한만으로 분석 정확성을 보장할 수는 없다. 신뢰할 수 있는 분석 결과가 필요하면 작성 권한/검증 주체를 별도로 정해야 한다.

## 2. 공용 저장 한도와 처리량 남용

근거: `server/audio-analysis-api.ts`, `server/audio-analysis-store.ts:10–29`.

요청 본문 256KiB 제한과 전체 10,000행 제한은 있다. 하지만 앱 코드에는 요청자별 빈도 제한, 기록 만료, 오래된 기록 정리가 없다. 음원 증명 없이 새 해시를 등록할 수 있어 공용 한도를 채우는 남용이 가능하다. 조회 및 저장 요청도 DB 처리량을 소비한다.

예상 영향은 새로운 분석정보 저장 실패와 기기별 재분석 증가다. 캐시 오류 시 로컬 분석으로 돌아가므로 곧바로 모든 연습 기능이 중단되는 것은 아니다. 실제 비용·과금 영향과 플랫폼의 추가 차단 정책은 미확인이다.

권장: 플랫폼/공유 저장소 수준의 요청 제한, 봇 방지, 캐시 만료·정리, 사용량 경보를 도입한다. 한 Worker 인스턴스의 메모리 카운터만으로 전역 제한을 구현하지 않는다. [OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)도 요청 빈도·자원 상한과 공급자 사용 한도 관리를 권고한다.

## 3. 공개 응답의 보안 헤더

홈 및 JS 응답에서 Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy가 없었다. API에는 `X-Content-Type-Options: nosniff`와 `Cache-Control: no-store`가 있었다. 어느 응답에서도 Access-Control-Allow-Origin은 관측되지 않았다.

현재 스크립트 삽입 취약점이 발견됐다는 뜻은 아니다. CSP와 프레임 삽입 방지는 추가 방어다. 프레임에 앱을 넣어 버튼 클릭을 유도할 가능성은 있지만 실제 브라우저에서 재현하지 않았다. Referrer-Policy가 없어도 최신 브라우저 기본 정책은 적용되므로 이를 전체 URL 유출로 단정하지 않는다.

HTTPS 응답은 확인했다. Strict-Transport-Security는 응답에 없었지만 상위 도메인의 정책·preload 여부는 확인하지 않았으므로 다운그레이드 공격 가능성을 확정하지 않는다.

권장: HTML에 CSP의 `frame-ancestors` 등과 호환되는 프레임 방지 정책, 정적 응답의 nosniff, 명시적 referrer 정책을 추가한다. CSP는 앱의 blob 음원·Worker·SVG와 플랫폼이 삽입하는 Cloudflare 스크립트를 고려해 보고 전용 정책부터 검증한다. [OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html) 참고.

## 4. 큰 음원 파일의 기기 메모리 위험

근거: `src/audio-practice.ts:120–128`.

빈 파일만 걸러낸 뒤 전체 파일을 arrayBuffer로 읽고 오디오를 디코딩한다. 분석 대상 시간 제한은 디코딩 후에 적용되므로 큰 파일의 메모리 사용을 예방하지 못한다. 사용자가 직접 파일을 선택해야 하는 경로이므로 서버 원격 실행 문제와 구분한다.

권장: 전체 읽기 전에 파일 크기 상한, 가능한 경우 길이 사전 확인, 지원 범위를 넘는 파일의 명확한 오류 안내를 추가한다. 특히 모바일에서 허용할 최대 용량/길이를 실제 기기 검증으로 정해야 한다.

## 확인한 보호 장치와 데이터 범위

- API의 허용 필드·해시·숫자 범위·박 배열 개수 검사와 실제 스트림 바이트 제한이 있다. Content-Length만 믿지 않는다.
- SQL은 prepared statement와 bind를 사용한다. 검토한 API에서 사용자 입력을 SQL 문자열에 연결하는 경로는 없었다.
- 목록의 곡명·가수는 HTML escape를 거치고 오류 안내는 textContent를 사용한다.
- MusicXML 크기 제한, ENTITY 거부 및 실행성 요소/이벤트 속성 제거가 있다. 재생 SVG도 script·foreignObject·이벤트·외부 참조 등을 거르고, 전체 악보는 img로 표시한다.
- .drumscore는 경로·중복 항목·항목 수·압축 해제 크기를 검사한다. 실제 해제 바이트가 선언된 상한을 넘으면 중단한다.
- 공개 Worker는 분석 JSON과 정적 파일을 다룬다. 검토한 API에 사용자 지정 외부 URL을 서버가 대신 요청하는 기능은 없다.
- **음원 원본은 기기에 유지된다.** 서버의 곡명·가수는 ID3 또는 구조화된 파일명에서 추출될 수 있다. 개인 녹음에 사람 이름 등이 들어 있다면 그 메타정보까지 개인정보가 아니라고 보장할 수는 없다. 원본 파일 경로·일반 파일명 전체를 그대로 서버에 보내는 구조는 아니다.
- 분석정보 조회는 공개 공유 캐시의 의도된 동작이다. 같은 파일이나 해시를 아는 사람이 해당 메타정보를 조회할 수 있다. 사용자별 청취 이력/계정 조회나 전체 목록 API는 검토한 코드에 없었다.
