# 확정 가사 교정의 기록과 재제작 반영

상태: 프로세스 합의·앱/제작 도구 구현·정적 검사 완료. 실제 저장→전달→재제작 동작 검사는 미실행이다. 현행 Rule은 [확정 교정 저장 계약](../reference/score/file-formats.md#confirmed-lyric-corrections)을 따른다.

- 목표: 악보제작기에서 저장 확정한 가사 위치가 재제작 후에도 유지되게 한다.
- 범위: 확정 수정 이력, 제작 자료 전달, 공통 재적용 코드, 제작 절차·앱 저장 경로.
- 완료 조건: 저장 전후 위치와 확정 시각을 보존하고, 재제작 입력에 교정을 연결하며, 전달·반영 상태를 구분한다.
- 제외: 커밋·push·공개 배포, 기존 사용자 곡의 무단 일괄 교체, 가창 시각 분석, 별도 상시 감시 서비스.
- 검증: 변경 범위의 서식·lint·타입·정적 경계 검사. 실제 저장·전달·재제작 기능 검사는 현행 검사 허가와 릴리스 범위에 따라 구분해 기록한다.

## 합의한 공통 처리

1. 직전 확정 상태와 저장할 최종 상태의 의미를 비교한다. 가사 ID·문구·마디 ID·사분음표 기준 시작/길이를 기록하며 재생 초·SVG 좌표를 교정 정본으로 사용하지 않는다.
2. 초안·취소·변경 없는 저장은 확정 이력을 만들지 않는다. 악보와 이력을 같은 영속 저장 단위로 취급하고 전달 실패가 저장된 악보를 되돌리지 않게 한다.
3. 재제작은 기존 공통 가사 처리 뒤 확정된 수동 교정을 적용하고 정본을 쓴다. 확정 묶음을 다시 자동 병합하여 사용자의 위치를 바꾸지 않는다.
4. 같은 교정의 재접수·재적용은 중복 변경을 만들지 않는다. 다른 판본·없어진 ID·변경된 문구/구조로 대상이 달라지면 해당 항목을 충돌로 기록하고 독립적인 항목은 계속 처리한다.
5. `저장됨`, `프로젝트 접수됨`, `개발자 전달됨`, `앱 반영됨`을 별도 증거로 관리한다. 파일 수신을 채팅 전달이나 앱 수록으로 보고하지 않는다.

## 연결 경로의 확인 사항

- 기존 `common/evidence.py`는 일회성 제작 산출물 수신기다. 확정 교정 목록·중복 접수·상태 조회는 현재 계약에 없다.
- 작업 시작 당시 Vite는 `/api/`를 404로 처리했다. 이번 구현은 로컬 제작용 플러그인에서 아래 접수 경로만 먼저 처리하며 공개 player 배포와 분리한다.
- 세션 연결 스킬에서 Codex 내장 전달 도구와 외부 앱 런타임의 호출 가능 범위를 구분한다. 자동 채팅 알림은 실제 지원·설정 확인 없이 구현 완료로 표시하지 않는다.

## 합의된 형식과 경로

- 공통 교정 타입과 diff/적용 함수는 앱의 `src/model/lyric-correction.ts`, `src/modules/lyrics/lyric-corrections.ts`에 둔다. 제작 도구는 이 함수를 가져온다.
- 교정 기록은 `id`, `songId`, `savedAt`, `source: editor`, 변경 전후 정본 SHA256, 가사 변경 목록으로 구성한다. 각 항목은 이전/새 가사의 ID·문구·확인 상태·음악적 위치를 보존한다. 추가/삭제는 한쪽 상태가 없는 것으로 구분한다.
- `RecordData.lyricCorrections`는 이전 버전 스냅샷과 별도로 저장하고 제작 전체 백업에 포함한다. MusicXML과 완성 재생 패키지에는 넣지 않는다.
- 개발 서버 5173의 제작 전용 접수 경로는 `POST /api/lyric-corrections`다. 공개 player 서버의 폐기 API와 구분한다.
- 프로젝트 보존 경로는 `data/production/lyric-corrections/<encodeURIComponent(songId)>/latest.json`이다. 봉투에 형식/버전·곡 ID·최신 정본·해시·전체 교정 이력을 담는다. 이전 교정 ID를 보존하고 늦게 도착한 구판이 최신 정본을 덮지 않게 한다.
- 제작 브라우저 경로는 `prepareProductionCanonical`에서 자동 묶음 후 확정 교정을 적용한다. 현행 정본을 받는 CLI는 곡 ID와 같은 파일을 명시해 읽는다. 교정 없음과 읽기 실패·잘못된 자료를 구분한다.
- 공통 적용은 최신 값까지 반영된 입력에도 멱등적이어야 한다. A→B→C 이력에 C 입력이면 과거 A→B를 충돌로 다시 만들지 않는다. 가사 대상 변경은 문자열 유사도로 추정하지 않는다.
- 로컬 자료 접수는 자동화하되 앱에서 Codex 채팅을 호출하는 새 서비스는 만들지 않는다. 제작자가 접수한 교정을 반영·검수하고 기존 완성본 자동 인계 절차로 개발자에게 전달한다. 저장 직후 즉시 채팅 알림 기능으로 안내하지 않는다.

구체 함수 시그니처와 보고서 필드는 앱 구현 파일을 정본으로 하고, 문서에 별도 복제 스키마를 두지 않는다.

## 구현 연결과 완료 확인

- 앱: `prepareLyricCorrectionSave`가 직전 확정 상태와 최종 가사를 비교한다. `editor-session.ts`는 정본·이력·동결 봉투를 같은 저장 호출로 넘기고 실패 시 제작 이력 상태를 복원한다. 전달은 저장 성공 이후의 별도 작업이다.
- 연속 저장: 이전 전송 중 확정된 새 봉투는 전달 큐에 보관해 이어 보낸다. 접수증 갱신은 저장된 곡 전체를 다시 쓰지 않으므로 진행 중 초안을 확정 상태로 바꾸지 않는다.
- 같은 ID의 패키지 교체: 기존 교정의 최신 값이 입력 가사와 일치하는지 공통 함수로 확인한다. 과거 위치·분기 이력은 저장 전에 중단한다. 전체 백업 복원은 당시 상태를 복원하는 기존 의미를 유지한다.
- 제작: `common/lyric-correction-input.mjs`가 공통 검증·적용 API를 사용한다. `prepareProductionCanonical`의 브라우저 경로와 `group_canonical_lyrics.mjs`의 v2 전환 경로가 곡 ID로 접수 자료를 읽는다.
- 현행 정본 교정: `apply_lyric_corrections.mjs`는 새 출력 폴더에 원본·접수 봉투·선택적 ID 대응·변경 보고서와 결과를 보존한다. 정본의 최종 묶음은 다시 자동 병합하지 않는다. 공통 writer/reader로 변경한 가사를 재읽는다.
- 충돌: 공통 적용은 독립적으로 적용 가능한 항목을 처리한다. CLI는 충돌 후보와 보고서를 남기고 실패 상태를 반환한다. 브라우저 제작은 충돌 보고서가 있는 오류로 패키지 생성을 중단한다. 무시하거나 곡 전체를 추정 재배치하지 않는다.
- 구판 전환 검사기는 자동 묶음의 원음절 대응을 확인한 뒤 실제 적용 보고서의 전후 값을 XML과 대조한다. 적용 의미를 Python에 다시 구현하지 않는다.
- 제작 절차는 `docs/how-to/correct-lyrics.md`, 공통 API 안내는 `docs/reference/score/tools.md`, 다음 제작 진입점은 악보 제작 스킬에 연결했다.

### 기능 검사에 남긴 시나리오

릴리스 또는 별도 승인된 기능 검사에서 실제 보존 자료를 우선 사용한다. 새 합성 자료·시험 DB는 해당 허가 범위를 먼저 확인한다.

1. 위치 수정·확정 저장 후 이전/새 위치·시각·정본 해시와 프로젝트 접수를 대조한다. 초안·취소·변경 없는 저장은 새 교정을 만들지 않아야 한다.
2. 연속 두 번 저장, 전송 중 추가 저장, 전달 실패·재전달, 구판 재전달에서 최신 정본과 누적 이력을 유지하는지 확인한다.
3. 원본 재제작과 이미 교정된 정본 재적용을 비교한다. 동일 교정의 중복 이동이 없고, 대상이 달라진 항목은 후보·보고서에만 남아야 한다.
4. 같은 ID의 패키지 교체에서 기존 이력과 전달 상태가 유지되고 새 가사와 일치하는지 확인한다. 전체 백업 복원은 사용자가 선택한 백업 당시의 이력·봉투를 복원하는 기존 의미를 유지한다. 과거 백업에서 재전달해도 프로젝트의 더 최신 접수 파일은 후퇴하지 않으며 분기 이력은 조용히 덮지 않아야 한다.
5. 교정된 XML의 가사 위치·음가를 재읽고 드럼·지시·음원 연결 보존, 실제 SVG 표시, 완성본 인계와 앱 수록을 각각 확인한다.
