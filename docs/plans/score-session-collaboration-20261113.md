# 악보제작기와 담당 세션의 공동작업

2026-11-17 릴리스 준비: 아래는 당시 요청 모달의 구현·검증 기록이다. 현재 작업대는 [파일 프로젝트 흐름](../how-to/collaborate-on-score.md)을 사용하며, 호출되지 않는 브라우저 요청/결과 코드와 전달 재시도 UI는 제거했다. 기존 기록·서버·CLI는 보존한다.

이 문서는 초기 요청·결과 전달 방식의 구현과 검증 기록이다. 최신 제작·수정 흐름은 [공동작업 워크플로우](../how-to/collaborate-on-score.md#shared-score-workflow), 로컬 프로젝트 전환의 현재 상태는 [전환 계획](local-score-projects-20261113.md)을 따른다.

상태: 앱 `0.11.5`, 빌드 `f061fba8c59f`에서 로컬 요청 전송·진행·질문/답장·악보 미리보기·보고서·Finder 폴더 열기·결과 반영·새로고침 후 재열기를 확인했다. 후속 내보내기 제거는 미적용이다. 앱 개발 채팅에서 직접 대화창 방식을 논의 중이므로 기존 요청 화면의 추가 수정·재시험은 보류했다. 커밋·push·공개 배포는 수행하지 않았다.

## 로컬 결과 화면의 실제 왕복 재검증 — 2026-11-13

- 목표: 변경된 실제 앱에서 전송·진행·질문/답장·미리보기·결과 반영·재열기를 확인한다.
- 범위: 기존 5173 서버와 Safari MCP, 실제 수록곡 `갑자기`, 요청별 파일·세션 수신·앱 저장 기록. 결과의 가사 위치 검수와 패키지 재생성은 제작자가 수행한다.
- 완료 조건: 같은 요청·질문·답장·산출물·접수증을 연결하고, 미리보기는 저장하지 않으며 명시적 반영 뒤 재열기에도 결과가 유지된다. 수동 다운로드·재가져오기는 사용하지 않는다.

- 검증: 사용자가 실제 왕복을 다시 명시했으므로 이번 범위의 GUI·로컬 송신·결과 저장을 실행한다. 화면·파일 해시·공통 읽기 API·접수증을 대조하고 실패한 단계는 근거와 함께 교정한다.

사용자는 앞선 질문·답장에 파일을 그대로 반환하라는 내부 검증 지시가 등장한 점을 지적했다. 이는 사용자가 결정할 질문이 아니었다. 파일 처리·검증·결과 반환은 제작자가 맡으며, 정상 제작에서 질문 단계를 억지로 만들지 않는다. 이번 질문/답장 경로 시험은 검증용임을 본문과 결과에 명시하고 수행자 Codex가 입력한다. 별도 사람의 승인이나 미확정 음악 교정의 근거로 사용하지 않는다. 실행 근거는 `.tmp/production-result-local-e2e-20261113/`에 보존한다.

앱 담당은 후속 방향을 정리하는 동안 기존 요청 화면의 내보내기 제거와 추가 화면 시험을 보류했다. 현재 코드에는 접힌 내보내기가 남아 있고 직접 대화창 전환도 구현하지 않았다. 기존 미리보기·직접 반영·폴더 열기·보고서 보기와 위 실제 검증 결과는 유지한다. 이번 검증에는 수동 다운로드·재가져오기를 사용하지 않았다. 향후 화면 개편의 완료 근거로 이번 기록을 대신 사용하지 않는다.

## 로컬 결과 확인 흐름 — 2026-11-13

아래는 최초 로컬 UI 구현 당시의 기록이다. 실제 실행 결과와 후속 화면 논의·미적용 상태는 위 절을 따른다.

- 목표: 프로젝트에 이미 저장된 결과를 내려받아 다시 올리는 과정 없이 검토하고 반영한다.
- 범위: 결과 미리보기·악보에 반영·저장 폴더 열기, 접힌 내보내기, 관련 문구·절차·결정 기록.
- 완료 조건: 실제 악보 미리보기는 현재 편집/곡/접수증을 저장하지 않는다. 반영은 기존 해시·기준 정본·접수증 경로를 사용한다. 폴더 열기는 해당 요청의 결과 폴더에 한정한다.
- 제외: 새 요청 전송·악보 제작·기존 결과나 사용자 DB 변경, 공개 배포·버전 올림·Git 통합, 별도 서비스·독립 HTML.
- 검증: 변경 코드·경로·저장 경계 검토와 집중 타입·Lint·서식·i18n·문서 검사, 소스 빌드번호 갱신. 개발 단계의 정적 검사 범위를 유지하며 실제 화면·Finder 열기·반영 재시험 여부를 별도로 기록한다.

사용자는 결과 화면의 내려받기를 필수 작업처럼 제시하는 이유를 지적했다. `결과 미리보기 → 악보에 반영`, 파일 접근은 `저장 폴더 열기`, 별도 사본은 선택적 `내보내기`로 옮기는 제안을 승인했다. 이유는 [ADR-0035](../decisions/0035-score-session-collaboration.md), 실행은 [공동작업 절차](../how-to/collaborate-on-score.md)에 반영한다. 기존 웹앱 담당이 UI/API·UX Rule·history를, 악보제작자가 절차·계획·결정 기록과 최종 검토를 맡는다.

### 구현과 확인 결과

- `production-requests.ts`는 미리보기·반영·폴더 열기를 기본 동작으로 배치한다. 보고서는 앱 안에서 읽고 사본 저장은 접힌 내보내기에서 선택한다. 기준 정본 충돌 안내도 미리보기·저장 폴더 비교로 바꿨다.
- `production-result-read.ts`의 파일 크기·SHA256·패키지·정본 읽기를 미리보기와 반영이 공유한다. `production-result-preview.ts`는 분리해 읽은 결과와 공통 전체 SVG 조판기를 사용한다. `cache: none`으로 파생 캐시 DB를 사용하지 않고, 닫을 때 요청을 취소하고 임시 이미지 URL을 해제한다. 보고서는 검증된 파일을 `textContent`로 표시한다.
- `POST /api/score-requests/:id/open-result-folder`는 같은 origin의 로컬 요청과 빈 JSON만 허용한다. 공통 store가 해당 요청의 `result/` 실경로·디렉터리를 확인한다. 서버가 고정된 Finder 명령에 그 경로를 전달하며 클라이언트의 임의 경로·명령은 받지 않는다.
- 제작자가 위 코드와 기존 `acceptProductionResult`를 직접 대조했다. 현재 편집·곡·접수증을 저장하는 경로는 명시적 반영 동작에만 연결되며, 기준 정본 충돌 확인·저장 전 비교·곡과 접수증의 원자적 저장은 유지된다.
- 앱 담당의 앱/테스트/서버 TypeScript, 변경 코드 ESLint·Prettier, i18n, 공통 컴포넌트·소스 경계, 문서 검사 결과를 확인했다. i18n은 900문구·미등록 UI 0건, 소스 경계는 228파일·963참조다. 로그는 `.tmp/production-result-local-20261113/`에 보존한다. 제작자의 최종 문서·차이 검사는 `producer-docs.log`, `producer-diff-check.log`에 남긴다.
- 앱 버전은 `0.11.5`를 유지하고 소스 빌드번호는 `f061fba8c59f`로 갱신했다. 새 요청 송신·실제 미리보기·Finder 열기·결과 반영 재시험·자동 회귀·프로덕션 빌드는 수행하지 않았다. 이전 화면 캡처와 왕복 성공을 변경 후 UI 검증으로 사용하지 않는다.

사용자가 후속 요청에서 실제 앱의 요청 전송·진행 상태·질문/답장·결과 반영 전 과정을 명시적으로 승인했다. 아래 기록은 앞선 정적 검사 한정을 이번 실행에만 확장한다.

- 목표: 로컬 제작기 UI와 이 담당 세션 사이의 실제 왕복을 검증한다.
- 범위: 기존 5173 서버, Safari MCP, 보존된 실제 악보 패키지, 요청·답장·진행·결과·앱 저장 기록.
- 완료 조건: 실제 세션 수신, UI 상태 갱신, 질문 답장 일치, 결과 반영과 재열기, 입력 음악·자산 보존을 근거로 확인한다.
- 제외: 새 합성 악보·시험 DB, 기존 악보의 임의 음악 수정, 원복·자료 삭제, 공개 배포·Git 통합, 별도 유료 API.
- 검증: DOM/필요 화면·실제 전달 기록·파일 해시·앱 공통 읽기 API로 상태를 대조한다. 실패 시 해당 구간을 수정하고 필요한 검사만 재실행한다.

근거는 `.tmp/score-session-collaboration-e2e-20261113/`에 보존한다. Safari MCP에서 실제 수록곡 `시작 전 손 풀기` 96마디를 음악 수정 없이 검수·반환했다. 초기 앱 빌드는 `b25ca1d9`였고 마지막 검증은 `5efd8d2e`다. 사용자가 승인한 검증 문구를 Codex가 UI에 입력했으며 새 사람의 판단으로 간주하지 않는다.

### 발견한 문제와 수정

첫 요청 `7ffc2241-13e3-418f-a726-db7fedd770a7`의 관측을 보존했다.

- 초기 Bridge 상대경로 설정은 IPC 전에 실패했다. 최초 불확실 관측과 사후 확인 근거를 보존하고 확인된 미전송으로 정정한 뒤 같은 요청을 UI에서 한 번 재시도했다.
- 실제 요청·답장이 지정된 제작자 세션에 도착했다. 요청·질문 ID와 SHA256을 공통 CLI로 확인했다. 앱은 새로고침 없이 진행·질문·답장 접수·제작 완료를 표시했다.
- 입력 XML·패키지를 바이트 그대로 반환했다. 앱에서 반영을 승인했으나 저장본 SHA가 달라 거부했다. 편집 열기에서 note 자식을 재직렬화한 공백 변화였고, DOM 요소·속성·유의미 텍스트 트리와 원본·음원 자산은 동일했다. 접수증은 생성되지 않았다.
- 무변경 정본의 바이트 보존을 수정했다. 원본과 이미 직렬화된 표현 각각의 SHA·두 번째 호출 동일성을 확인했다. 기존 DB나 첫 요청을 되돌리지 않고 현재 확정본으로 후속 요청을 검증했다. SHA 충돌 보호는 유지한다.

## 합의한 흐름

1. 사용자가 제작 또는 교정 요청을 작성하고 전송한다. 일반 저장·임시저장은 작업 지시를 보내지 않는다.
2. 새 제작은 요청문·선택한 원본 파일을 보존한다. 기존 곡 교정은 확정 정본·곡 ID·SHA와 선택 마디를 동결한다.
3. 로컬 서버가 기존 Session Bridge CLI로 지정된 악보제작자에게 요청 ID와 입력 경로를 전달한다. 원본 전체를 채팅 메시지에 붙이지 않는다.
4. 제작자가 요청을 읽고 같은 요청 ID로 진행·질문·실패 또는 결과를 기록한다. 앱은 해당 파일의 상태를 보여주고 질문 답장을 동일 작업에 연결한다.
5. 결과는 검증 항목·한계와 산출물 경로·SHA를 포함한다. 앱의 명시적 결과 동작에서 현재 확정본과 요청 당시 기준을 대조한다. 이후 수정이 있으면 자동 덮어쓰기 대신 결과를 별도로 제공한다.
6. 사용자 판단이 필요한 내용은 질문 상태로 남긴다. 채팅 전달 접수, 실제 작업 시작, 제작 완료, 앱 반영을 같은 상태로 취급하지 않는다.
