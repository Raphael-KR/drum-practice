# 곡별 로컬 프로젝트에서 함께 악보 제작하기

상태: **선행 검토 기록**. 이 문서의 구현 상태는 검토 당시의 기록이다. 사용자 승인 후 작업대·파일 저장 구현은 [후속 구현 계획](score-editor-workflow-20261114.md)에서 추적한다. 실제 사용자 자료 이관과 왕복 검증은 아직 실행하지 않았다.

후속 앱 수정은 [사용자 검토용 구현 계획](score-editor-workflow-20261114.md)에 정리한다. 이 문서는 저장 매체 비교와 선행 작업 기록으로 보존한다.

## 목표와 완료 조건

- 목표: 악보 하나를 프로젝트 폴더 하나에서 제작하며, 사용자·악보제작기·악보제작자가 같은 파일과 변경 이력을 사용한다.
- 현재 범위: 제작·검수·수정 흐름, 사용자/제작자 역할, 저장 상태와 남길 기록, PDF · MusicXML 동시 검수 방식, 기준 문서·절차·스킬. 가사 편집 개선·파일 저장·요청 버튼 구현은 후속 단계다.
- 이번 완료 조건: 하나의 제작·수정 워크플로우로 진입점을 연결하고 현행 구현과 필요한 후속 변경을 구분한다. 실제 저장·재열기·교정 보존의 완료 조건은 후속 구현에서 검증한다.
- 제외: 악보 내용의 임의 교정, 원본·기존 DB 삭제, 공개 재생 앱의 저장소 전환, 새 대화 서비스·별도 DB, Git 추적 정책 변경·자동 커밋·push·발행.
- 이번 검증: 문서 링크·앵커, 제작 스킬 형식, 기존 규칙과 단계별 역할·상태 구분을 검사한다. 앱 코드·실제 자료·화면·송신 시험은 이번 문서 정비에 포함하지 않는다. 종전 요청 화면의 성공을 새 저장 경로의 검증으로 사용하지 않는다.

## 제작 워크플로우

실행 순서는 [공동작업 워크플로우](../how-to/collaborate-on-score.md#shared-score-workflow)에 한 번만 정의한다. **첫 검수본 → 사용자 검수·직접 교정 또는 채팅 지시 → 제작자 반영·저장·재검증 → 완성·인계** 순서다. PDF · MusicXML을 동시에 비교하는 검수 방식을 중심으로 한다.

후속 앱 구현은 이 흐름에 맞게 가사 편집·화면·조작을 개선하고 저장·작업 재개의 연결을 채운다. 곡·변경 내용을 다시 입력하는 요청서·첨부·결과 반입 절차는 만들지 않는다.

## 사용자 결정

2026-11-13 악보제작자 채팅에서 다음과 같이 확정했다.

악보제작기는 사용자와 악보제작자가 함께 제작·교정하는 도구다. 이 세션이 제작 흐름을 주도하고 필요한 앱 구현을 기존 앱 담당과 조율한다. 사용자가 같은 작업을 앱 담당에게 다시 설명하거나 자료 전달 절차를 따로 수행하게 하지 않는다.

1. 편집 내용의 기본 저장소는 로컬 파일이다. 저장 전 임시 편집에는 브라우저 내부 DB를 사용할 수 있다.
2. 각 악보는 자기 프로젝트 폴더에서 작업한다. 악보제작기와 제작자의 작업을 하나의 제작 과정으로 구성한다.
3. 앱에서 요청 버튼을 누르면 어떤 프로젝트를 확인할지만 알린다. 곡 제목·마디·변경 내용 재입력, 첨부파일 재전송은 필요 없다.
4. 변경 내용은 프로젝트 파일과 저장 이력에서 읽는다. 저장과 작업 요청은 별도 동작이며 미확정 초안을 요청 버튼으로 자동 확정하지 않는다.

사용자는 이후 임시 편집도 브라우저 DB 대신 JSON 또는 SQLite가 적절한지 검토하도록 요청했다. 위 브라우저 DB 허용을 최종 저장 매체의 지정으로 해석하지 않는다.

## 임시 편집 저장 매체 검토

제작자는 후속 구현의 저장 매체로 곡별 로컬 JSON을 권고한다. 사용자·앱·제작자가 같은 폴더를 읽는 목적과 현재 문서 단위 편집 모델에 맞춘 판단이다. 별도의 사용자 확정 발언이나 구현 재개 지시로 기록하지 않는다.

| 후보 | 장점 | 이 작업에서의 판단 |
| --- | --- | --- |
| 브라우저 IndexedDB | 현재 초안 복구 코드를 재사용하기 쉽다. | 제작자가 일반 프로젝트 파일로 읽을 수 없고 브라우저별 상태가 갈린다. 새 초안의 기본 저장소로 권하지 않는다. |
| 로컬 JSON | 기존 EditDraft 구조를 읽을 수 있는 파일로 보존하고 일반 파일 도구로 비교할 수 있다. | 권고. 파일 쓰기 순서와 확정본/초안의 기준 버전은 공통 저장 경로에서 관리한다. |
| 로컬 SQLite | 여러 항목의 트랜잭션·부분 갱신·질의·동시 접근을 지원한다. | 유효한 대안이다. 현재 곡별 문서 저장·복원에서 이 기능들이 별도 DB 계약을 채택할 이점으로 확인되지는 않았다. |

- 근거: 현행 `EditDraft`는 Song·canonicalXML·lyricWork·입력 form·savedAt를 보관한다. `editor-session.ts`는 입력 후 180ms, `main.ts`의 다른 저장 경로는 400ms 지연을 사용한다. 잦은 입력마다 전체 미디어를 다시 저장할 이유가 없다.
- 실제 보존 자료 `b1e87067-7d19-4650-b9e4-beecba1598f3/input/`에서 갑자기 MusicXML은 598,886바이트, 패키지 내 음원은 4,732,958바이트다. 속도 비교 시험을 한 값은 아니다.
- 화면 반응은 메모리 상태로 처리한다. 자동 임시저장은 초안 파일만 갱신하며 PDF·음원은 별도 자산으로 참조한다. 확정 저장과 자동 임시저장을 구분한다.
- 같은 파일의 쓰기는 순서를 보장하고 이전 쓰기가 끝난 후 다음 쓰기를 수행한다. 새 내용의 임시 파일을 준비한 뒤 교체하며, 초안이 어느 확정 상태에서 시작했는지 기록한다. 앱과 제작자는 같은 저장 계약을 사용한다.
- 공식 근거: [브라우저 저장소의 origin·보존 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [SQLite 앱 파일 형식과 트랜잭션](https://sqlite.org/appfileformat.html), [Node 파일 쓰기 계약](https://nodejs.org/api/fs.html#fspromiseswritefilefile-data-options). SQLite가 일반적으로 느리거나 부적합하다는 결론이 아니다.

## 구현 전 확인한 구조

- `src/platform/storage/storage.ts`의 `saveRecord`는 확정 악보와 초안을 IndexedDB에 저장한다. 프로젝트 폴더의 최신 파일을 읽는 경로가 기본이 아니다.
- `production-request-form.ts`는 곡·마디·작업 이름·요청문·첨부 입력을 받는다. `production-request-client.ts`는 확정 XML·패키지를 요청별 `input/`에 복사한다.
- `data/production/`은 Git 추적 제외다. 로컬 파일 저장과 Git 추적·커밋은 별개이며 사용자 원본·제작물을 임의로 Git에 추가하지 않는다.
- `packSong`은 제작 초안과 이전 저장본을 포함하지 않는다. 제작 전체 백업은 이를 별도 필드로 보존한다. 완성 `.drumscore`만으로 제작 프로젝트 전체를 대체할 수 없다.
- 기존 가사 교정 이력·이전 저장본·제작 자료·원본/음원·대체 악보·접수증을 유지해야 한다. 새 파일 계약은 공통 모델·읽기·검증 경로에 반영한다.

## 저장·작업 경계

- 저장 전: 편집 중 상태는 메모리에 두고, 복구용 초안은 로컬 JSON으로 저장한다. 마지막 확정 파일을 대신하지 않는다. 브라우저 DB에 이미 있는 자료는 전환 과정에서 보존한다.
- 저장 확정: 로컬 파일 쓰기가 성공한 뒤 저장 완료를 표시한다. 파일 쓰기가 실패하면 저장 성공으로 보고하지 않는다.
- 다시 열기: 로컬 프로젝트의 최신 확정 파일을 읽는다. 남아 있는 초안은 작성 기준과 함께 구분하며, 제작자가 고친 파일을 오래된 브라우저 사본으로 덮지 않는다.
- 제작자 요청: 현재 저장된 프로젝트의 식별 경로를 전달한다. 변경 내용은 프로젝트에서 확인한다. 요청별 전체 자료 복사본과 결과 패키지 재가져오기를 기본 제작 흐름으로 만들지 않는다.
- 제작자 작업: 승인된 범위에서 같은 프로젝트를 교정하고 새 저장 상태·변경 근거·검증 결과를 남긴다. 앱은 그 파일을 읽는다. 공개 재생 앱 수록·발행은 기존 담당과 별도로 확인한다.
- 기존 자료: 현재 브라우저 자료를 삭제하거나 초기화하지 않는다. 로컬 파일로 전환한 항목·미전환 항목과 실제 검증 범위를 구분한다.

## 파일 구성 후보

앱 담당과 검토한 구현 후보다. 워크플로우보다 먼저 적용하지 않으며 실제 코드·검사 결과는 아래에서 따로 확인한다.

- 곡별 루트: `data/production/projects/<곡 ID>/`.
- `project.json`: 현재 확정 저장본 참조와 프로젝트 식별 정보.
- `saves/<저장 UUID>/record.json`, `canonical.musicxml`: 확정할 때마다 남기는 저장본. 공통 RecordData의 제작 자료·교정 이력·이전 저장본·접수증을 보존한다.
- `assets/<SHA256>`: 원본·음원 등 자산. 초안/저장본마다 같은 미디어 바이트를 복제하지 않는다.
- `draft.json`: 확정 저장본을 바탕으로 한 미확정 편집·입력 form. 자산은 참조하고 기준 저장본을 기록한다.
- 앱과 제작 CLI가 같은 store의 읽기/저장을 사용한다. 저장본 파일을 기록한 뒤 `project.json`을 교체하고, 그동안 바뀐 확정본을 이전 사본으로 덮지 않는다.
- 기존 DB 자료는 처음 확정 저장할 때 로컬 파일로 보존한다. DB 일괄 삭제·자동 초기화는 하지 않는다. 새로 여는 제작 프로젝트는 로컬 파일을 기준으로 읽는다.
