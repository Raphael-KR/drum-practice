# 악보제작실 / 드럼연습실 분리

2026-10-02 사용자 승인: 독립 실행 웹앱 둘, 단일 ZIP 완성 파일, 기존 자료·기록 보존, 구현·QA·로컬 커밋. 하위 에이전트 병렬 작업 승인.

- 목표: 제작 앱에서 완성 파일을 만들고 독립 재생 앱이 보관·재생하며 수정본에도 연습 기록을 보존한다.
- 범위: 같은 저장소 두 HTML 진입점/별도 빌드, 공통 재생 런타임, .drumscore v1, 별도 플레이어 저장소.
- 완료 조건: 제작→패키지→재생→동일 구조 수정본 재가져오기, 구조 변경 충돌 선택과 기존 기록 보존; 테스트/번들 경계/Safari 검증.
- 제외: 공개 배포·원격 push, 실제 보관함 덮어쓰기 이전, 곡 포함 HTML 재생 파일 생성/저장.
- 검증: ZIP 검증/손상·버전 거부, IndexedDB roundtrip/기록 보존, 앱 회귀/빌드, 실제 Safari 워크플로. UI 검증은 별도 QA origin/시험 자료.

## 명칭과 운영 방침

- 사용자 확정: 제작 앱 이름은 악보제작실이며 로컬에서만 운영한다.
- 재생 앱이 드럼연습실 최신 버전이다. 이후 공개 배포 대상은 재생 빌드만이다.
- 기존 Sites에 두 앱을 함께 배포하지 않는다. 이번 커밋에서는 배포하지 않는다.

## 경계

- 기존 index.html은 제작 앱 호환 진입점으로 유지하고 editor.html로도 실행한다. 기존 제작 DB drum-practice는 그대로 읽는다.
- player.html은 독립 재생 앱. 새 보관함 drum-practice-player에만 기록한다. 완성 패키지만 가져온다.
- 각각 독립 빌드/실행 명령을 제공한다. 제작 앱이 공유하는 재생 미리보기와 독립 재생 앱/HTML은 동일 runtime/core를 호출한다. 편집 UI·소스 렌더러는 player 번들에서 제외한다.
- .drumscore v1은 manifest와 바이너리 자산을 묶는 ZIP. 원본과 렌더 결과를 포함하되 편집 세션 임시 이력은 넣지 않는다. 원본은 재제작용으로 보관하고 player는 렌더 결과만 사용한다.
- Song.id가 같은 패키지는 수정본이다. 마디 ID/박수/분모가 같으면 로컬 마커·반복·설정·위치를 유지하고 시간은 마디 내 상대 위치로 다시 연결한다.
- 구조가 달라 자동 연결할 수 없으면 무변경 conflict를 반환하고 선택 UI를 제공한다. 명시적 수정본 사용 시 기존 전체 자료를 archive store에 원자적으로 보관한다. 기존 악보 유지 선택도 제공한다.

## 담당과 검증 순서

1. score-package: ZIP 계약과 실패 검증.
2. practice-library: 별도 저장소, 수정본/충돌/복구 보존.
3. playback-runtime: portable 호스트를 공통 Blob 기반 runtime으로 추출, 반복 mount/dispose.
4. authoring: 기존 편집에 완성 패키지 입출력 추가.
5. root: player 보관함/충돌 UX, 두 진입점 빌드, 감사 규칙, 전체 통합 QA와 커밋.

실험/실패/해결 기록은 docs/experiments/editor-player-separation/ 및 history.md에 남긴다.

## 기능 대조표

| 기능 | 제작 앱 | 재생 앱 / 공유 구현 |
|---|---|---|
| PDF/MusicXML/음원/가사 가져오기·교정 | 기존 제작 흐름 유지 | 미포함 |
| 완성 악보 입출력 | score-package 생성/읽기, 동명 ID는 복사 확인 | score-package 읽기 |
| 마디 표시·스크롤·재생·일시정지·속도·반복·클릭 | playback-screen | playback-runtime → playback-screen |
| 재생바·설정·아이콘·키보드·터치 | playback-shell / playback-screen | 같은 구현 |

| 저장 | 기존 storage/editor-session | practice-library, 별도 IDB |
| 수정본 기록 유지·충돌·복원 | 제작 원본 자동 이전 없음 | 동일 구조 상대 위치 보존 / 충돌 선택 / archive 복원 |

## 알려진 환경 차이

- 제작 앱은 제작 세션·PDF/MusicXML 소스 렌더러가 필요하다. 재생 앱은 패키지에 포함된 렌더 결과만 표시한다.
- 제작 화면의 연습 미리보기는 기존 main 호스트에서 공통 playback-screen/shell을 호출한다. 독립 재생 앱과 HTML은 공통 playback-runtime을 호출한다. 제작 상태·미리보기와 재생 전용 저장소의 생명주기는 별도다.
- 재생 앱의 반복·마커 관리 목록은 전체 표시하며 제작 화면의 범용 목록 페이지 구분에 의존하지 않는다.
- 브라우저 저장은 origin별이다. 기존 제작 자료를 새 origin으로 자동 이전하지 않는다. 제작 앱에서 패키지를 내보내 옮긴다.
- iPad 실기기 실행과 공개 배포는 이번 로컬 검증에 포함하지 않는다.

## 실험·실패·해결

1. 기존 구조 테스트가 portable-player에서 화면 직접 호출을 기대해1개 실패: runtime 위임으로 바뀐 실제 호출 경계를 반영, 전체325통과.
2. 제작 입력의 빈 MIME와 .mxl: 식별 가능한 파일 바이트/container 검사로 정규화. 확장자만 맞는 임의 입력은 거부.
3. Safari BFCache에서 pagehide dispose: persisted이면 일시정지·저장하고 DOM 보존, 실제 종료만 해제. 회귀 테스트 통과.
4. Vite 문구 변경 자동 재시작 중 Safari 연결 실패: HTTP200 재확인 후 재접속. 최종 QA는 정적 빌드에서 수행.
5. 뷰어 CSS 직접 import로 빈 HTML 템플릿 esbuild 실패: 공통 playback-ui.css로 합쳐 템플릿/공유 감사 통과.
6. 이전 마커 ID와 새 관리 목록 ID 충돌: 빠른 슬롯 quick-markers 분리, 유일 ID 회귀 검증.
7. 원본 사용자 보관함은 미변경. 로그·화면 캡처·시험 패키지는 Git 제외된 docs/experiments와 dist에만 보관.

권한/계정 차단은 없음. 공개 배포·push·iPad 실기기 시험은 수행하지 않았다.
