### 적용 기준

build-03을 입력으로 보존한다. 음원전용 앱41마디는 PDF42마디에 대응하는 후보이며, 새 악보는 PDF 번호를 유지한다. 83.560초를 PDF41에 적용하지 않는다.

마디별 `beatTimes`를 선택적인 음원 연결 정보로 정본 `drum-practice:score:v1`에 저장한다. 값이 없으면 기존 시작/끝 균등 보간을 유지한다. 실연의 미세한 그루브를 자동 추적하는 기능이 아니라 제작자가 전달한 템포 지도이며, 기존 Loveholic 연결은 변경하지 않는다. 제작용 `recording-grid:v1`은 근거로 보존하고 런타임에서 암묵적으로 적용하지 않는다.

원곡에서는 원본 오디오 1배속과 해당 지도에 맞춘 메트로놈을 사용한다. 연습에서는 악보 사분음표 위치로 변환해 일정한 BPM을 사용한다. 녹음 앞부분과 마지막 악보 이후의 음원 꼬리를 보존한다.

자유 엔딩134–137의 시각은 제작자의 잠정 추정값이다. 소비 코드 검증을 실제 연주와의 청취 확정으로 보고하지 않는다.

### 로컬 재현

- 자료: 사용자 제공 폴더의 `YB - 붉은 노을.mp3`.
- SHA-256: `e1af6bbfb2f9ed16e6c7e91ff1a30f9e97f198de5a537cddabecd51ac7047a29`.
- FFmpeg로 32kHz stereo PCM을 읽고 현재 `beatAnalysisSamples`, `trackAudioBeats`, `estimateAudioBarOne`, `trackedAudioMeasures`를 실행했다. 실제 iPad Safari 디코더/기기 캐시의 재현은 아니다.
- 음원 길이 267.8335초, 분석 BPM 137.9, 자동 1마디 기준 12.990초, 박 배열 578개.
- 이 기준의 41마디는 `[83.370, 83.813, 84.257, 84.700]`초다. 2·3박은 인접 채택 타격 사이를 보간한 위치이며 가장 가까운 감지 타격까지 각각 197ms, 213ms다.
- 37~40마디에도 감지 타격에서 떨어진 보간 위치가 있다. 타격 검출 누락이나 약박/엇박도 가능하므로 보간 자체를 오검출 증거로 보지는 않는다.
- 두 재생 모드는 동일한 저장 박 배열을 사용한다. 배열 오류라면 원곡 클릭과 연습 BPM의 음원 정규화에 함께 영향을 준다.

### 보정 후보의 한계

`music-tempo`의 추종 계수만 20에서 10으로 바꾼 비교에서는 같은 12.990초 기준의 41마디가 `[83.580, 84.010, 84.470, 84.950]`초로 이동했다. 그러나 전체 박 수가 578에서 573으로 바뀌며, 사용자가 추가로 정정한 약 ¼~½박 범위에는 들어가지만 실제 첫 박과 일치한다고 확정할 수 없다. 계수 5는 1078박으로 증가했다. 이 비교를 근거로 앱 계수를 변경하지 않았다.

저주파 강세만으로 마디 첫 박을 확정할 수 없다. 사용자가 듣는 기기의 41마디 시작 시각을 요청했다. 저장된 1마디 기준·박 배열이 로컬 새 분석과 같은지 먼저 확인해야 한다. 기존 기기 자료가 확보되기 전 83.370초를 사용자 기기의 실제 값으로 간주하지 않는다.

재현 파일: `.tmp/red-sunset-41/analyze.ts`, `analysis.json`, `events.json`, `variants.ts`, `variants.jsonl`, `alignment.png`. 앱 코드·분석 버전·사용자 저장값은 수정하지 않았다.

사용자 기기의 재생 화면에는 분·초 표시가 없어 시각을 확인할 수 없다고 답했다. 사용자에게 시각 확인을 다시 요구하지 않는다. 메트로놈 클릭 자체가 먼저 들리는지, 소리는 맞고 화면만 빠른지 구분 질문을 추가했다. `AudioEngine.current()`는 AudioContext.currentTime을 사용하며 출력 지연 보정이 없지만, 이것만으로 관측 원인을 확정할 수 없다.

### 입력과 대응 기준

- 기존값: `.tmp/red-sunset-41/analysis.json`. 41마디 문제 조사 당시 같은 MP3를 FFmpeg 32kHz stereo로 디코딩하고 앱 자동 분석 경로로 재현한 결과다. 578박, 자동 1마디 12.990초. **사용자 iPad의 캐시를 추출한 값이 아니다.**
- 새 값: `public/scores/red-sunset.drumscore`의 `manifest.song.measures[].beatTimes`. 패키지 source XML과 canonicalXML의 전체 137마디 시각·박 배열·박자가 manifest와 일치함을 검사했다.
- 원본 MP3와 패키지 음원 SHA-256 모두 `e1af6bbfb2f9ed16e6c7e91ff1a30f9e97f198de5a537cddabecd51ac7047a29`.
- 동일 MP3를 다시 디코딩한 PCM과 기존 분석 입력 `.tmp/red-sunset-41/audio.f32` SHA-256 모두 `e59d21379d6d8a4dc658e3f69461f443b0a1566f41b79f78fda674b5d5497568`.
- 새 악보 1마디는 녹음된 카운트다. 기존 박 배열의 연주 시작 직전 4박과 비교한다. 본문은 **새 악보 N마디 = 기존 자동 분석 N−1마디**로 대응한다.

<a id="red-sunset-late-audio-analysis--결론"></a>

### 결론

약230.67초(3:50.67) 이후 추적 경로가 갈라진다. 기존 추적은 검출된 타격 중 일부를 받지 못해 빈 박을 보간하고, 이후 더 늦은 타격을 채택한다. 이 경로 선택은 재생 이전의 분석 배열에 이미 들어 있다. 단순 재생 지연이나 전곡에 적용할 일정한 시간차로 설명할 수 없다.

음원만으로 새로 찾은 경쟁 경로는 231.920초부터 기존값보다 앞쪽 타격을 따라가며 후반 첫 박 차이를 약440~460ms 줄이는 후보다. 그러나 기존 경로도 실제 검출 타격을 많이 사용하고, 경쟁 경로가 모든 박의 정답이라는 근거는 아직 부족하다. **앞선 악보 대비 최대710ms를 전부 자동 분석의 오류로 확정하지 않는다.**

### 음원 단독 분석 계약과 재현

- 새 분석 스크립트는 `.drumscore`, MusicXML, 악보 시각·BPM을 읽지 않는다. 이전 검사에서 정한 후반 범위를 포함하도록 200/210/220초부터244초까지를 분석하고,250초까지 포함하는 민감도 검사도 수행했다. 구간의 정확한 끝값을 특정 악보 마디 끝에 맞추지 않았다.
- 입력은 기존 32kHz stereo PCM이며, 원본 MP3 해시 `e1af6bbfb2f9ed16e6c7e91ff1a30f9e97f198de5a537cddabecd51ac7047a29`. 원본/PCM의 동일성 검사는 직전 전곡 비교 기록을 따른다.
- 전체 음원 기준 기존578박을 밀리초 단위까지 모두 재현했다. 악보 기반 보정값을 섞지 않았다.
- 전체·244초 절단·200/210/220초 시작 등6개 범위에서 추종 계수20/10으로12개 경로를 계산했다. 초기 BPM은 전체 음원의 기존 자동 추정137.9 또는 해당 구간 자체의 자동 추정135.6~138.5를 사용했다.
- 비교는 공통으로 검출된224.960초 타격을 기준으로 순번을 맞췄다. 마디 이름은 이전 비교와 연결하기 위한 표기이며 분석·선택 입력이 아니다.
- 라이브러리의 채택 이벤트·보간 전 배열·추적 오차를 임시 복사본에 계측했다. 앱과 설치 라이브러리 코드는 수정하지 않았다.

<a id="red-sunset-late-audio-analysis--왜-기존-경로가-계속-늦어지는가"></a>

### 왜 기존 경로가 계속 늦어지는가

1. **초기 박 근거 약화:** 별도로 계산한3개 주파수대 spectral flux의 자기상관에서220~230초의 주기 상관 최대값은0.606(약0.44초),230~237초는0.078까지 낮아진다. 단순한 일정 박 주기가 흐려졌다는 신호이며, 드럼 필인·보컬·악기 중 무엇 때문인지는 분리음원 없이 확정하지 않는다.
2. **이미 선택한 타격을 기준으로 다음 후보를 거른다:** 기존 경로가231.58초를 채택한 뒤 예측하는 다음 박은232.018초다. 실제 검출 후보231.92초는 예측보다98ms 빠르다. 이 경로의 허용창은 앞64.7ms/뒤129.5ms이므로 앞쪽 후보가 허용창 밖으로 밀려난다. 이후232.91초를 채택하고 사이를 보간한다.
3. **늦은 타격 채택과 템포 추정의 누적 변화:** 기존 경로는238.81·239.35·241.72초 등 예측보다 약99·94·119ms 늦은 타격을 수용한다. 전자는 허용 범위 안이다. 그때마다 주기를 조금 늘린다. 230.22초 타격을 평가할 때 주기는 약434ms,241.72초 채택 직전 약451ms로 바뀐다. 다만 이 변화 중 실제 연주 감속과 잘못된 타격 선택의 비율은 미확정이다.
4. **국소 정확도 대신 전곡 누적 점수로 한 경로를 고른다:** music-tempo1.0.3은 후보 경로의 누적 점수가 가장 높은 것을 선택한다. 200~244초·계수20 분석에서만 이 경쟁 경로가 선택됐고 나머지11조건은 이 후반부에서 기존 경로와 같은 결과였다. 시작점을 바꾸면 경로가 달라지는 민감성을 확인했지만 다수결로 어느 쪽을 정답이라 판단하지 않는다.

코드 근거는 `node_modules/music-tempo/src/Agent.js`의 `considerEvent/acceptEvent/fillBeats`, `src/MusicTempo.js`의 최고점 경로 선택이며, 앱은 `src/modules/audio/audio-beat-tracking.ts`에서 계수20을 사용한다.

<a id="red-sunset-late-audio-analysis--경쟁-경로를-지지하는-별도-음원-신호"></a>

### 경쟁 경로를 지지하는 별도 음원 신호

동일 mono 평균 음원에 중앙 시각을 명시한1024샘플 Hann 창·10ms 간격 FFT를 새로 적용했다. 30~180Hz,180~3000Hz,3000~7900Hz 대역의 양의 로그 스펙트럼 변화량을 각각95백분위로 정규화했다. 각 후보 박 ±35ms의 최대 신호를 평균했다. 타격의 강도 비교이며 박의 의미를 확정하는 정확도 점수는 아니다.

| 구간 | 기존 저주파 지지값 | 경쟁 저주파 지지값 |
| --- | ---: | ---: |
| 220~230초 | 1.883 | 1.883 |
| 231~234초 | 0.668 | 1.280 |

### 해결한 문제와 다음 적용 기준

- 세로 속성 미지원은 기존 개발 담당의 [공통 native words 지원](../archive/rendering-experiments.md#words-position-20261023--연주-지시-words-세로-위치-지원--2026-10-23)으로 해결했다. 실제 원본 높이를 default-y로 기록해 native 자동 배치의 빔 접촉을 피했다. 원본에 높이 근거가 있으면 먼저 기록하고 그 상태에서 최소 표시 offset을 탐색한다.

### 하이햇 O+의 연속 동작과 MusicXML 개별 기호를 혼동함 (2026-10-23)

- 공통 규칙 확정: 사용자는 아래 교정 결과의 같은 음표 harmonic·stopped와 XML 위치 속성에 의한 가로 배치를 다음 악보에도 적용하도록 결정했다. 현재 실행 기준은 [O+ 공통 매핑](../../reference/score/notation.md#score-musicxml-osmd-mapping--o-복합-지시의-승인-범위)과 악보 제작 스킬이다. 곡별 간격은 실제 표시로 검수하며 붉은 노을 좌표를 고정값으로 복사하지 않는다.
- 후속 적용: 사용자가 같은 음표의 두 주법과 XML 위치 기록을 승인한 뒤 open 대신 harmonic을 지정했다. 현재 붉은 노을6곳은 harmonic·stopped, 같은 default-y와 stopped default-x13으로 교정했고 실제 공통 네 경로24쌍/Safari 확대6곳을 검증했다. 아래 표준 조사·미적용 문장은 그 전 조사 시점의 이력이다. [최신 제작·전송/HMR 해결 기록](red-sunset.md#red-sunset-open-close-20261023--붉은-노을-o-가로-배치-교정)을 따른다.

- 사용자 의미 확인: 붉은 노을 원본의 `O+`는 하이햇을 열어 친 뒤 곧바로 닫는 오픈 앤 클로즈 주법이다. 원 안 ＋로 표시하는 반열림과 구별한다.
- 원인: 앞선 답변은 두 기호를 가로로 배치하는 문제에 집중하고, 같은 음표에 기호 두 개를 저장하는 것과 열기 → 닫기의 시간적 순서를 표준 데이터로 표현하는 것을 구분하지 않았다. 기존 변환의 `open-string`은 공식적으로 개방현 기호이며 하이햇 전용 요소가 아니다.
- 공식 확인: MusicXML 4.0의 `technical` 요소 목록과 XSD에는 하이햇의 열기 → 곧 닫기를 하나로 정의하는 전용 요소가 없다. `open`은 원형 열기 기호, `stopped`는 ＋형 정지/닫기 기호를 정의한다. SMuFL 1.4 타악기 주법 표도 Open(`pictOpen`), Closed / rim shot(`pictOpenRimShot`), Half-open(`pictHalfOpen1`)을 개별 글리프로 정의하며 O+ 복합 동작의 단일 글리프를 정의하지 않는다.
- XML 구조의 후속 확인: `open`과 `stopped`의 부모는 `note/notations/technical`이다. `articulations`의 허용 자식에는 둘 다 없으며 `muted`라는 요소도 MusicXML 4.0 XSD에 없다. `mute`는 `play` 아래의 재생용 요소이므로 ＋ 기호용 태그로 대체하지 않는다. 음표에 기호를 조합하는 것과 잘못된 부모/태그를 사용하는 것을 구별한다. [articulations 허용 목록](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/articulations/), [mute](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/mute/).
- 제시된 외부 자료의 범위: [StackExchange 글](https://music.stackexchange.com/questions/54057/how-to-notate-a-quick-open-and-close-hi-hat)은 열기·닫기를 기보하는 방법을 설명하며 MusicXML 태그 구조의 근거는 아니다. 함께 제시된 YouTube Shorts는 이번 웹 조회에서 Cache miss로 본문을 확인하지 못했다. 태그 허용 여부는 조회 가능한 W3C 공식 요소 목록/XSD로 확인했다.
- 표현의 한계: 한 음표의 `technical`에 열기·닫기 요소를 함께 넣어도 XML 나열 순서나 좌우 위치가 닫는 시점·지연 길이를 정의하지는 않는다. `other-technical`로 주법 설명을 보존할 수 있지만, SMuFL 지정 없는 확장 설명의 프로그램 간 자동 해석은 표준이 보장하지 않는다.
- 후속 검토 후보: `open`/`stopped`에 타악기 전용 SMuFL 글리프를 지정하는 경로와 원본 O+의 결합 표시를 함께 검토한다. 이는 일반 도형/문자 조합의 신규 매핑 승인이나 OSMD 지원 확인이 아니다. 현재 확정 범례와 실제 XML·SVG는 이번 조사에서 변경하지 않았다.
- 확인 범위: 기존 v10 XML의3·5·7·127·129·131마디에 동일 음표의 `stopped`와 `open-string` 조합이 있다. 공식 규격 대조와 기존 파일 재읽기만 수행했으며 새 XML·SVG 생성, 조판 호환성·음향 재생 검증은 하지 않았다.
- 다음 기준: O+의 오픈 → 클로즈 의미와 원본 타격 연결을 보존한다. 반열림으로 치환하거나 원본에 없는 닫기 박·지연 길이·추가 타격을 추정해 넣지 않는다. 표준 요소의 유효성, 원본 의미의 보존, 조판 지원, 실제 재생 지원을 따로 확인한다.
