# Safari 두 줄 보기 스크롤 진단·갱신 개선

문서 역할: **실측·수정 기록**. 불필요한 표시 갱신 감소와 native 충돌의 최종 해결 여부를 구분한다.

## 목표·범위

- 목표: 사용자 두 줄 재생 충돌의 실제 원인을 확인하고 정지/스크롤 중 불필요한 화면 갱신을 줄인다.
- 범위: 사용자 승인 macOS Safari/WebKit 충돌 로그의 읽기 전용 진단, 두 앱 공통 재생 표시 코드·기존 실제 자료 회귀·기록. 기존 수록본/미커밋 변경을 보존한다.
- 완료 조건: 충돌 유형·앱 유발 조건의 확정 범위를 구분하고, 같은 값의 프레임 갱신이 텍스트 노드를 교체하지 않으며 실제 Safari에서 정지 DOM 변경 감소·탐색/재생/정지의 정상 갱신을 확인한다.
- 제외: Safari/OS 설정 변경·강제 재시작·사용자 라이브러리 변경·새 합성 자료/시험DB·스냅/스크롤 기능 제거·버전 인상·커밋·push·발행. 제한된 비재현을 충돌 완치로 보고하지 않는다.
- 검증: 사용자 시각의 native crash stack → 실제 붉은 노을 공통 runtime 전후 DOM 계측 → 기존 fixture 집중 회귀와 두 앱 전체 검사/빌드. 출력·박 시각·저장 계약은 유지한다.

## 충돌 진단

- 사용자는0.8.13/빌드9240c536의 붉은 노을 **2줄 재생 중** 재로드 안내가 떴고, 두 줄 스크롤이 불규칙하게 버벅인다고 보고했다. 이전 패키지 검증은 표시·왕복·ready 확인이며 지속 재생 안정성 보증이 아니었다.
- 별도 사용자 승인을 받아 `~/Library/Logs/DiagnosticReports`의 해당 시각 WebContent 보고서와03:35–03:39:30 관련 시스템 로그를 읽었다.03:35:57/PID78977과03:38:30/PID87170은 같은 pageProxyID2589에서 `reason=Crash`로 종료됐다. 두 보고서 모두 `EXC_BAD_ACCESS / SIGSEGV / KERN_INVALID_ADDRESS 0x40`이며 main thread 상단은 `ScrollAnimationMomentum::updateScrollExtents` → `ScrollableArea::didAddScrollbar` → `RenderLayerScrollableArea::createScrollbar`다.02:26:27 보고서에도 같은 native stack이 있다.
- 종료 사유는 메모리 제한에 의한 강제 종료가 아니다. 같은 시각의 메모리 압력·약1–2GB footprint 관측은 별도 사실이며, 이 기록만으로 메모리 누수나 충돌과의 인과를 확정하지 않았다. IPS의 수십GB 예약 가상 주소를 실제 RAM 사용량으로 읽지 않는다.
- 참고한 [WebKit 공식 ScrollAnimationMomentum 소스](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/ScrollAnimationMomentum.cpp)는 스크롤 범위 갱신 때 momentum calculator를 사용하는 경로를 보여 준다. 조회한 main을 설치 Safari22625.1.29.11.28의 동일 리비전으로 간주하지 않는다. 특정 앱 DOM/스크롤 동작이 native 충돌을 유발하는 정확한 재현 조건은 아직 확정하지 못했다.

## 실측과 공통 수정

- 원래 Safari MCP 호출은 Transport closed였다. 다른 세션·브라우저를 종료하거나 전역 설정을 바꾸지 않고, 같은 공식 `/usr/bin/safaridriver --mcp`의 임시 CLI 연결로 새 Safari 자동화 탭을 열었다. 기존 연결 복구와 새 연결에서의 검증을 구분한다. 개인 저장곡을 열거나 저장하지 않고 실제 수록 패키지를 공통 runtime에 저장 콜백 없이 전달했다.
- 수정 전 붉은 노을112마디부터 실제 재생 버튼으로137마디/곡 끝까지 실행했다. 정지 중 native 스크롤→실제 재생 시작·카운트오프·두 줄 교체·종료가 동작했고 이 제한된 실행에서는 충돌이 재현되지 않았다.
- 곡 끝의 정지 화면1.2초/43프레임 동안 stage에258건의 DOM 변경이 생겼다. 같은 hidden/class 속성과 마디/박/박자 텍스트 노드를 매 프레임 다시 쓴 결과다. 공통 `playback-ui.ts`·`playback-frame.ts`·`playback-screen.ts`에서 값이 달라질 때만 갱신하도록 수정했다.
- 첫 수정 후112마디/정지 화면에서는 텍스트 변경이 없어졌지만1.2초/86프레임에 SVG beam clip의 동일 x/width 쓰기344건을 추가 확인했다.137마디의 첫 측정과 위치·beam 수가 다르므로 직접적인 성능 전후 비교로 사용하지 않았다. 공통 `note-highlight.ts`도 clip 값이 달라질 때만 기록한다.
- 스크롤/줄 경계 스냅·음표 강조 효과·한 줄/두 줄 교체·재생 박 시각은 유지한다. SVG 조판/패키지/저장 형식은 변경하지 않으므로 조판 캐시 정책v36은 그대로다. 악보제작기와 드럼연습실 모두 같은 공통 표시 모듈을 사용한다.
- 최종112마디 정지 화면은1.2초/86프레임 동안 stage DOM 변경0건, 측정 최대 프레임 간격16ms였다. 최초137마디와 다른 위치이므로 그 두 측정을 직접적인 FPS 향상률로 보고하지 않는다. Safari 도구로 위700px·아래400px 실제 스크롤 후 scrollTop5160→4460→4860, 곡 위치205.93초 보존을 확인했다. 이 구간에는 실제 scroll 이벤트에 따른 style 변경2건만 있었고 텍스트/beam 재기록은 없었다. 자동화 scroll은 실제 트랙패드/손가락의 관성 입력과 동일하다고 보지 않는다.
- 최종 코드에서도 실제 재생 버튼으로112마디205.93초→137마디/음원 끝267.83346875초를 실행했다. ready 유지·마디 교체·곡 끝 정지와1줄→2줄 복귀 시 위치 보존을 확인했다. 같은 곡 끝 정지 상태의1.2초/87프레임에서 DOM 변경0건으로, 수정 전 같은 위치의258건이 없어졌다. 실행 중 새 WebContent 충돌 보고서는 없었지만, 기존 충돌은 수정 전 재실행에서도 재현되지 않았으므로 완치 근거로 삼지 않는다. 검사 후 임시 runtime과 이 작업에서 연 탭/CLI 연결만 정리했다.

## 자동 검사·보존

- 기존 실제 demo 자료의 두 호스트 회귀에 정지 반복 프레임의 텍스트 노드/scrollTop 보존과 실제 다음 마디 갱신 검사를 추가했다. 기존 beam fixture에는 같은 박의 clip attribute 변경0건과 다른 박으로의 x 갱신 검사를 추가했다. 새 합성 fixture는 생성하지 않았다.
- 최초 집중3파일116검사 통과 후 beam 보완을 포함해 전체 검사를 다시 실행했다. 최종 `npm run verify`129파일765검사·lint·서식433파일·타입/문서/구조·두 앱 빌드/경계 통과. 기존 Node localStorage/큰 청크 경고는 유지되며 검사 실패는 없다.
- 두 앱0.8.13/소스 빌드 `fbac2388f3bf`. public 수록6개와 새 player 빌드 패키지는 직전 수록 작업의 해시와 같다. 기존 사용자 원본/교정본·미커밋 renderer/제작 변경을 보존했다. 청취·iPad 실기기·공개 사이트 시험과 커밋·push·발행은 수행하지 않았다.
- 근거는 Git 제외 `.tmp/safari-reload-20261024/`에 있다. 진단 요약에는 관련 프로세스·예외·native frame만 남기고 무관한 보고서 필드·사적 데이터는 제외했다. `before.json`·`intermediate.json`·최종 계측·집중/전체 로그와 실제 로컬 페이지 관측을 함께 읽는다.
