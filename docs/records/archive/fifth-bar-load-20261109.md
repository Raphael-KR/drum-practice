# 5번째 마디 경계의 CPU·메모리 조사

- 목표: 일부 iPhone Safari의 5번째 마디 재로드와 관련될 수 있는 공통 재생 부하를 재측정하고, 확인된 불필요한 처리를 줄인다.
- 범위: 실제 Loveholic·바람과 언덕의 발라드 자료, 1줄/2줄 공통 재생 경로, 로컬 CPU·DOM·힙·프로세스 관측과 필요한 최소 수정.
- 완료 조건: 같은 입력/환경의 전후 근거, 마디 경계·표시·재생·저장 계약 보존, 집중 회귀·정적 검사·두 앱 빌드 결과를 기록한다.
- 제외: 문제 기기 로그 없는 충돌 원인 확정/완치 주장, iOS 기기·시뮬레이터 실행, 새 시험 DB·무허가 합성 자료·원본 변경, 커밋·푸시·발행.
- 검증: 기존 실제 자료와 fixture, 5번째 마디 전후의 실제 재생/갱신·자원 수명 비교. Chromium 수치를 iPhone/Safari 측정으로 확대하지 않는다.

## 시작 상태

main `1fe915bcd40e560e100eb62d49e5bb1341609eef`, 두 앱 0.10.2, source `bafd7bde5196`. 앞선 의존성·경고·화면 준비 변경 25개 파일을 보존한다. 사용자는 문제 당시 보기 모드를 확인하지 못했다고 답해 두 경로를 조사한다.

이전 조사에서 2줄 보기의 첫 4마디 교체 경계와 과거 macOS native 스크롤 충돌이 확인됐지만 이번 iPhone의 Jetsam/WebContent 로그는 없다. 이 기록은 새 실측을 과거 결과와 분리한다.

## 실제 관측과 수정

### 1. 자동 저장마다 전체 악보를 읽던 폐기 ID 검사

`savePracticeState → openScoreDatabase → purgeRetiredScore`가 위치 저장 때마다 `songs.openCursor()`로 모든 악보 레코드를 읽었다. `songs`의 키는 이미 `song.id`다. 따라서 폐기한 `tom-moving-original-v1` 한 개를 확인하려고 다른 악보의 큰 음원·페이지까지 읽을 필요가 없다.

- 변경: `store.get(RETIRED_SCORE_ID)`로 해당 키만 조회한다. 양쪽 DB의 기존 16마디 검증·삭제 조건·트랜잭션·예외 처리는 유지한다. 폐기 정책을 없애거나 초기화 완료를 영구 캐시하지 않았다.
- 실제 Loveholic 자동 저장 관측: 약 13초·저장 11회에서 전체 cursor 22회 → 0회. 수정 전 순회된 레코드의 음원·주 원본·주 페이지 크기 합은 누적 632,593,335바이트, 수정 후 해당 전체 순회는 0바이트다. 대체 악보 미디어는 이 합에서 제외했다. 누적 접근 payload이며 동시 RSS 또는 실물 메모리 할당량을 뜻하지 않는다. 저장 횟수·저장 형식·저장 큐를 줄이거나 끄지 않았다.
- 같은 기존 DB에서 이전 함수 사본과 수정 함수를 번갈아 3회 실행한 준비 비용: 이전 24.7/22.7/17.9ms, 수정 0.8/0.4/0.4ms. 중앙값 22.7 → 0.4ms다. 정상 완료 시 매번 수행하는 같은 조회 계약이며 소스/운영 코드를 되돌리지 않았다.
- 활성 곡 자체를 읽고 갱신하는 기존 큰 레코드의 `get/put`은 남는다. 이것까지 분리하려면 연습 상태와 미디어의 저장 책임에 대한 별도 설계·호환성 검토가 필요하다. 이번에 DB 이름·버전·키·bytes-v1·마이그레이션·저장 간격을 바꾸지 않았다.

### 2. 두 줄의 현재 행 DOM 보존

기존 `renderScoreRows`는 5번째 마디에서 `[1..4,5..8]`을 `[9..12,5..8]`로 바꾸면서 현재 재생할 5..8마디까지 모두 다시 만들었다.

- 변경: 같은 폭의 재생 창에서는 계속 표시할 마디와 강조 SVG를 보존한다. 나가는 네 칸만 제거하고 새 네 칸을 만든다. 보존할 행을 불필요하게 detach/attach하지 않는다. 마지막 행의 위아래 교환, 불완전 마지막 행, 균등 보기의 wrapper, 정지 시 시간순 전체 탐색은 유지한다. 폭/track 무효화 때는 모두 다시 만든다.
- 실제 Loveholic, 같은 5번째 마디에서 새 칸 8 → 4개, 제거 칸 8 → 4개. 하위 요소 생성 692 → 385개, 제거 659 → 352개. 파싱 HTML 134,077 → 68,821문자다. 해당 native HTML setter 단일 관측은 4.5 → 1.2ms였으나 이것만으로 프레임 전체 개선율을 계산하지 않는다.
- 실제 바람과 언덕의 발라드에서 얻은 마디 HTML을 이전·수정 함수에 똑같이 전달한 별도 비교: 조건별 10회 평균을 3회 관측한 중앙값 3.06 → 1.88ms. 새 칸 8 → 4, 유지 칸 0 → 4이며 직렬화 SHA-256은 둘 다 `6c566d53b83dcd7b51976fe269e85b1fe5381dc09939cd1eebfa824abfaced0a`였다. DOM 준비 경로만의 비교이며 오디오·가사 충돌 배치·paint를 포함한 전체 프레임 시간은 아니다.

### 3. 두 줄에서 사용하지 않는 transform 준비 힌트

가로 transform이 `none !important`인 두 줄 ribbon에도 `will-change: transform`이 적용돼 있었다. 두 줄에만 `will-change: auto`를 사용해 브라우저가 불필요한 가로 합성 준비를 강제받지 않게 했다. 표시 좌표·색·빛나기·스크롤 정책은 유지한다. 실제 computed style도 auto다. 이 변경으로 GPU 메모리가 얼마 줄었다는 주장은 하지 않는다.

한 줄의 힌트는 별도 A/B/A 임시 CSS 실험에서 일관된 개선을 확인하지 못해 유지했다. 한 줄에 새 가시성 제한·가상화·기능 축소를 넣지 않았다.

## 환경·메모리 해석과 한계

- macOS Darwin 27.2 / Apple M4 Pro / 24GiB, Ego Lite 0.6.2.9 / Chrome 156. CPU 4배 제한·852×393 CSS px·DPR 3이다. Safari MCP가 지원하지 않는 CDP CPU profiler·힙/DOM 계측을 위해 ego-browser를 사용했다. 이 조건은 iPhone/WebKit 실기기 에뮬레이션이나 iOS 검증을 뜻하지 않는다.
- 현재 실제 저장 Loveholic 경로와, 저장 콜백 없이 같은 공통 runtime을 사용하는 실제 두 곡을 분리했다. 후자는 수록 패키지 → 공통 MusicXML 조판 → 실제 AudioContext/재생 경로다. 원본 저장곡을 새로 import하거나 시험 DB를 만들지 않았다. 라이브러리와 별도의 가짜 플레이어/가짜 음원을 만들지 않았다.
- 실제 자동 저장 경로의 메인 스레드 TaskDuration 증가분은 수정 전 13.10초 관측에 2.657초, 수정 후 13.92초에 2.175초였다. 1회씩의 관측이며 전체 CPU 사용률이나 실기기 개선율로 일반화하지 않는다. 입력/브라우저 계측 시간도 포함하므로 직접 조회 3회 비교와 분리한다.
- 같은 실제 저장 관측에서 JS 힙은 약 17~25MiB였다. CDP backingStorageSize는 이전 24~163MiB, 수정 27~157MiB 범위였다. 각각 서로 다른 소유 영역이므로 단순 합산해 앱 RAM으로 쓰지 않는다.
- 렌더러 PID 18697은 CDP ProcessTime과 `ps` 누적 CPU가 여러 지점에서 일치하는 것으로 구분했다. 저장 관측의 RSS는 이전 약 481~643MiB, 수정 약 682~803MiB로 수정 후 높은 시행도 있었다. 반복 탐색/조판·Blob 이미지 캐시·GC/브라우저 회수 시점과 시작 상태가 같지 않아 고정 상주량 감소 또는 증가를 이번 수정의 효과로 판정하지 않았다. 제거한 반복 접근량과 DOM 생성량은 위에서 별도로 확인했다. 장기 누수·최대 순간 피크·GPU/폰트별 native 소유량 감소는 이번에 확정하지 못했다.
- 저장 콜백이 없는 두 줄 관측에서는 5번째 마디의 JS 힙 급증을 관측하지 못했다. 첫 4마디 교체와 반복 저장이 부하 요인임을 확인한 것이며, 일부 iPhone의 Jetsam/네이티브 충돌 원인을 확정한 것은 아니다. 1줄·2줄에서 재생은 진행됐으나 Ego의 높은 DPR·CPU 제한에서는 긴 프레임 간격이 관측돼 Safari/iPhone의 매끄러움 통과로 사용하지 않는다.
- 한 번의 두 번째 곡 실행 중 개발 빌드가 generated JSON을 갱신해 Vite가 페이지를 reload했다. 이 실행은 실패/제외로 남겼다. source/생성 파일을 고정하고 재실행해 실제 두 곡 모두 7번째 마디까지 진행·일시정지했다. 이 개발 HMR을 사용자 iPhone 장애 재현으로 보고하지 않는다.

## 보존·검사·작업 상태

- 실제 Loveholic의 원래 ribbon 보기·position 0·전체 Song·앱 선호 원문을 검사 전후 일치시켰다. canonicalXML·음원/원본/페이지 해시도 직전 검증값과 같았다. 마지막 임시 runtime dispose에서 AudioContext closed, 30개 URL 고유 해제·남은 마디 DOM 0을 확인했다. 기존 DB 목록/버전 v4·v3·렌더 캐시 v1은 같았다.
- 기존 123마디 fixture를 재사용한 행/빈 칸/균등/마지막 행/재시작/폭 변경 검사를 보완했다. 현재 행의 동일 Node와 미제거, 4회 생성, 폭/track 무효화 후 새 Node를 확인한다. 화면 관련 3파일·122검사·정적 검사·두 앱 빌드는 통과했다. 소스 `f3ab5d3ad6b0`, 두 앱 0.10.2 유지다.
- 저장 회귀용 `retired-score`·`practice-library`와 메모리 전용 fake-indexeddb 실행은 사용자 허가를 요청해 대기 중이다. 지정 ID 조회·28/96마디 보존의 기존 fixture에 무관한 cursor 미호출 단언을 준비했으며 아직 실행 결과로 표시하지 않는다. 새 디스크 DB·SQLite·새 악보 fixture를 생성하지 않았다.
- 후속 [0.10.3 릴리스](release-0.10.3.md)에서 전체 기존 fixture·임시 시험 DB를 허가받았다. 폐기 악보 집중 2개와 전체 810테스트를 통과해 위 개발 단계의 저장 회귀 대기를 해소했다. 과거 측정 시점과 릴리스 재실행은 구분한다.
- 실행 근거: `.tmp/fifth-bar-20261109/`의 `stored-rows-{before,after}.json`, `stored-comparison.json`, `database-open-comparison.json`, `love-rows-phone-{before,after}.json`, `real-rows-phone-after.json`, `row-replay.json`, `ribbon-hint.json`, `library-{before,after}.json`, `closure.json`, 검사·빌드 로그다. 초기의 viewport가 기본값으로 돌아간 진단은 폰 비교에서 제외했다.
- 과거 지침/기록은 현재 소스와 대조했으며, 문제 iPhone의 로그 확보·iOS 기기/시뮬레이터·원격 CI/공개 사이트·전곡 청취는 수행하지 않았다. 커밋·푸시·버전 인상·발행 없음. 계측용 TaskSpace 3을 한 번 종료하고 제한을 해제했으며 작업용 Vite 서버도 중단했다.
