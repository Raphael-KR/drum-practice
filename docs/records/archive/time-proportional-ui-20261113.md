# 시간 비례 조판의 두 앱 실제 출력 검증

- 목표: 공통 조판 전환 후 가사 묶음·변박 폭·초과 줄 축소와 재생 좌표를 실제 화면으로 확인한다.
- 범위: 로컬 드럼연습실과 악보제작기의 SVG 전체 보기·연주 1줄·2줄 보기.
- 입력·환경: 실제 수록 `real-paradis.drumscore`, Safari MCP, `http://127.0.0.1:5173/`, Node 26.13.0·pnpm 12.18.0, 앱 0.11.5.
- 변경: 공통 timeline의 페이지 분리·캐시 정책 v53, 제작기의 자산 준비 완료 전 프레임 실행 방지. 정본·가사·음원은 수정하지 않는다.
- 제외: 합성 입력·시험 DB·전체 회귀 실행·편집 저장 왕복·iOS·빌드·커밋·push·발행.

- 1024px 화면에서 일반 4/4 셀은 약 251.344 CSS px다. 81–84줄의 4/4 셀은 각각 237.281px, 5/4는 293.516px이며 합계 약 1005.36px로 줄 안에 들어간다. 공통 SVG 배율은 일반 줄 0.930909, 초과 줄 0.878830이다. 같은 SVG의 음표·가사와 진행선·탐색 좌표가 해당 배율을 함께 사용한다.
- 실제 패키지와 연주 SVG의 12개 마디(17–19, 63–64, 81–85, 109–110)에서 최종 묶음 문구가 일치했다. 묶음 첫 시작점과 사분음표당 64의 시간축을 확인했다. 가사 글자의 왼쪽 잉크 경계는 OSMD 라벨의 고유 여백을 가지므로 진행선과 글자 왼쪽이 항상 같은 픽셀이라는 뜻은 아니다.
- 선택한 전체 SVG 10마디의 음표머리 중심에서 `64 × 음악적 시점`을 뺀 값의 마디 내 차이는 최대 약 0.415 SVG단위다. 연주 SVG의 기대 중심 대비 오차는 최대 약 0.405단위다. 이는 글리프별 잉크 중심 차이를 포함하며 64단위 시간축과 일치한다.
- 실제 재생 표본: 드럼연습실 2줄의 84마디 525프레임·85마디 154프레임, 악보제작기 1줄의 84마디 377프레임·85마디 153프레임·86마디 36프레임. 마디 안에서 진행선이 뒤로 이동한 표본은 없었다. 두 앱 모두 정지 상태로 돌려놓았다.

## 발견하고 수정한 페이지 분리 오류

최초 연주 진입은 `MusicXML 마디 영역이 올바르지 않습니다.`로 실패했다. 공통 timeline 경로에서 `RenderSingleHorizontalStaffline`이 켜져 OSMD가 세로 페이지를 나누지 않았다. 한 마디씩 줄은 계속 내려가지만 첫 SVG 높이만 남아 8마디의 상단 933.640이 페이지 하단 801.980을 넘었고 높이가 음수가 됐다. 전체 보기 출력의 성공이나 정적 검사만으로 이 경로를 확인할 수 없었다.

`musicxml-engine.ts`에서 timeline에는 이 옵션을 적용하지 않아 native 페이지 분리를 복원했다. `musicxml-geometry.ts`의 잘못된 영역 오류에 마디·페이지·경계 수치를 추가했다. 수정 후 두 앱에서 110마디의 연주 화면을 열고 위 표의 보기·재생 전환을 확인했다. 캐시 정책은 `drum-time-proportional-v53-pagination`으로 갱신했다.

## 남은 실제 충돌

88마디의 최종 묶음 `리누케`가 다음 `테`를 약 12.95 SVG단위 침범한다. 28마디의 `리누`와 `케테모` 사이에는 약 2.02단위가 남는다. 최종 묶음의 텍스트·시작점은 정본과 같고, 여러 원음절을 묶은 결과가 다음 묶음까지 침범한 사례다.

[승인된 가사 묶음 결정](../../decisions/0033-final-lyric-groups.md)에 따라 정본을 표시 단계에서 다시 묶거나 임의 축소하지 않았다. 따라서 이번 결과를 가사 충돌이 모두 해소됐다는 뜻으로 사용하지 않는다. 실제 사례에 대한 후속 표기 결정과 필요 시 악보제작자의 정본 작업이 남는다.

## 제작기 열기 중 일시적인 잘못된 좌표

같은 악보를 목록에서 다시 열 때 `viewBox="50 NaN 270 NaN"` 등의 경고가 발생했다. 안정된 화면의 좌표는 유효했지만, 활성 record를 먼저 노출하고 자산·음원 준비를 기다리는 사이에 프레임이 숨겨진 stage의 크기로 계산됐다. 자산 교체 뒤로 record 할당만 옮겨서는 경고가 남았다.

제작기 host의 `ready`에 record 로딩 완료를 반영하고, 자산·음원 준비와 화면 표시가 끝난 뒤 프레임을 허용했다. 별도 기본 좌표나 NaN 대체값은 추가하지 않았다. 최종 첫 열기와 목록 복귀 후 재열기에서 110마디·유효한 viewBox·기존 변박 폭과 콘솔 경고 없음을 확인했다. 원래 경고는 `editor-reopen-warning.json`, 수정 후 결과는 `editor-ready-recheck.json`에 보존했다.

## 검증 증거와 한계

- 화면 및 측정 원본: `.tmp/time-spacing-ui-20261113/`. `player-`·`editor-`로 시작하는 PNG는 실제 각 보기다. `measurements.json`에 셀·SVG·재생 측정값, `read-actual-svg-geometry.js`에 실제 패키지/출력 읽기 절차를 보존했다.
- 화면 측정 당시 소스 빌드번호는 `8f096105`다. 이후 캐시 정책 v53과 제작기 준비 순서를 수정했으며 조판 배치식은 그대로다. 최종 빌드번호는 `7374d7f43a94`다.
- 실제 화면 검증은 Real Paradis를 대표 입력으로 한 위 범위다. 전곡 모든 마디, 편집 저장·재열기, 모든 화면 크기와 기기의 통과를 뜻하지 않는다. 음원·정본 편집이나 별도 저장 버튼은 사용하지 않았고 앱의 정상적인 보기·재생 상태 저장과 파생 캐시는 발생할 수 있다.

## 최종 실행 결과

- 변경한 공통 코드 3파일과 제작기 host의 ESLint, 앱 TypeScript 검사, 공통 재생/컴포넌트/소스 경계 검사, 관련 코드·문서 Prettier 검사와 `git diff --check`를 통과했다. 문서 검사는 178개 Markdown·4,884개 로컬 링크·3,503개 앵커 링크를 통과했다. 로그는 증거 디렉터리의 `lint.log`, `editor-lint.log`, `typecheck.log`, `structure.log`, `format.log`, `docs.log`에 있다.
- 빌드번호 `e3c8e2f8afae`와 정책 v53으로 두 앱을 다시 열었다. 각각 110개 마디와 81–88의 기존 셀 폭·SVG 배율을 확인했다. 값은 `cache-v53-reopen.json`에 보존했다.
- 제작기 재열기 한 번에서 `NotReadableError: The I/O read operation failed.`가 기록됐다. 시각은 타입 검사 준비 단계의 build-info 재생성·개발 서버 갱신과 겹쳤다. 그 뒤 파일을 변경하지 않은 상태의 두 차례 재열기는 성공했고 최종 콘솔에는 새 오류가 없었다. 갱신과의 인과관계는 확정하지 않으며, 일반 사용 중 재현되는 읽기 오류를 해결했다는 근거로 삼지 않는다.
- Git은 기존 main `0d74c288ddeb4c274ddef14cdbdd2360a3e28b18`을 유지한다. 이번 변경은 미커밋이며 원격 push·배포는 수행하지 않았다.
