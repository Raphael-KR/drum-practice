# 공개 사이트 보안 보강

- 목표: 공개 사이트 검토에서 발견한 분석정보 오염·요청/저장 남용·응답 헤더·음원 디코딩 위험에 대응한다.
- 범위: 분석 API, 로컬 검토 UI와 승인 저장소, 배포 스냅샷, 음원 사전 검사.
- 완료 조건: 승인/미승인 경계·요청/저장 한도·로컬 검토 검증과 앱/Worker 빌드.
- 제외: 원본 음원 업로드, 기존 자료 자동 승인/삭제. 커밋·push·발행은 후속 명시 요청으로 수행했다.
- 검증: 사용자가 2026-10-14 검사·테스트·빌드를 허가했다. 공격/부하 검사는 공개 사이트에서 하지 않는다.

## 확정된 저장·검토 경계

사용자 결정: 로컬 자료는 Site에서 바꾸지 못한다. 미등록 파일의 익명 분석정보는 검토 대기로 받고, 로컬에서 검토·승인한 정보만 공용 자료에 반영한다.

1. 공개 GET은 **로컬에서 명시적으로 승인해 발행한 스냅샷만** 반환한다. 승인 해시 인덱스는 Worker에, 승인 JSON은 정적 자산에 둔다. D1 장애가 승인 정보 조회를 막지 않는다.
2. 익명 PUT은 계약을 검사한 뒤 D1 `audio_analysis_pending`에 저장하고 202를 반환한다. 승인 해시 PUT은 409다. 동일 해시 재등록은 기존 후보를 덮어쓰거나 보관 기간을 연장하지 않는다.
3. 공개 사용자는 대기 자료를 조회할 수 없다. 분석정보가 없으면 기기에서 분석한다. 음원 원본·파일명·개인 마커·구간은 전송하지 않는다.
4. 로컬 5173의 초기 화면에 **검토대기 00건** 버튼을 표시한다. 버튼을 누르면 후보 선택, 곡명/가수/BPM/첫 박/박자표/전체 박 시각 수정, 검토 확인 후 승인·반려가 가능하다. 서버 조회 실패는 `서버 확인 불가`로 표시하고, 표시된 건수가 로컬 후보만 포함함을 안내한다.
5. 로컬 승인 DB가 정본이다. 수정·승인 후 다음 발행 때 승인 스냅샷을 다시 만든다. 공개 API에는 정본 수정 경로가 없다. 반려 결정도 로컬에 보관한다.
6. 승인/반려는 로컬에 먼저 저장한다. 이어 전용 인증으로 동일 revision의 서버 대기 자료만 삭제한다. 삭제 실패 시 로컬 결정은 유지하고 사용자에게 알린다. 남은 서버 후보는 만료 정책을 적용한다.

기존 `audio_analysis` 테이블은 보존하되 공개 조회에서 제외한다. 현재 분석기 버전의 로컬 기존 자료는 검토 후보로 표시한다. 과거 익명 서버 기록은 자동 승인하거나 새 대기함으로 복사하지 않는다. **발행 시점에 승인 자료가 0건이면 공용 재사용도 0건부터 시작한다.** 기기에 이미 가져온 음원/분석은 유지된다.

## 로컬 권한과 인증

- 로컬 API는 loopback 주소와 5173 Host만 허용한다. 다른 Origin·cross-site 요청은 거부한다. 승인/반려 POST에는 세션 CSRF와 후보 revision, 명시적 검토 여부가 필요하다.
- `data/runtime/analysis-review-token`에 256비트 난수 키를 권한 0600으로 저장한다. Git/정적 자산/브라우저에 넣지 않는다. Worker에는 SHA-256 검증값만 포함한다.
- 로컬 서버만 고정 Site 주소에 Bearer 키를 전송한다. 리디렉션을 따르지 않고 응답 크기·시간을 제한한다. 원격 검토 API는 인증된 조회/대기 후보 삭제만 제공한다.
- 키를 잃거나 유출하면 새 키를 생성한 뒤 그 검증값으로 다시 발행해야 한다. 이전 키로 연결할 수 없는 상태를 빈 대기함으로 표시하지 않는다.
- 검토 UI·로컬 DB/CSRF 처리 코드는 공개 player 번들에 포함하지 않는다.

## 요청 제한과 운영 용량

| 범위 | 한도 | 초기화 |
| --- | --- | --- |
| 같은 IP | 하루 10회 | 한국시간 매일 00:00 |
| Site 전체 순간 요청 | 분당 60회 | 매분 |
| Site 전체 | 시간당 1,000회 | 매시 정각 |
| Site 전체 하루 | 하루 3,000회 | 한국시간 매일 00:00 |

유효한 등록뿐 아니라 중복·잘못된 형식·금지 메서드 등 등록 API의 쓰기 시도를 센다. GET은 이 등록 한도를 사용하지 않는다. 한도 초과는 429와 다음 허용 시각까지의 `Retry-After`를 반환하며 클라이언트는 즉시 재시도하지 않는다. 여러 기기가 같은 공인 IP를 공유하면 10회를 공유한다. 고정 구간 정책이므로 경계 직전·직후에 각각 한도까지 요청할 수 있다.

Worker는 플랫폼이 제공하는 `CF-Connecting-IP`를 사용한다. DB에는 날짜별 해시 키만 저장하고 원본 IP를 넣지 않는다. 이 키는 익명화 보장이 아닌 단기 가명이다. 전역 한도를 먼저 소비해 IP 카운터가 무한히 생성되지 않게 한다. SQL 조건부 upsert로 동시 요청의 초과 허용을 막는다.

- 대기함: 최대 **500건 / 직렬화 JSON 합계 32MiB / 후보 유효기간 30일**. 둘 중 하나의 용량 한도를 넘으면 503과 Retry-After를 반환한다.
- 30일이 지난 자료는 조회에서 제외하며 다음 등록 요청에서 실제 삭제한다. 예약 삭제 작업은 없다. 처리 완료 자료는 로컬 검토 직후 서버 삭제를 시도한다.
- COUNT/SUM 조건을 포함한 단일 INSERT로 동시 Worker의 저장 상한을 적용한다. 파일별 256KiB, 박 시각 20,000개 제한도 유지한다.
- 등록 실패·한도 초과·서버 장애가 기기 분석과 연습을 막지 않는다.

**1,000회/시간은 기존 200회의 5배인 초기 운영 상한이지, 실측된 최대 처리량은 아니다.** 100명이 각 10회 등록할 수 있는 시간당 용량이다. 실제 Sites 계정의 D1/Workers 할당량과 전체 서비스 부하는 확인되지 않아 무제한 증량하지 않는다. 3,000회 일일 제한은 누적 DB 작업을, 60회 분당 제한은 집중 요청을 줄인다. 대기함 500건은 별도 상한이므로 신규 파일이 몰리면 검토·삭제가 먼저 필요하다.

근거: [D1 요금·쿼터](https://developers.cloudflare.com/d1/platform/pricing/)는 행 읽기/쓰기와 인덱스 갱신 비용을 설명하고, [Workers 제한](https://developers.cloudflare.com/workers/platform/limits/)은 플랜별 요청/CPU 제한을 설명한다. 공개 무료 플랜 수치를 이 Site의 실제 할당량으로 가정하지 않았다. D1 서비스 쿼터의 UTC 날짜와 앱의 KST 날짜도 다르다. 거부 요청도 최소 DB 조회를 소비하며 이 제한은 WAF/DDoS 방어 또는 가용성 보증을 대신하지 않는다.

## 나머지 두 보호 조치

- Worker: nosniff, Referrer-Policy, X-Frame-Options, HTTPS HSTS. CSP의 frame-ancestors/object/base는 강제하고 전체 리소스 CSP는 **보고 전용**으로 둔다. 플랫폼 삽입 스크립트 호환을 공개 환경에서 확인하기 전에는 전체 스크립트 차단 완료로 보지 않는다.
- 음원: 전체 읽기 전 100MiB, 디코딩 전 메타정보로 30분/2채널/32kHz PCM 256MiB 상한을 검사한다. 크기를 판정할 수 없으면 중단하며 디코딩 결과도 재검사한다. 파일 메타정보가 거짓일 수 있으므로 브라우저 디코더의 모든 메모리 사용을 보증하지 않는다.
