# 사용자와 악보제작자가 같은 로컬 악보 프로젝트에서 공동작업한다

## Context and Problem Statement

사용자는 악보제작기를 이 악보제작자 세션과 함께 제작·수정하는 도구로 요청했다. 최초 구현은 별도 요청서, 입력 복사본, 결과 패키지 반영을 중심으로 구성했다. 실제 왕복은 검증했지만 사용자가 같은 작업 내용을 다시 입력하고 로컬 파일을 다시 전달하는 흐름이 남았다.

사용자는 곡별 프로젝트 폴더에 모든 작업이 남고, 버튼은 제작자에게 어떤 프로젝트를 확인할지만 알리도록 정정했다. 확정 저장의 기준은 로컬 파일이다. 저장 전 브라우저 DB는 허용할 수 있다고 말한 뒤 JSON·SQLite까지 비교하도록 요청했다.

이어 사용자는 앱부터 구현하지 말고 워크플로우를 먼저 정비하도록 지시했다. 사용자 역할은 첫 악보의 전체 검수와 필요한 가사 위치 교정이며, PDF · MusicXML을 동시에 보는 검수 방식은 적절하다고 확인했다. 이후 가사 편집이 불편하므로 워크플로우에 현재 프로그램을 그대로 사용한다는 표현을 두지 말라고 정정했다. 악보제작자가 이 협업을 주도하고 필요한 앱 구현을 담당자와 조율한다.

## Decision Drivers

- 한 곡의 자료와 변경 이력을 사용자·앱·제작자가 함께 읽을 수 있어야 한다.
- 사용자는 최초 검수와 가사 위치 교정에 집중할 수 있어야 한다.
- 제작자가 기술 작업·다른 오류 수정·재검증을 끝까지 맡아야 한다.
- 사용자 교정이 재제작에도 유지되어야 한다.
- PDF · MusicXML 동시 검수와 편리한 가사 교정을 지원하고 불필요한 요청·전달 절차를 줄여야 한다.

## Considered Options

- 앱의 요청서·입력 복사본·결과 반입을 독립된 제작 시스템으로 유지한다.
- 원본과 결과를 사용자가 매번 파일로 전달한다.
- 곡별 로컬 프로젝트를 공동 작업의 기준으로 삼고 앱과 제작자가 같은 작업을 이어간다.

## Decision Outcome

세 번째 방식을 선택한다. 첫 검수본, 사용자 전체 검수, 직접 교정 또는 채팅 지시, 제작자 반영·저장·재검증, 완성·인계를 하나의 흐름으로 정리한다. 사용자는 가사 수정도 이 채팅에서 지시할 수 있으며 직접 편집은 필수 단계가 아니다.

현행 요구사항은 [공동작업 Rule](../reference/score/production.md#score-session-collaboration), 실행 순서는 [공동작업 워크플로우](../how-to/collaborate-on-score.md#shared-score-workflow)에 둔다. 파일 저장의 구현 상태와 매체 비교는 [전환 계획](../plans/local-score-projects-20261113.md)에서 관리한다. SQLite 또는 JSON이라는 형식 선택을 제작 워크플로우보다 앞세우지 않는다.

### Consequences

- PDF · MusicXML 동시 비교를 중심으로 검수한다. 가사 편집을 포함한 기능·화면·조작은 워크플로우에 맞게 개선한다.
- 앱에서 저장한 교정은 제작자가 같은 프로젝트에서 읽고, 제작자가 저장한 수정은 앱에서 다시 읽는다. 공동 편집 과정에 자료 재첨부·결과 다운로드·재가져오기를 요구하지 않는다.
- 초안과 확정 저장본은 구분한다. 제작자가 읽은 뒤 추가된 사용자 교정을 오래된 사본으로 덮지 않는다.
- 로컬 파일 저장은 Git 추적·커밋·push와 별개다. 원본·음원 등 기존 Git 제외 자료를 자동으로 추적하지 않는다.
- 기존 요청 파일과 검증 근거는 보존한다. 종전 왕복 성공을 새 프로젝트 저장·교정 재개 경로의 검증으로 대신하지 않는다.
- 새 파일 저장 구현은 아직 미완성이다. 워크플로우 우선 지시에 따라 추가 앱 구현을 중단하고 이미 작성한 변경은 보존한다. 문서 정비 완료만으로 구현을 재개하지 않는다.
