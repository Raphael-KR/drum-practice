# 두 앱은 같은 릴리스 번호와 소스 빌드 식별자를 사용한다

## Context and Problem Statement

패키지 버전과 앱 표시 번호, 당시 잘못 표시한 릴리스 번호를 구분해야 했다. 원래 결정 시기는 2026-10-04·10-13 이후이며, YAML 날짜는 이번 문서 정리일이다.

## Considered Options

* 각 앱 번호와 package.json을 혼용한다.
* app-versions.json을 정본으로 삼아 두 앱의 릴리스 번호를 기본적으로 맞춘다.

## Decision Outcome

후자를 채택한다. 독립 사용자 흐름은 minor, 기존 기능 보완은 patch이며 문서만 변경하면 앱 버전을 유지한다. 사용자 커밋 지시 때 앱 변경 버전을 올리고 공개 여부·검증은 별도로 기록한다.

### Consequences

과거 SHA·배포 ID·로그 경로는 번호 정정으로 바꾸지 않는다. 공통 번호가 두 앱 검증·공개 완료를 뜻하지 않는다. 새 기능·삭제·전송·배포 승인을 추가하지 않는다.

### Confirmation

현행 계약과 실행 절차는 [버전 Rule](../reference/engineering/release.md#app-versions--앱-공통-버전), [버전 절차](../how-to/release.md#app-versioning--앱-버전-갱신-절차), [릴리스 기록](../records/releases.md#app-version-history--앱-릴리스-번호와-정정-기록)에서 확인한다. 아래 당시 검증 수치·실패·미확인은 해당 환경의 기록이며 이번 작업에서 앱·악보 검증을 다시 수행한 결과가 아니다.

## More Information

대안은 원문에서 확인되는 채택·대체 경로를 정리한 것이다. 별도 회의나 새로운 합의를 추정하지 않는다. 이관 원문에 포함된 대체 전 값은 현행 규칙이 아니다.

> ## 두 앱의 공통 버전 관리
> - 앱 버전 정본은 src/app-versions.json이다. package.json 버전은 공용 개발 패키지 버전이며 앱 표시 버전으로 사용하지 않는다.
> - 사용자 결정(2026-10-13): 악보제작기와 드럼연습실은 같은 릴리스 버전으로 맞추는 것을 기본으로 한다. 한쪽 전용 수정도 함께 버전을 올리고 실제 변경 대상은 변경 기록에 명시한다. 독립 릴리스가 필요한 예외만 별도로 판단한다. 문서만 변경하면 앱 버전은 유지한다.
> - 버전 단계는 변경 내용으로 판단한다. 새로운 사용자 기능·독립된 사용 흐름 추가는 minor(예: 음원만으로 연습 → 0.7.0), 기존 기능의 오류 수정·화면/조작 개선은 patch(예: 가져오기 분리·버튼 배치 → 0.7.1)로 올린다. 0.x에서도 이 기준을 적용하며 patch를 기계적으로 선택하지 않는다. 호환성을 깨는 변경이나 1.0 전환은 영향과 출시 범위를 먼저 판단한다. 변경 기록에는 단계 선택 이유를 적는다.
> - 기본 명령은 `npm run version:app -- both patch|minor|major`이며 변경 기록과 함께 커밋한다. 버전 일치는 같은 소스 릴리스 기준이라는 뜻이며 양쪽 검증 완료·공개 배포를 뜻하지 않는다. 제작기는 로컬 전용을 유지한다.
> - 사용자 결정(2026-10-04): 앱 수정마다 `node scripts/build/build-info.mjs`로 소스 기반 빌드번호를 갱신한다. 커밋 없이도 변경된 빌드번호가 화면에 표시되도록 한다.
> - 앱 버전번호는 사용자가 커밋을 지시했을 때 함께 올린다. 사용자가 별도로 버전 정정·동기화를 요청하면 해당 요청을 따른다. 자동 커밋·푸시·퍼블리싱은 하지 않는다.
