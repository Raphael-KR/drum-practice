### 1. 자료 접수와 원본 보존

**입력:** 사용자가 지정한 PDF·음원, 곡명·제작자 정보, 기존 XML·패키지·교정본과 이번 작업 범위.

**수행 방법·도구:** 실제 루트 `/Users/raphael/Playground/drum-practice`에서 `pwd`, `git status --short --branch`, `git rev-parse HEAD`를 확인한다. 자료의 SHA256, 파일 크기, PDF 쪽 수, 음원 길이·채널·샘플레이트를 `shasum -a 256`, `pdfinfo`, `ffprobe`와 기존 분석 도구로 기록한다. 원본은 읽기만 하며 프로젝트 안의 Git 제외 실험 폴더에 사본을 둔다. 새 시도는 새로운 하위 폴더에서 수행한다. 같은 내용의 재접수 여부도 해시로 확인한다.

**산출물:** 곡별 `docs/<곡 식별자>-CONVERSION.md`, 로컬 `docs/experiments/<곡 식별자>-<접수일>/`의 원본 사본·provenance·이전 결과 목록. provenance에는 원본 경로/해시, 사본 경로/해시, 접수일, 도구 버전, 실행 명령과 출력 폴더를 기록한다.

**완료 조건:** 원본과 사본 바이트가 같고 기존 결과의 보존 위치가 확인된다. 원본·자동 초벌·교정·최종 파일을 서로 구별할 수 있다. 미디어·실험 자료가 Git 제외 대상인지 확인하며 자동 stage하지 않는다. 출력명은 `source-transcription.musicxml`과 `score-final.musicxml`처럼 역할로 구분한다. 대소문자만 다른 이름은 쓰지 않는다.

**실패 시 확인:** 프로젝트 지침과 [통합·자료 보존 기록](MUSICXML-INTEGRATION.md). 과거 worktree·이동된 venv를 현재 실행 경로로 가정하지 않는다. 기존 파일이 있는 출력 경로는 새 폴더로 바꾸고, 사용자 자료를 지우거나 덮어써서 해결하지 않는다.

### 2. PDF 유형과 변환 경로 결정

**입력:** 보존한 원본, 페이지별 글리프·글꼴·선/이미지 조사 결과.

**수행 방법·도구:** [변환 정책](MUSICXML-CONVERSION-POLICY.md#선택-순서)에 따라 벡터/스캔/사진/혼합을 구별한다. `pdfplumber`로 문자 행렬·좌표·오선·줄기·빔을 조사하고 원본 렌더와 대조한다. 벡터는 구조 추출을 우선하고 스캔·사진은 Audiveris 자동 초벌 후 원본 교정을 먼저 시험한다. 혼합 입력은 페이지별로 평가한다. 새로운 양식은 대표 2~3줄에서 일반 패턴·필인·박자/주법 예외를 포함해 시험한다.

**산출물:** 페이지 유형표, 대표 원본 crop, 교정 전 출력/로그, 오류 목록, 선택한 경로와 선택 이유. 대표 구간의 위치와 집계 기준을 고정한다.

**완료 조건:** 대표 구간의 음표·쉼표·동시음·음가와 중요한 예외를 실제로 판독할 수 있다. 누락·애매한 항목 및 필요한 교정량을 기록한 뒤 전체 확장 경로를 결정한다. 낮은 표본 오류율을 전곡 정확도로 표현하지 않는다.

**실패 시 확인:** [Real Paradis 변환](MUSICXML-CONVERSION.md)·[비교](MUSICXML-COMPARISON.md), [Loveholic 구조 추출](LOVEHOLIC-CONVERSION.md), 문제 해결 기록 → 과거 제작 세션 → 공식 웹 자료. 기존 코드의 해시 가드를 해제해 다른 곡을 통과시키지 않는다.

### 3. MusicXML 구조와 악기·주법 교정

**입력:** 원본 구조, 대표 판독 근거, 추출한 마디별 이벤트 또는 보존한 자동 인식 초벌.

**수행 방법·도구:** 실제 마디 경계·박자표·템포·성부·동시음·음가·쉼표·점·붙임줄·연음·장식음·반복·구간 지시를 원본과 대조한다. 기존 `scripts/musicxml/`의 추출/내보내기/검증 구조를 참고하되 새 곡의 글꼴·좌표·예외에 맞는 판독과 fixture를 만든다. 악기 이름·MIDI·오선 위치·음표머리·주법은 [확정 매핑](SCORE-MUSICXML-OSMD-MAPPING.md)을 따른다. 원본 성부·화음·기둥 구성을 임의로 공통화하지 않는다.

독립적으로 원본에서 읽은 대표 fixture와 XML 재읽기를 비교한다. 마디 합계가 맞는지뿐 아니라 각 시작·길이·화음·악기·표기를 검사한다. 로컬 MusicXML 4.0 XSD와 기존 `verify.py`의 의존 스키마 resolver를 사용한다. 변환 코드를 바꾸면 누락·잘못된 음가/악기/박자·동시음 분해 등의 오류 주입으로 검출 능력을 확인한다.

**산출물:** 추출 IR/원본 객체, 교정 목록, 마디별 판독 상태, MusicXML 후보, fixture, XSD·재읽기·오류 주입 결과. 번호 연속성·드럼 파트의 마디 수·총 사분음표 길이·머리/쉼표/주법 개수도 기록한다.

**완료 조건:** 원본과 이벤트가 대응하고 의도된 성부별 박 합계·규격·재읽기를 통과한다. 여러 파트의 마디 수를 합쳐 전곡 길이를 계산하지 않는다. 반복 표기와 실제 재생 순서는 현재 [정본 계약](MUSICXML-CANONICAL.md)의 지원 범위를 확인한다. 미확정 의미·렌더링 미지원·표시 성공을 서로 구분한다.

**실패 시 확인:** 매핑 정본과 그 승인 이력 → 곡별 제작 문서·원본 fixture → 과거 제작 세션 → MusicXML/OSMD/Audiveris 공식 자료. PDF X간격이나 마디 합계를 맞추기 위한 임의 음가 조정은 하지 않는다. 새 대체 매핑이 필요하면 매핑 정본의 보고·사용자 결정 절차를 따른다.

### 4. 인쇄 가사 대조와 음악적 위치 저장

**입력:** 원본 가사 문자·bbox, 마디 경계, 판독한 음표/쉼표 시작·음가. 제공된 보컬 악보가 있으면 함께 대조한다.

**수행 방법·도구:** [가사 기준](MUSICXML-CONVERSION-POLICY.md#가사-기준--악보-우선)과 [정본 계약](MUSICXML-CANONICAL.md)을 따른다. 문자/음절/영어 단어의 순서·줄·마디를 보존하고 실제 음표 또는 쉼표 underlay에 대응시킨다. 기존 `loveholic_printed_lyrics.py`·`loveholic_lyric_notes.py`는 해당 원본의 재현 도구로만 참고한다. 독립 `DrumPracticeLyrics`의 표준 `note/lyric/text`와 `measureId + quarterOffset + durationQuarters`로 기록하며 없는 보컬 음높이를 만들지 않는다.

판독 추정에는 대상 음절·마디·근거 구절·선택한 위치·다른 가능성을 남긴다. 마디 귀속만 판독되는 경우에는 [마디 가사 계약](MEASURE-LYRICS.md)을 확인하고 그 한계를 보고한다. 음표 대응을 요구한 가사를 중앙 문구만으로 완료 처리하지 않는다. PDF 표시 좌표와 음악적 시작·길이는 별개로 다룬다.

**산출물:** 원문 보존 자료, 음절별 판독/추정표, 표준 가사 XML, 왕복 비교. 필요하면 원본 해시·region geometry와 lyricId/음악적 위치에 묶인 PDF 표시 anchor 근거를 추가한다.

**완료 조건:** 문자·순서·마디·시작·표시 음가가 저장/재읽기 후 유지된다. 드럼 데이터·음원 연결은 가사 추가로 바뀌지 않는다. PDF 음표 중심과 실제 파란 가사를 대조한다. 가수의 실제 발음 시작/끝·길이, STT·CTC·LRC 검색은 완료 조건이 아니다.

**실패 시 확인:** [가사 제작·과거 음원 시험](LOVEHOLIC-LYRICS-REVIEW.md), [실제 PDF 가사 수정](LOVEHOLIC-PDF-LYRIC-PLACEMENT.md), 문제 해결 기록. 인쇄 위치를 가창 시간 측정으로 해석하거나 PDF의 가로 간격을 그대로 음가로 바꾸지 않는다.

### 5. 음원 첫 박·BPM·마디 시간 연결

**새 드럼 음원을 제작하는 경우:** [드럼킷 선택 기준](GARAGEBAND-DRUM-KITS.md#제작-시-드럼킷-선택--사용자-결정-2026-10-06)을 먼저 적용한다. 현재 보존된 SoCal·Portland 중 곡·연습 목적에 맞는 키트를 선택하고 프로젝트 복사본의 샘플과 필요한 매핑을 확인한 뒤 악보 이벤트와 같은 시간표로 제작한다. 선택한 키트와 이유·출처·검증을 곡별 문서에 기록한다. 아래 원음원 보존·연결 절차는 제공된 원음원을 사용하는 경우에 적용한다.

**입력:** 원음원 전체, 검증한 마디/박자표, 악보 템포, 판독한 타격 시작, 음원 분석 결과.

**수행 방법·도구:** [변환 정책의 필수 검증](MUSICXML-CONVERSION-POLICY.md#초기-악보음원-제작-필수-검증--첫-박과-카운트오프)을 실행한다. `ffprobe`, 앱 템포 추정/박자 탭, `loveholic_audio.py`의 PCM·spectral-flux/타격 대조 방식을 참고한다. 계산에는 임시 디코딩을 사용할 수 있으나 원음원을 자르거나 재인코딩해 대체하지 않는다. 음원0초와 악보 첫 박을 구분하고 `firstBeat`·첫 마디 start를 맞춘다. 인쇄 BPM과 실연 템포/마디별 연결값이 다르면 각각 기록한다.

초반·중간·후반의 특징적인 타격/필인과 박자 변화·휴지 뒤 시작을 비교한다. 경쟁하는 ±박 위상과 누적 드리프트를 점검한다. 국소 상관값·주변 피크는 추정 근거이며 실제 드럼 타격이나 청취 오차의 확정값이 아니다. 마지막 쉼표와 원음원 끝부분도 보존한다. XML의 안정 마디 ID·음원 해시·시작/끝 연결과 파생 Song을 왕복 대조한다. 국소 연결을 단일 BPM으로 덮어쓰지 않는다.

**산출물:** 음원 연결 JSON/정본 메타데이터, 첫 박·인쇄 BPM·실연 추정·마디 start/end·근거·불확실성, 아래 재생 검수표. 가사 초 단위 캐시는 이 연결에서 계산하며 실제 가창 전사로 표시하지 않는다.

**완료 조건:** 첫 박·템포·시간표의 근거와 원음원 보존을 확인하고, OFF/ON·배속·반복을 실제 재생/청취에서 대조한다. 코드 수치/자동 검사와 기기 청취를 별도 결과로 남긴다. 청취가 없으면 패키지의 재생 검증은 미완료로 표시한다.

**실패 시 확인:** 아래 책임 구분 → 해당 곡 제작 기록과 history → 정본 연결 계약·공통 재생 예약 코드 → 과거 세션 → 공식 자료. OFF 정상·ON 실패를 곡 데이터나 음원 자르기로 우회하지 않는다.

#### 첫 박·카운트오프 검수표

곡명, PDF/음원 해시, firstBeat, BPM/해당 구간 박 길이, 앱 버전/빌드, 브라우저·기기, 시작 위치, 배속, 카운트 설정, 관측 방법과 결과를 각 행에 기록한다. 수치만 검사했다면 ‘청취 미검증’이라고 적는다.

| 확인 | 시작 위치·조건 | 완료 판단 |
|---|---|---|
| OFF | 곡 처음과 중간 마디, 기본 배속 | 음원·악보·메트로놈의 박이 일치 |
| ON | 음원0초·첫 마디 시작점·중간 마디에서 각각 | 네 번의 사분음표 준비 카운트 다음 박에 실제 첫 박 연결 |
| 느린/빠른 배속 | 같은 시작점에서 OFF/ON 비교 | 마지막 카운트→첫 박이 해당 배속의 사분음표 한 박 |
| 앞부분 | 실제 곡의 첫 박 이전 구간, 긴 앞부분 회귀 사례 | 앞부분 보존, 준비 카운트와 첫 박 정렬; 실제 입력에 없는 긴 앞부분은 코드 회귀 검사로 구분 |
| 반복 | 같은 반복 경계에서 여러 회차 | 박 중복·누락 없이 이어짐 |

| 관측 | 조사 책임과 처리 |
|---|---|
| OFF에서도 어긋남 | 제작 측 첫 박·BPM·마디별 연결을 검토하고 실제 음원/악보와 재대조 |
| OFF 정상, ON만 어긋남 | 앱 카운트오프 예약 문제로 전달. 정상인 곡 시간표는 이동하지 않음 |
| 수치 검사 정상, 청취 미실시 | 수치 통과만 기록. 기기 청취 완료로 표현하지 않음 |
| 시뮬레이터/Chromium만 확인 | 그 환경의 결과로 기록. 실물 iPad Safari·오디오 결과로 대체하지 않음 |

### 6. SVG 조판·재생 캐시·완성 패키지

**입력:** 검증한 XML, 음악적 가사·음원 연결, 원본 PDF/음원, 검증한 페이지·마디 영역과 표시 좌표.

**수행 방법·도구:** [SVG 정본](SVG-SCORE-RULES.md)과 [브라우저 조판](BROWSER-MUSICXML-RENDERING.md)을 읽고 공통 `src/musicxml.ts::renderMusicXML`을 사용한다. 전체 인쇄 SVG와 연습 화면의 배치를 구분한다. 캐시는 현재 렌더러/표시 정책/원문에 맞게 생성하며, `src/browser-score.ts::prepareBrowserScore`의 실제 열기 결과도 검수한다. 기존 동봉 SVG만으로 최신 화면의 모양을 보증하지 않는다. 원문을 렌더러 출력으로 재생성하지 않는다.

`src/canonical-xml.ts`의 정본 쓰기·읽기와 `src/score-package.ts`의 `createScorePackage → readScorePackage`로 완성 `.drumscore`를 생성·재읽기한다. 곡별 helper는 입력·원본 해시·경로·포트를 검토한 뒤 사용한다. loopback 근거 수신기는 새로운 출력 폴더에서 실행하고 작업 후 그 프로세스만 종료한다. ZIP 감사는 확장자 추정 대신 manifest의 실제 자산 경로를 읽는다.

**산출물:** 최종 MusicXML·전체 SVG/재생 캐시·원본 PDF 페이지·`.drumscore`, 패키지 manifest와 해시·CRC·왕복 보존 보고서, 실제 출력 캡처.

**완료 조건:** Song 전체와 canonicalXML, PDF/음원 원시 바이트, 마디/박자·가사·대체 악보 연결이 왕복 유지된다. 모든 마디와 주법을 실제 렌더에서 확인한다. glyph DOM 개수는 쉼표·꾸밈음 포함 여부를 명시한다. PDF 세로 영역은 자기 줄 내용 포함·이전 줄 혼입 방지, 가로 자르기는 승인된 표시 규칙과 원본 geometry에만 적용한다. 다른 곡의 crop/anchor를 복사하지 않는다.

**실패 시 확인:** 패키지 계약 → SVG/매핑 정본 → 문제 해결 기록. XML 파싱 성공이나 warnings 없음은 주법 출력 성공이 아니다. Poppler/CairoSVG PNG와 실제 Safari SVG의 폰트/잘림 결과를 구별한다. HMR·병행 소스 변경이 있으면 조율해 입력·렌더러 상태를 고정하고 새 증거를 만든다.

### 7. 실제 앱 수록본과 저장 곡 검수

**입력:** 검증한 최종 패키지, 작업 대상 origin/앱·현재 빌드, 기존 저장 곡/수록 파일과 연습 상태.

**수행 방법·도구:** 이미 승인된 로컬 앱 범위에서 Safari MCP로 실제 ‘완성 악보 가져오기’ 또는 수록곡 ‘악보 업데이트’를 실행한다. 대상 곡·origin을 먼저 확인하고 기존 자료를 보존한다. 같은 곡 구조의 설정·마커·루프를 유지하는 업데이트 계약을 따른다. 구조가 달라지면 자동 재배치하지 않는다. Safari 실패는 원인을 기록한 뒤 프로젝트의 대체 브라우저 절차를 따른다.

저장 후 화면을 닫고 다시 연다. 실제 저장 레코드·canonicalXML·음원 해시·마디/가사 개수를 입력 패키지와 대조한다. PDF/SVG × 한 줄/두 줄, 전체 악보의 첫/중간/끝·밀집 필인·주법·가사·페이지 경계를 확인한다. 마디 클릭·진행선·재생/일시정지·배속·반복·마커·보기 전환 후 상태 보존과 5단계의 OFF/ON 청취를 확인한다. 화면에 가사가 있는 것과 PDF 대응 위치가 맞는 것은 별도 검사다.

**산출물:** 실제 저장·재열기 대조, 화면/재생 검수표·캡처, 앱/기기/빌드·원문/패키지 식별, 유지된 연습 상태와 잔여 결함.

**완료 조건:** 생성 파일·실제 수록 파일·실제 저장 곡의 버전이 연결되고 재열기 후 내용과 상태가 유지된다. 합성 fixture나 메모리상의 render 호출만으로 실제 수록 완료를 선언하지 않는다. 제작 검수와 앱 수정·발행 책임을 나누며, 현재 대상 밖의 기존 탭/공개 사이트가 갱신됐다고 가정하지 않는다.

**실패 시 확인:** [Loveholic 실제 수록 수정](LOVEHOLIC-PDF-LYRIC-PLACEMENT.md), 패키지 업데이트/구조 충돌 계약, 조판 캐시 키·음원 해시. 오래된 저장 곡·수록 파일·표시 캐시·다른 origin 중 어느 단계인지 확인한다. 데이터와 UI/오디오 예약 결함을 분리해 담당 세션에 정확한 근거를 전달한다.

### 8. 결과 인계와 제작 종료

**입력:** 원본/최종 해시, 단계별 검사 결과, 해결·추정·미검증 목록, 실제 작업/수록/배포 상태.

**수행 방법·도구:** 곡별 제작 문서와 `history.md`를 갱신한다. 해결한 문제는 원인·수정·검증·다음 적용 조건을 문제 해결 기록에 연결한다. 전달받은 세션의 성공 보고만으로 상태를 확정하지 않고 필요한 최종 파일/핵심 근거를 직접 확인한다. 지시받은 담당 채팅에는 범위 안의 결과를 전달하며 새 외부 메시지/발행 권한은 별도로 판단한다.

**산출물:** 다음 담당자가 이전 대화 없이 사용할 인계: 정확한 원본/최종 파일 경로·SHA256, 생성 코드·버전·명령·의존 파일·새 출력 폴더, 실제 마디/총 길이, 가사/주법 상태, 첫 박/BPM·연결표, 실제 앱 origin/빌드·수록/재열기·청취 결과, 보존 자료, 앱 결함·추정·미검증과 다음 조치.

**완료 조건:** 아래 완료 판정표의 상태를 모두 채웠다. 미검증은 이유와 담당/다음 확인을 명시한다. commit·push·수록·deploy·청취는 별개 상태로 보고한다. 실험 자료를 자동 Git 추가하거나 삭제하지 않는다. 앱을 수정했다면 프로젝트 지침의 build-info 갱신을 따르며, 버전 상승은 사용자 커밋 지시 때만 수행한다. 문서 작업만이면 앱 빌드/버전을 바꾸지 않는다.

**실패 시 확인:** 인계 파일의 실제 존재·해시·Git 상태부터 재확인한다. 사라진 worktree, 절대 경로가 남은 venv, 불완전한 로컬 원본 때문에 재현할 수 없으면 그 선행 조건을 적는다. 별도 요청 없는 원격 통합·배포로 인계 누락을 덮지 않는다.

## 기존 도구의 재사용 범위

새 곡용 범용 자동 변환 CLI가 완성됐다는 뜻은 아니다. 아래 도구는 절차와 검증 설계를 재사용하는 출발점이다. 새 양식의 추출·fixture·메타데이터·패키지 helper를 이번 입력에 맞게 작성/검증한 뒤 곡별 문서에 **실제로 실행한 명령**을 남겨야 처음부터 재현할 수 있다.

| 도구·코드 | 확인한 인터페이스와 선행 조건 | 새 곡에서의 적용 |
|---|---|---|
| `scripts/musicxml/convert.py` → `export.py` → `verify.py` | convert: `--pdf --geometry --out`; export: `--input --out`; verify: `--xml --ir --schema --out`. Real Paradis 해시/geometry·전용 예외에 결합 | 구조를 참고. 새 입력에 그대로 실행하지 않음 |
| `scripts/musicxml/loveholic.py`, `verify_loveholic.py` | `--pdf --out`, `--dir`. 원본 해시, provenance, Poppler 페이지, 로컬 XSD, 원본 fixture 필요 | Opus 좌표·마디 예외를 새로 평가. 보존 결과에 재실행하지 않음 |
| `loveholic_printed_lyrics.py`, `loveholic_lyric_notes.py` | 원본 문자 bbox·이벤트와 동일 원본 해시. 후자 `--dir --out` | 직접 음표 대응/추정표의 검증 방법을 참고 |
| `loveholic_audio.py` | `--audio --bars --out`; ffmpeg·numpy 필요. 신호 분석 추정 출력 | 새 곡의 위상·템포·변화 구간을 다시 검증 |
| `loveholic_package.mjs` | Vite 브라우저 모듈, 특정 곡 경로/해시/개수·loopback 수신기에 결합 | 범용 명령으로 제시하지 않음. 공통 API 사용 방법을 참고 |
| `src/canonical-xml.ts`, `src/musicxml.ts`, `src/score-package.ts` | 브라우저 DOM/Blob 계약, 현재 공통 정본/조판/ZIP API | 새 곡도 공통 계약으로 저장·렌더·재읽기 |
| `src/browser-score.ts`, `src/practice-library.ts` | 공통 조판 결과와 실제 저장/업데이트 계약 | 실제 앱 수록·재열기에 사용 |

실행 환경에는 Node/package lock, Python interpreter·라이브러리, Poppler/ffmpeg, 로컬 XSD의 `musicxml.xsd/xml.xsd/xlink.xsd`, 사용한 Audiveris/OSMD 버전을 기록한다. `scripts/musicxml/requirements.txt`의 기존 환경에 numpy·ffmpeg까지 포함된다고 가정하지 않는다. 이동된 venv는 별도 재생성하거나 정상 interpreter를 확인한다. [Loveholic 재현 절](LOVEHOLIC-CONVERSION.md#근거재현-경로)은 해당 곡의 정확한 선행 파일과 명령 예다.

변환/저장 코드 변경에는 관련 `musicxml`, `canonical-xml`, `score-package` 테스트부터 실행하고, 영향 범위에 따라 `npm run test:drum`·TypeScript·관련 Python 검사를 수행한다. 실제 fixture가 없는 실패를 삭제로 우회하지 않는다. 기본 `npm test`의 하위 기타 프로젝트 수집 문제와 기본 빌드의 portable 템플릿 생성 여부는 기존 지침을 확인한다. 문서만 변경한 작업에는 악보 재생성·앱 빌드·청취를 실행한 것처럼 기록하지 않는다.

### 확인한 자료와 현재 미확인 사항 — 2026-10-04

이번 문서 정비에서 제작 문서·history·정본·기존 도구 인터페이스와 보존된 원시 자료를 읽었다. 위 두 제작 세션의 보존 요약도 대조했다. 전체 과거 대화를 다시 전수 열람하거나 악보를 재생성하지는 않았다.

- Real Paradis 보존 후보 `experiments/musicxml/real-paradis-110-candidate.musicxml`의 현재 해시가 기록의 `d5033d473bef0a63d2ded5f2e09234b168b7306d1872fdce9981d9864516f8f6`와 일치한다. 재현 폴더와 Audiveris 원시 보고서도 존재한다. 이는 현재 앱의 XML을 이 과거 후보로 교체하라는 뜻이 아니다.
- Loveholic의 최초/재생성 `verification.json`, 표준 가사 `printed-note-lyrics.json` 및 실제 표시 `note-centre-alignment-after.json`을 확인했다. 최종 표시 자료는269개·문자 불일치0·최대0.0972342316px,25–32마디27개 최대0.0229176475px다. 당시 패키지 해시18c741…는 보존된 그 시점의 결과다.
- 현재 로컬 수록 ZIP을 읽은 결과 Loveholic123마디/269가사/firstBeat0.193초/BPM136, Real Paradis110마디/515가사/firstBeat0.38897134124462235초/BPM94다. 수록 해시는 각각 `2a544df486c26feca450e7021787e43c4ad6db4fc8f8be1dc6d49d5f4cbcaf50`, `9673fb348e3c84f9f7789ccdc07fffcea414d36161fcb3496047e0fec3fca8e4`로 초기 제작 패키지와 다르다. 현재 파일의 존재/메타데이터 확인이며 새 재생 검수가 아니다.
- 카운트오프 로컬 수정은 현재 미커밋 `src/model.ts`에 있으며 history에90파일441테스트·build26dbe96c 기록이 있다. 이번 문서 작업에서 테스트를 다시 실행하지 않았다. 실물 iPad OFF/ON 청취·이 수정의 공개 배포는 미확인이다.
- 두 곡 전곡의 독립 외부 이중 전사, 스캔·사진 신규 곡에서 위 경로의 전체 제작 성공, 모든 새 양식/주법·다른 소비자에서의 렌더/확장 필드 왕복은 확인하지 않았다. 현재 방식은 두 벡터 PDF의 경험을 일반화한 절차이며 성능·정확도 보증이 아니다.
- 이번 작업은 문서 정비다. 실제 앱 재생·기기 청취·새 패키지 생성·수록 교체·commit·push·발행은 수행하지 않았다. 다음 곡에서는 그 곡의 실제 환경·입력으로 각 단계의 근거를 새로 만든다.
